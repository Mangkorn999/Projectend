## 2. ปูพื้นฐานจากศูนย์: แปลงโค้ดโปรเจกต์เป็น if / for ที่คุณคุ้นเคย

ถ้าคุณรู้แค่ `if`, `else`, `for`, `while`, `console.log` ให้จำไว้เสมอว่า: **"ไวยากรณ์แปลกๆ ในโปรเจกต์นี้ ย่อมาจาก if และ for ทั้งสิ้น"**

### 2.1 Arrow Function (`=>`) = ฟังก์ชันปกติ
```javascript
// โค้ดในโปรเจกต์:
const isPass = (score) => score >= 60;

// ความหมายที่แท้จริง (แบบที่คุณคุ้นเคย):
function isPass(score) {
  if (score >= 60) {
    return true;
  } else {
    return false;
  }
}
```

### 2.2 Array Method ยอดฮิต = for + if
ทุกครั้งที่เจอ `.map()`, `.filter()`, `.find()` ในโค้ด ให้มองเป็นลูป `for`:

#### ก. `.filter()` = คัดเฉพาะของที่ตรงตามเงื่อนไข
```javascript
// โค้ดในโปรเจกต์ (dashboard.service.js):
const passedResults = results.filter(r => r.staff_status === "approved");

// ความหมายที่แท้จริง:
const passedResults = [];
for (let i = 0; i < results.length; i++) {
  if (results[i].staff_status === "approved") {
    passedResults.push(results[i]);
  }
}
```

#### ข. `.map()` = แปลงข้อมูลทุกตัวในลิสต์เป็นรูปแบบใหม่
```javascript
// โค้ดในโปรเจกต์:
const studentNames = students.map(s => s.first_name);

// ความหมายที่แท้จริง:
const studentNames = [];
for (let i = 0; i < students.length; i++) {
  studentNames.push(students[i].first_name);
}
```

#### ค. `.find()` = ค้นหาตัวแรกที่ตรงเงื่อนไข เจอแล้วหยุดทันที
```javascript
// โค้ดในโปรเจกต์:
const foundUser = users.find(u => u.user_id === 5);

// ความหมายที่แท้จริง:
let foundUser = null;
for (let i = 0; i < users.length; i++) {
  if (users[i].user_id === 5) {
    foundUser = users[i];
    break; // เจอแล้วหยุดวน
  }
}
```

#### ง. `.every()` = ตรวจว่า "ทุกตัว" ผ่านเงื่อนไขจริงไหม
```javascript
// โค้ดในโปรเจกต์ (ตรวจว่า 8 วิชาผ่านหมดไหม):
const isAllPassed = subjects.every(s => s.is_pass === true);

// ความหมายที่แท้จริง:
let isAllPassed = true;
for (let i = 0; i < subjects.length; i++) {
  if (subjects[i].is_pass !== true) {
    isAllPassed = false;
    break; // เจอไม่ผ่านตัวเดียว ถือว่าไม่ผ่านทั้งหมดทันที
  }
}
```

### 2.3 เครื่องหมายตัดสินใจแบบย่อ
* **Ternary (`? :`):** `const status = score >= 60 ? "ผ่าน" : "ไม่ผ่าน";`  
  👉 คือ `if (score >= 60) status = "ผ่าน"; else status = "ไม่ผ่าน";`
* **Optional Chaining (`?.`):** `user?.student?.room_id`  
  👉 คือ `if (user != null && user.student != null) return user.student.room_id; else return undefined;` (ป้องกันโค้ดค้าง/พังเวลาเจอค่าว่าง)
* **Nullish Coalescing (`??`):** `const name = input_name ?? "ไม่มีชื่อ";`  
  👉 คือถ้า `input_name` เป็น `null` หรือ `undefined` ให้ใช้ค่า `"ไม่มีชื่อ"` แทน

### 2.4 `async / await` และ `try / catch` = การรอคอยงานที่ช้า
การติดต่อ Database หรือเรียก API ผ่านเน็ตไม่ได้เสร็จทันที
* `await` = **"หยุดรอบรรทัดนี้ให้ทำงานเสร็จก่อน"** ค่อยไปบรรทัดถัดไป
* `try { ... } catch (err) { ... }` = ลองทำใน `try` ถ้าเกิด error (เช่น เน็ตหลุด, database ล่ม) โค้ดจะไม่พังทั้งโปรแกรม แต่จะกระโดดไปทำงานใน `catch` เพื่อบันทึก log หรือส่งข้อความเตือน

## 3. สถาปัตยกรรมระบบ & เส้นทางเดินของข้อมูล (Data Flow)

ระบบเราใช้ **Client-Server Architecture** แบบ 4 ชั้น (4-Tier Architecture):

```
┌─────────────────────────────────────────────────────────────┐
│ 1. Frontend (React 19 + Vite)                               │
│    - หน้าจอแสดงผล, จัดการ UI State                          │
│    - เรียก backend ผ่าน axios/fetch ใน api.js               │
└──────────────────────────────┬──────────────────────────────┘
                               │ HTTP Request (JSON / FormData)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. Backend (Node.js + Express 5)                            │
│    ├── routes/      : แยกลู่จราจรตาม URL                    │
│    ├── controllers/ : รับ request, ตรวจ input, ตอบ HTTP     │
│    ├── services/    : ตรรกะทางธุรกิจ (Business Rules)       │
│    └── repositories/: สั่ง Prisma ไปคุยกับ Database         │
└──────────────────────────────┬──────────────────────────────┘
                               │ SQL Query ผ่าน Prisma ORM
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. Database (PostgreSQL 16)                                 │
│    - เก็บข้อมูล 11 ตาราง มีความสัมพันธ์และ Foreign Keys     │
└─────────────────────────────────────────────────────────────┘
```

### เส้นทางข้อมูลตัวจริง (Data Flow Walkthrough): เมื่อนักศึกษากดส่งผลสอบ
1. **Frontend:** นักศึกษาติ๊กผลสอบ 8 วิชาและแนบ PDF ในหน้า `examFormReal.jsx` -> เมื่อกดปุ่ม "บันทึก" ข้อมูลถูกรวบรวมเป็น `FormData` ยิง `POST /api/exam-results` ผ่าน `api.js`
2. **Middleware:** 
   - `authenticate` ตรวจ JWT Token ใน cookie -> ดึง `user_id` ออกมา
   - `requireRole(["student"])` เช็คว่าคนนี้คือนักศึกษาจริงไหม
   - `upload` (Multer) รับไฟล์หลักฐาน เขียนลงดิสก์ที่ `uploads/`
3. **Route:** ส่งต่อไปยัง `examResults.controller.js -> create()`
4. **Controller:** เช็คเบื้องต้นว่าส่งข้อมูลมาครบไหม -> ส่งต่อให้ `examResults.service.js -> createExamResult()`
5. **Service (สมอง):** 
   - เช็คว่ารอบสอบเปิดอยู่ไหม (`isRoundOpen`)
   - นักศึกษามีสิทธิ์สอบไหม (`exam_eligible === true`)
   - ตรวจสอบความถูกต้องของผล 8 วิชา
   - ตรวจไฟล์แนบ (Magic Bytes)
6. **Repository:** ใช้ `prisma.$transaction()` บันทึกข้อมูลลง 3 ตารางพร้อมกัน:
   - บันทึกแถวใหม่ใน `exam_results`
   - บันทึก 8 แถวใน `subject_results`
   - บันทึก path ไฟล์ใน `certificates`
7. **Database:** PostgreSQL รับคำสั่ง ตรวจสอบ Foreign Key แล้วเขียนข้อมูลลง Disk สำเร็จ
8. **Response:** คืนค่า `{ success: true, message: "บันทึกสำเร็จ", data: ... }` รหัส `201 Created` กลับไปหา React เพื่อแสดง Toast สีเขียว

## 4. ผ่าโครงสร้าง Database: 11 ตาราง, ความสัมพันธ์ และ Index

โครงสร้างฐานข้อมูลนิยามอยู่ที่ `backend/prisma/schema.prisma`

### 4.1 สรุปหน้าที่ของทั้ง 11 ตาราง
1. `roles`: เก็บสิทธิ์ผู้ใช้ (`student`, `staff`, `executive`, `reviewer`)
2. `users`: บัญชีผู้ใช้ทุกคน เก็บ `psu_passport_id`, `password_hash` (bcrypt), และข้อมูลทั่วไป
3. `faculties`: ข้อมูลคณะ (ปัจจุบันคือคณะพยาบาลศาสตร์)
4. `rooms`: ห้องเรียน/กลุ่มเรียนของนักศึกษา
5. `students`: ข้อมูลเฉพาะของนักศึกษา เชื่อมกับ `users` แบบ 1:1 มีฟิลด์สำคัญ `exam_eligible` (เปิด/ปิดสิทธิ์สอบ)
6. `subjects`: รายวิชาที่ใช้สอบใบประกอบวิชาชีพ (ปัจจุบันมี 8 วิชา รหัส `1101`–`1108`)
7. `submission_rounds`: รอบการกรอกผลสอบ มี `open_date`, `close_date`, `status`
8. `exam_results`: ใบผลสอบของนักศึกษาในแต่ละรอบ มี 2 สถานะคือ `student_status` และ `staff_status`
9. `subject_results`: ผลการสอบแยกรายวิชาของแต่ละใบสอบ (ผ่าน/ไม่ผ่าน) มีฟิลด์ `carried_forward` (ยืมผลเก่ามา)
10. `certificates`: ไฟล์หลักฐานที่แนบมากับผลสอบ (เก็บเป็น path ในโฟลเดอร์ ไม่เก็บ binary ใน DB)
11. `news`: ข่าวสารและประกาศประชาสัมพันธ์

### 4.2 ตารางเสริมที่สำคัญ
* `notifications`: เก็บประวัติการแจ้งเตือนของนักศึกษา (เช่น เมื่อถูกตีกลับใบสอบ)
* `review_logs`: บันทึก Audit Log ว่าเจ้าหน้าที่คนไหน ตรวจใบสอบไหน เมื่อไหร่ ผลเป็นอย่างไร

### 4.3 กฎความสัมพันธ์ (Relationships)
* `User` (1) <---> (0..1) `Student`: ผู้ใช้ 1 คนอาจจะเป็นนักศึกษา หรือเป็นเจ้าหน้าที่/ผู้บริหารก็ได้
* `Student` (1) <---> (Many) `ExamResult`: นักศึกษา 1 คนยื่นผลสอบได้หลายรอบ
* `ExamResult` (1) <---> (8) `SubjectResult`: การส่งผล 1 ครั้งมีผลสอบย่อย 8 วิชา
* `ExamResult` (1) <---> (1..5) `Certificate`: การส่งผล 1 ครั้งแนบหลักฐานได้สูงสุด 5 ไฟล์

### 4.4 ทำไมต้องมี Index? (`@@index([academic_year])`)
* **เหตุผลที่กรรมการชอบถาม:** ตาราง `students` มีการค้นหาและกรองตาม "ปีการศึกษา" หรือ "รุ่น" ตลอดเวลา (โดยเฉพาะหน้า Dashboard)
* ถ้าไม่มี Index ระบบต้องสแกนหาทีละแถวตั้งแต่ต้นจนจบตาราง (Full Table Scan)
* เมื่อมี Index (B-Tree) PostgreSQL จะสร้างสารบัญค้นหา ทำให้หาข้อมูลตามรุ่นได้เร็วแบบ **O(log N)** ทันที

## 5. เจาะลึก Backend: สถาปัตยกรรม 4 ชั้น (Route-Controller-Service-Repository)

เราใช้หลักการ **Separation of Concerns (แยกหน้าที่กันทำ)** เพื่อให้โค้ดเป็นระเบียบ เทสง่าย และแก้ง่าย:

```
[Request จากภายนอก]
         │
         ▼
[1. Route] ────────► ทำหน้าที่: กำหนด URL, เช็ค HTTP Method, แปะ Middleware (Auth/Role)
         │
         ▼
[2. Controller] ────► ทำหน้าที่: แกะ req.body, req.params, validate รูปแบบข้อมูล, ส่ง HTTP Status
         │
         ▼
[3. Service] ───────► ทำหน้าที่: สมอง! คำนวณ business logic, ตรวจสิทธิ์, อัลกอริทึม
         │
         ▼
[4. Repository] ────► ทำหน้าที่: คุยกับ Prisma ORM เท่านั้น (SELECT, INSERT, UPDATE, DELETE)
         │
         ▼
[PostgreSQL Database]
```

### คำตอบเมื่อกรรมการถาม: "ทำไมไม่เขียนรวมกันในไฟล์เดียว?"
> *"การแยกเป็น 4 ชั้นทำให้ระบบมี **High Cohesion and Low Coupling** ครับ เช่น ถ้าวันหนึ่งเราต้องการเปลี่ยน Database จาก PostgreSQL ไปใช้ MongoDB เราจะแก้ไขโค้ดเฉพาะในชั้น **Repository** เท่านั้น โดยที่ logic ในชั้น **Service** และ **Controller** ยังคงทำงานได้เหมือนเดิม 100% โดยไม่ต้องแตะต้องเลยครับ"*

## 6. เจาะลึกความปลอดภัย (Security Architecture)

ถ้ากรรมการถามเรื่องความปลอดภัย ให้ตอบ 4 ด่านนี้:

### 1. การเก็บรหัสผ่าน (Password Hashing)
* ใช้ **`bcrypt`** ร่วมกับ Salt 10 rounds
* **ห้ามใช้ MD5 หรือ SHA-1 เด็ดขาด** เพราะถอดรหัสผ่าน Rainbow Table ได้ง่าย
* ระบบเก็บเฉพาะ Hash เท่านั้น แม้ Database หลุด ข้อมูลรหัสผ่านจริงก็ยังปลอดภัย

### 2. การยืนยันตัวตน (Authentication & JWT)
* เมื่อ Login ผ่าน ระบบจะสร้าง **JSON Web Token (JWT)**
* Payload ใน Token เก็บ: `user_id`, `role_name`, `student_id`
* เซ็นกำกับด้วย Secret Key ใน `.env` ป้องกันการปลอมแปลง

### 3. การเก็บ Token ป้องกันการถูกขโมย (XSS vs CSRF)
* เก็บ Token ใน **`httpOnly Cookie`**
* **ทำไมไม่เก็บใน localStorage?** เพราะ JavaScript ฝั่งหน้าเว็บอ่านไม่ได้ ทำให้ปลอดภัยจากการโจมตีประเภท **XSS (Cross-Site Scripting)** 100%

### 4. การตรวจสอบไฟล์อัปโหลด (Magic Bytes Inspection)
* ตรวจสอบไฟล์ที่อัปโหลดที่ฟังก์ชัน `detectFileType()` ใน `certificates.controller.js`
* **ไม่เชื่อแค่นามสกุลไฟล์ (`.pdf`, `.png`)** เพราะผู้ไม่หวังดีสามารถเปลี่ยนนามสกุลไฟล์ไวรัส `.exe` ให้เป็น `.pdf` ได้
* ระบบอ่าน 4 ไบต์แรกของเนื้อหาไฟล์จริง:
  * PDF: ต้องขึ้นต้นด้วย `%PDF` (`0x25 0x50 0x44 0x46`)
  * PNG: ต้องขึ้นต้นด้วย `0x89 0x50 0x4E 0x47`
  * JPEG: ต้องขึ้นต้นด้วย `0xFF 0xD8 0xFF`

## 7. 12 อัลกอริทึม & Business Logic สำคัญของระบบ

### 1. อัลกอริทึมการตรวจสอบ 8 วิชา (`validateSubjectResults`)
* นักศึกษาต้องส่งผลสอบครบทั้ง 8 วิชาที่มีอยู่ในตาราง `subjects`
* ห้ามมีวิชาซ้ำ และรหัสวิชาต้องมีอยู่จริงในระบบ

### 2. การยกยอดผลสอบเดิม (Carried Forward Logic)
* ในการสอบใบประกอบวิชาชีพ วิชาใดที่ **"เคยสอบผ่านแล้วในรอบก่อนหน้าที่ได้รับการอนุมัติ (approved)"** จะคงสถานะผ่านตลอดไป
* เมื่อนักศึกษากรอกรอบใหม่ ระบบจะตั้งค่า `carried_forward = true` ให้วิชาที่เคยผ่าน เพื่อให้รู้ว่าไม่ได้สอบใหม่ในรอบนี้

### 3. การคำนวณอัตราการผ่านบน Dashboard (Pass Rate Algorithm)
* สูตร: `(จำนวนคนที่ผ่านครบ 8 วิชา / จำนวนคนที่เข้าสอบจริงทั้งหมด) * 100`
* **กฎสำคัญ (แก้วันที่ 9 ส.ค.):** ตัดเฉพาะใบสอบที่ **"ถูกตีกลับ (rejected)"** ออกจากการคำนวณ ส่วนใบที่ "รอตรวจ" ให้นำมาคิดเป็นผู้เข้าสอบ เพื่อไม่ให้กราฟ Dashboard ว่างเปล่าขณะรอเจ้าหน้าที่ตรวจ

### 4. การจัดการ Transaction (`prisma.$transaction`)
* เมื่อนักศึกษาส่งผลสอบ ต้องบันทึก `exam_results` + `subject_results` 8 แถว + `certificates`
* ถ้าบันทึกวิชาที่ 5 แล้วเกิด Database ดับ หรือไฟล์มีปัญหา ระบบจะ **Rollback (ยกเลิกทั้งหมด)** เสมือนไม่เคยมีอะไรเกิดขึ้น ป้องกันปัญหาข้อมูลขยะตกค้าง

### 5. Timezone ไทย (UTC+7) เสมอ
* ฟังก์ชัน `parseThaiDateTime()` แปลงวันที่เปิด-ปิดรอบให้เป็นเวลาประเทศไทย UTC+7 เสมอ
* **ห้ามใช้ `new Date().setHours()`** เพราะจะใช้ timezone ของเครื่อง Server ทำให้ถ้า deploy บน Cloud ต่างประเทศ รอบสอบจะเปิด-ปิดผิดเวลา!

### 6. การแก้ใบสอบที่ถูกตีกลับได้แม้รอบปิด (`findSubmittableRound`)
* ถ้าใบสอบของนักศึกษาถูกเจ้าหน้าที่ "ตีกลับ (rejected)" นักศึกษาจะได้รับสิทธิ์ให้ส่งแก้ตัวใหม่ได้ แม้ว่ารอบสอบนั้นจะเลยกำหนด `close_date` ไปแล้วก็ตาม (เพื่อความเป็นธรรมต่อนักศึกษาที่ถูกตีกลับในวันสุดท้าย)

## 8. ทำความเข้าใจ Frontend (React 19) ในมุมมองคนเขียน Backend

แม้คุณจะดูแล Backend แต่เกณฑ์ให้คะแนนวัดทั้งระบบ! นี่คือ 4 สิ่งที่ต้องรู้ใน React:

1. **State (`useState`):** กล่องเก็บข้อมูลบนหน้าจอ เมื่อข้อมูลในกล่องเปลี่ยน React จะวาดหน้าจอใหม่ทันที
   ```jsx
   const [results, setResults] = useState([]); // กล่องเก็บรายการผลสอบ
   ```
2. **Effect (`useEffect`):** ฟังก์ชันที่ทำงานอัตโนมัติเมื่อเปิดหน้าเว็บขึ้นมา มักใช้ยิง API ไปขอข้อมูลจาก Backend
   ```jsx
   useEffect(() => {
     api.get("/api/exam-results/me").then(res => setResults(res.data));
   }, []); // [] ว่าง = ทำงานแค่ครั้งเดียวตอนโหลดหน้าเว็บ
   ```
3. **Props:** การส่งข้อมูลจาก Component พ่อ ไปให้ Component ลูก
4. **Conditional Rendering:** การใช้ `if` แบบย่อเพื่อเลือกแสดงผลบนหน้าจอ เช่น
   ```jsx
   {isLoading ? <p>กำลังโหลด...</p> : <Table data={results} />}
   ```

## 10. คลังคำถาม-คำตอบมัดใจกรรมการ 20 ข้อเด็ด

### หมวดที่ 1: สถาปัตยกรรม & ฐานข้อมูล
**Q1: ทำไมเลือกใช้ PostgreSQL แทน MySQL?**
> **A:** PostgreSQL มีความเข้มงวดด้าน Data Integrity สูงกว่า รองรับการทำ Transaction ที่ซับซ้อน และทำงานร่วมกับ Prisma ORM ได้อย่างมีประสิทธิภาพไร้รอยต่อครับ

**Q2: ทำไมเลือกใช้ Prisma ORM แทนการเขียน Raw SQL?**
> **A:** Prisma ช่วยสร้าง Type-Safety ป้องกันข้อผิดพลาดจากการพิมพ์ชื่อฟิลด์ผิด มีระบบ Migration ที่ติดตามประวัติการแก้ Database ได้ชัดเจน และช่วยป้องกัน SQL Injection ได้อัตโนมัติแบบ 100% ครับ

**Q3: ความสัมพันธ์ระหว่าง User กับ Student ทำไมแยกเป็น 2 ตาราง?**
> **A:** ใช้หลักการ Data Normalization ครับ เพราะระบบมีผู้ใช้งานหลายกลุ่ม (เจ้าหน้าที่, ผู้บริหาร, นักศึกษา) ซึ่งเจ้าหน้าที่ไม่จำเป็นต้องมีข้อมูลรหัสนักศึกษาหรือห้องเรียน การแยกตารางทำให้ตาราง User กระชับ และตาราง Student เก็บเฉพาะข้อมูลที่จำเป็นจริงๆ ตามหลัก PDPA ครับ

### หมวดที่ 2: ความปลอดภัย & ประสิทธิภาพ
**Q4: ป้องกัน SQL Injection อย่างไร?**
> **A:** ทุก Query ทำผ่าน Prisma ซึ่งใช้ **Prepared Statements / Parameterized Queries** ภายในตัวแปร ทำให้ Input ของผู้ใช้ถูกมองเป็นข้อมูล (Data) เสมอ ไม่สามารถถูกตีความเป็นคำสั่ง SQL ได้ครับ

**Q5: ป้องกัน XSS (Cross-Site Scripting) อย่างไร?**
> **A:** เราเก็บ JWT ไว้ใน **`httpOnly Cookie`** ทำให้ Script ฝั่ง Client ไม่สามารถเข้าถึงหรือขโมย Token ได้ และ React มีระบบ Auto-Escape ตัวอักษรพิเศษก่อน Render ลงหน้าเว็บโดยธรรมชาติครับ

**Q6: ระบบรองรับนักศึกษาพร้อมกันเป็นพันคนได้อย่างไร?**
> **A:** Node.js มีจุดเด่นด้าน **Non-blocking I/O (Asynchronous)** ทำให้ไม่บล็อก Thread ขณะรอ Database และที่ฝั่ง Database เรามีการทำ **Index** ในคอลัมน์ที่มีการสืบค้นบ่อย เช่น `academic_year` ทำให้ค้นหาข้อมูลได้รวดเร็วครับ

### หมวดที่ 3: กฎธุรกิจ & อัลกอริทึม
**Q7: อธิบายหลักการ Carried Forward ของผลสอบ?**
> **A:** เป็นการอำนวยความสะดวกตามระเบียบวิชาชีพครับ ถ้านักศึกษาสอบผ่านวิชาใดแล้วในรอบก่อนที่ได้รับการรับรอง ข้อมูลวิชานั้นจะถูกดึงมาใส่อัตโนมัติและตั้งสถานะ `carried_forward = true` เพื่อให้นักศึกษาเลือกลงสอบเฉพาะวิชาที่ยังไม่ผ่านได้ครับ

**Q8: ถ้ามีคนอัปโหลดไฟล์ไวรัสมาในระบบ จะเกิดอะไรขึ้น?**
> **A:** ระบบมีฟังก์ชัน `detectFileType()` คอยตรวจ Magic Bytes ของไบนารีไฟล์จริง ถ้าไบต์แรกไม่ใช่โครงสร้างของ PDF, PNG หรือ JPEG ระบบจะปฏิเสธการอัปโหลดทันที และไฟล์ที่เซฟจะถูกเปลี่ยนชื่อสุ่มใหม่ทั้งหมด ไม่รันไฟล์บน Server ครับ

### 12.2 ข้อจำกัดที่รู้อยู่แล้ว (เขียนในรายงานหัวข้อ "ข้อจำกัดและข้อเสนอแนะ")
1. **รหัสผ่านนักศึกษา = เลขบัตรประชาชน** — เลือกเพราะคณะไม่มีระบบอีเมล/SSO และเจ้าหน้าที่ต้องรีเซ็ตให้ได้ (รู้เลขบัตรอยู่แล้ว) · ลดความเสี่ยง: เก็บเป็น bcrypt hash, นักศึกษาเปลี่ยนรหัสเองได้, จำกัดการเดา 10 ครั้ง/15 นาที · อนาคต: บังคับตั้งรหัสเองครั้งแรก หรือเชื่อม PSU Passport
2. **token เพิกถอนทันทีไม่ได้** — เปลี่ยน/รีเซ็ตรหัสแล้วเครื่องเดิมใช้ต่อได้ถึง 24 ชม. (ระบบเช็กบัญชีกับ DB ทุก request จึงตัดทันทีได้เฉพาะ "ปิดบัญชี") · อนาคต: เพิ่มคอลัมน์ `password_changed_at` แล้วเทียบกับเวลาออก token
3. **เปิดรอบพร้อมกันสองเครื่อง** อาจเปิดได้ 2 รอบ (เช็คแล้วค่อยเขียน ไม่มีล็อก) — เจ้าหน้าที่มี 1–3 คน โอกาสต่ำ · อนาคต: unique index แบบมีเงื่อนไข (`status = 'open'`)
4. **สถิติรายรอบ vs รายปี** ต่างกันได้ในกรณีใบต้นทางถูกตีกลับภายหลัง (รายรอบนับวิชาที่ยกมา รายปีไม่นับ) — ตั้งใจ: รายรอบตอบ "จบรอบนี้ครบไหม" รายปีตอบ "ผ่านจริงตามหลักฐานที่ยืนยันแล้ว"
5. **ไฟล์ใหญ่** (`student.controller.js` ~920 บรรทัด, `dashboard.service.js` 964, `dashboardReal.jsx` 1,260) — มีเทสคุมครบ จึงไม่รื้อก่อนสอบ · อนาคต: แยกตามหน้าที่ต่อ (นำเข้า / ส่งออก ทำแล้วส่วนส่งออก)

### 12.3 แผน deploy (ยังไม่ deploy — เขียนเป็นข้อเสนอแนะ ไม่ต้องทำก่อนสอบ)
HTTPS ผ่านเว็บเซิร์ฟเวอร์ด้านหน้า (ตั้ง `COOKIE_SECURE=true`) · `pg_dump` ตั้งเวลา + สำเนาโฟลเดอร์ `backend/uploads/` · ตัวนับจำกัดการเดารหัสอยู่ใน memory เครื่องเดียว (ถ้ารันหลายเครื่องต้องย้ายไป Redis) · ตั้ง `NODE_ENV=production` ไม่ให้ error แสดง stack
