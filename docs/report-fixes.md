## A. บทที่ 4 — หน้าจอระบบ

### A1. วิธีเข้าสู่ระบบ — แก้ 3 จุด (4.1.1, 4.2.1, 4.3.1)

ระบบ **ไม่ได้ใช้ PSU One Passport** เพราะขอ credential จากศูนย์คอมพิวเตอร์ไม่ได้ จึงทำระบบ login เองโดยเก็บรหัสผ่านเป็น bcrypt hash

| เดิม | แก้เป็น |
|---|---|
| หน้าจอเข้าสู่ระบบ นักศึกษาสามารถเข้าสู่ระบบโดยการใช้บัญชี PSU One Passport | หน้าจอเข้าสู่ระบบ นักศึกษาเข้าสู่ระบบด้วยรหัสนักศึกษาและรหัสผ่านที่ตั้งไว้ในระบบ โดยการเข้าใช้งานครั้งแรกต้องตั้งรหัสผ่านด้วยตนเองผ่านหน้า "เข้าใช้งานครั้งแรก" ซึ่งต้องกรอกรหัสนักศึกษาพร้อมชื่อ-นามสกุลให้ตรงกับข้อมูลที่เจ้าหน้าที่นำเข้าระบบไว้ |
| หน้าจอเข้าสู่ระบบ เจ้าหน้าที่สามารถเข้าสู่ระบบโดยการใช้บัญชี PSU One Passport | หน้าจอเข้าสู่ระบบ เจ้าหน้าที่เข้าสู่ระบบด้วยรหัสผู้ใช้และรหัสผ่านที่ตั้งไว้ในระบบ |
| หน้าจอเข้าสู่ระบบ ผู้บริหารสามารถเข้าสู่ระบบโดยการใช้บัญชี PSU One Passport | หน้าจอเข้าสู่ระบบ ผู้บริหารคณะเข้าสู่ระบบด้วยรหัสผู้ใช้และรหัสผ่านที่ตั้งไว้ในระบบ โดยเจ้าหน้าที่เป็นผู้สร้างบัญชีให้ และผู้บริหารเป็นผู้ตั้งรหัสผ่านเองในการเข้าใช้งานครั้งแรก |

> ถ้าในบทที่ 1 หรือ 2 มีข้อความว่าใช้ PSU One Passport ยืนยันตัวตน ต้องแก้ให้ตรงกันด้วย และควรเขียนเหตุผลไว้ว่า *"เดิมออกแบบให้ยืนยันตัวตนผ่าน PSU One Passport แต่ไม่สามารถขอสิทธิ์เชื่อมต่อได้ จึงพัฒนาระบบยืนยันตัวตนภายในแทน"* — เป็นการอธิบายการเปลี่ยนแปลง ไม่ใช่ข้อผิดพลาด

### A2. ลบหัวข้อ 4.1.4 หน้าการกรอกรหัสเว็ปสภา

ระบบตัดฟีเจอร์นี้ออกแล้ว (ลบทั้งหน้าจอและ field ในฐานข้อมูล) เพราะการเก็บรหัสผ่านเว็บสภาการพยาบาลของนักศึกษาเป็นความเสี่ยงด้านความปลอดภัย

- ลบหัวข้อ **4.1.4** พร้อมภาพที่ 4.1.4 ทั้งหมด
- เลื่อนเลขหัวข้อที่เหลือขึ้น: 4.1.5 → 4.1.4, 4.1.6 → 4.1.5, 4.1.7 → 4.1.6 (พร้อมเลขภาพ)

### A3. ลบหัวข้อ 4.3.3 และ 4.3.4 (หน้าจอผู้บริหาร)

ผู้บริหารคณะไม่มีสิทธิ์เข้าถึงข้อมูลนักศึกษารายบุคคลแล้ว เห็นได้เฉพาะภาพรวมและสถิติ (หลักการ data minimization — ผู้บริหารใช้ตัวเลขภาพรวมในการตัดสินใจ ไม่จำเป็นต้องเห็นข้อมูลส่วนบุคคล)

- ลบ **4.3.3 หน้าจอรายละเอียดนักศึกษา** + ภาพที่ 4.3.3
- ลบ **4.3.4 หน้าจอผลการกรอกนักศึกษา** + ภาพที่ 4.3.4
- ส่วนของผู้บริหารเหลือ 2 หัวข้อ: เข้าสู่ระบบ กับ Dashboard

เพิ่มประโยคต่อท้าย 4.3 เพื่ออธิบายขอบเขต:

> ผู้บริหารคณะเข้าถึงได้เฉพาะข้อมูลสรุปภาพรวมและสถิติเท่านั้น ไม่สามารถเข้าถึงข้อมูลนักศึกษารายบุคคล ผลการกรอกรายคน หรือไฟล์หลักฐานได้ เพื่อจำกัดการเข้าถึงข้อมูลส่วนบุคคลให้อยู่เฉพาะผู้ที่จำเป็นต้องใช้ในการปฏิบัติงาน

### A4. เพิ่มหน้าจอที่ระบบมีจริงแต่ยังไม่มีในรายงาน (หัวข้อ 4.2)

ส่วนของเจ้าหน้าที่คณะในรายงานมี 7 หน้าจอ แต่ระบบจริงมีมากกว่า ควรเพิ่ม:

| หัวข้อที่ควรเพิ่ม | คำอธิบาย |
|---|---|
| หน้าจอคิวตรวจสอบผลสอบ | เจ้าหน้าที่ดูรายการผลสอบที่นักศึกษาส่งเข้ามาและรอการตรวจสอบ พร้อมกดยืนยันหรือตีกลับพร้อมระบุเหตุผล |
| หน้าจอนำเข้ารายชื่อนักศึกษา | เจ้าหน้าที่นำเข้ารายชื่อนักศึกษาทั้งรุ่นจากไฟล์ CSV หรือเพิ่มทีละคนได้ |
| หน้าจอจัดการข่าวสารและประกาศ | เจ้าหน้าที่เพิ่ม แก้ไข ลบ ประกาศ พร้อมแนบรูปภาพประกอบได้ |
| หน้าจอรายงานผลสอบ | เจ้าหน้าที่ดูสรุปผลสอบและดาวน์โหลดรายงานเป็นไฟล์ PDF |

และแก้คำอธิบายหัวข้อ **4.2.7 จัดการผู้ใช้งาน** ให้ตรงกับระบบจริง:

> หน้าจอจัดการผู้ใช้งาน เจ้าหน้าที่สามารถเพิ่มบัญชีผู้บริหารคณะและเจ้าหน้าที่ ถอนสิทธิ์การเข้าใช้งาน และรีเซ็ตรหัสผ่านให้ผู้ใช้ที่ลืมรหัสผ่านได้ โดยเจ้าหน้าที่ไม่สามารถเห็นรหัสผ่านของผู้ใช้รายใด เนื่องจากระบบจัดเก็บเฉพาะค่าที่เข้ารหัสแล้ว และการรีเซ็ตเป็นการล้างรหัสผ่านเพื่อให้เจ้าของบัญชีตั้งใหม่ด้วยตนเอง

## B. บทที่ 3.4 — พจนานุกรมข้อมูล

รายงานมี 10 ตาราง ระบบจริงมี **12 ตาราง** — ขาด `rooms` และ `notifications`

### B1. ตาราง USERS — แก้ 1 แถว เพิ่ม 2 แถว

แก้คำอธิบายของ `psu_passport_id`:

| Field | Description เดิม | แก้เป็น |
|---|---|---|
| `psu_passport_id` | รหัส PSU One Passport | รหัสผู้ใช้สำหรับเข้าสู่ระบบ (นักศึกษาใช้รหัสนักศึกษา เจ้าหน้าที่และผู้บริหารใช้รหัสที่เจ้าหน้าที่กำหนด) |

เพิ่ม 2 แถวต่อจาก `psu_passport_id`:

| Field Name | Data Type | Field Size | Description | Example | Key Type |
|---|---|---|---|---|---|
| `password_hash` | VARCHAR | 255 | รหัสผ่านที่ผ่านการเข้ารหัสด้วย bcrypt (ค่าว่างหมายถึงยังไม่ได้ตั้งรหัสผ่าน) | `$2b$10$N9qo8uLO...` | |
| `must_change_password` | BOOLEAN | - | ต้องตั้งรหัสผ่านใหม่ก่อนใช้งานหรือไม่ | true | |

> อย่าใส่รหัสผ่านจริงเป็นตัวอย่าง ใช้ค่า hash ตัวอย่างข้างบนได้เลย และควรเขียนกำกับว่าระบบไม่จัดเก็บรหัสผ่านในรูปแบบข้อความธรรมดา

### B2. ตาราง STUDENTS — ลบ 2 แถว เพิ่ม 1 แถว

- `nursing_council_password` — รหัสผ่านสภาการพยาบาล

**เพิ่ม** 1 แถว:

| Field Name | Data Type | Field Size | Description | Example | Key Type |
|---|---|---|---|---|---|
| `exam_eligible` | BOOLEAN | - | สิทธิ์ในการกรอกผลสอบ (ค่าเริ่มต้นเป็นจริง เจ้าหน้าที่ถอนสิทธิ์รายบุคคลได้) | true | |

และแก้ประโยคนำหน้าตารางเป็น:

> ตาราง STUDENTS เป็นตารางสำหรับจัดเก็บข้อมูลนักศึกษาพยาบาล ซึ่งประกอบด้วย รหัสนักศึกษา รหัสผู้ใช้งาน รหัสคณะ รหัสห้องเรียน ปีการศึกษา และสิทธิ์ในการกรอกผลสอบ

### B6. เพิ่มตารางใหม่ — ROOMS

> ตาราง ROOMS เป็นตารางสำหรับจัดเก็บข้อมูลห้องเรียนของนักศึกษา ซึ่งประกอบด้วย รหัสห้องเรียน รหัสคณะ และชื่อห้องเรียน

| Field Name | Data Type | Field Size | Description | Example | Key Type |

ใช้แยกสถิติระหว่างห้องเรียนปกติกับห้องเรียนภาษาอังกฤษ ตรงกับตารางที่คณะส่งสภาการพยาบาล

### B7. เพิ่มตารางใหม่ — NOTIFICATIONS

> ตาราง NOTIFICATIONS เป็นตารางสำหรับจัดเก็บข้อมูลการแจ้งเตือนของนักศึกษา ซึ่งประกอบด้วย รหัสการแจ้งเตือน รหัสนักศึกษา ประเภทการแจ้งเตือน ข้อความ สถานะการอ่าน และวันที่สร้าง

| Field Name | Data Type | Field Size | Description | Example | Key Type |
|---|---|---|---|---|---|
| `notification_id` | INT | 11 | รหัสการแจ้งเตือน | 12 | PK |
| `student_id` | VARCHAR | 20 | รหัสนักศึกษาผู้รับการแจ้งเตือน | 6610210631 | FK |
| `type` | VARCHAR | 20 | ประเภท (approved / rejected / eligible) | rejected | |
| `message` | TEXT | - | ข้อความแจ้งเตือน | ผลสอบรอบ 1/2569 ถูกตีกลับ: เอกสารไม่ชัด | |

## C. บทที่ 3.3 — ER Diagram

ต้องวาดใหม่ให้ตรงกับข้อ B:

1. เพิ่ม entity **ROOMS** — เชื่อม `faculties (1) → rooms (M)` และ `rooms (1) → students (M)`
2. เพิ่ม entity **NOTIFICATIONS** — เชื่อม `students (1) → notifications (M)`
3. ลบ attribute `nursing_council_email` และ `nursing_council_password` ออกจาก STUDENTS
4. เพิ่ม attribute `password_hash`, `must_change_password` ใน USERS
5. เพิ่ม `exam_eligible` ใน STUDENTS, `subject_ids` ใน SUBMISSION_ROUNDS, `carried_forward` ใน SUBJECT_RESULTS, `image_path` ใน NEWS

ความสัมพันธ์ที่เหลือไม่เปลี่ยน — `users (1) → students (0..1)` ยังคงเป็นแบบหนึ่งต่อศูนย์หรือหนึ่ง เพราะผู้ใช้ที่เป็นเจ้าหน้าที่และผู้บริหารไม่มีข้อมูลนักศึกษา
