# 03 — Backend: ตรรกะและอัลกอริทึมทั้งหมด

ไฟล์นี้อธิบาย "สมอง" ของระบบ ทีละเรื่อง ตามลำดับที่ request วิ่งผ่าน. ทุกหัวข้อมี
**(ก) ปัญหาที่แก้ (ข) วิธีทำ (ค) ทำไมเลือกแบบนี้ (ง) ไปเปิดดูโค้ดจริง (จ) คำถามที่กรรมการอาจถาม**

## 1. Request หนึ่งครั้งเดินทางยังไง (4 ชั้น)

```
routes.js  →  controller.js  →  (service.js)  →  repository.js  →  Prisma → PostgreSQL
ต่อ middleware   ตัดสินใจ/ตรวจ input   คำนวณหนัก ๆ          คุย DB เท่านั้น
```
| ชั้น | ทำ | ห้ามทำ |
|---|---|---|
| routes | จับคู่ URL → ฟังก์ชัน + ต่อ middleware | มี logic |
| controller | ตรวจ input, เช็คสิทธิ์ระดับข้อมูล, ตัดสินใจ, ตอบ | เรียก `prisma.` ตรง ๆ |
| service | คำนวณซับซ้อนที่ใช้ซ้ำ (มีเฉพาะ dashboard) | แตะ `req`/`res` |
| repository | คุย Prisma | ตัดสินใจเชิงธุรกิจ |

**ทำไม:** แก้ที่เดียวจบ — เปลี่ยนวิธีเก็บข้อมูลแก้ repository, เปลี่ยนกฎแก้ controller.
**ท่าประจำของ controller:** `try { ตรวจ input → เรียก repository → res.json({success:true,data}) } catch (err) { next(err) }`
error ทุกตัวไปรวมที่ `middlewares/errorHandler.js` ที่เดียว → รูปแบบตอบ error เหมือนกันทั้งระบบ

**ลำดับใน `app.js` สำคัญ:** `helmet` → `cors` → `express.json()` → `cookieParser()` → routers → 404 handler → `errorHandler`
- `helmet` (เพิ่ม 1 ต.ค.) ใส่ header ความปลอดภัยมาตรฐานให้ทุกคำตอบ เช่น ห้ามเบราว์เซอร์เดาชนิดไฟล์เอง (nosniff) — ปิด 2 ตัวที่ชนกับระบบ (`contentSecurityPolicy`, และตั้ง `crossOriginResourcePolicy` เป็น cross-origin เพราะหน้าเว็บกับ backend คนละพอร์ต)
- `cookieParser` ต้องมาก่อน router ไม่งั้น `req.cookies` ว่างแล้ว `authenticate` หา token ไม่เจอ = 401 ทุก request
- `errorHandler` ต้องท้ายสุด (Express ถือว่า middleware 4 พารามิเตอร์ `(err, req, res, next)` คือตัวจัดการ error)
- CORS: `credentials: true` + ระบุ origin จริงจาก `.env` (`CORS_ORIGIN`) — **ห้ามใช้ `*`** เมื่อใช้ cookie

## 2. Authentication — login ไล่ทีละบรรทัด

**ไฟล์:** `src/controllers/authController.js`, `src/middlewares/auth.js`

### 2.1 login (`POST /api/auth/login`)
```
รับ psu_passport_id + password
  1. ตรวจว่าเป็นข้อความทั้งคู่ (กัน object ที่ทำ Prisma พัง = 500)
  2. หา user จากรหัส
  3. ไม่พบ → 401 "รหัสผู้ใช้หรือรหัสผ่านไม่ถูกต้อง"   ← ข้อความเดียวกับรหัสผิด
  4. password_hash เป็น null → 403 ยังไม่ได้ตั้งรหัส
  5. bcrypt.compare(password, hash) ผิด → 401 ข้อความเดิม
  6. jwt.sign({ userId, role, studentId, mustChangePassword }, JWT_SECRET, { expiresIn: "1d" })
  7. res.cookie("token", token, TOKEN_COOKIE_OPTIONS)        ← ส่งใน cookie ไม่ใส่ใน JSON
  8. ตอบ { must_change_password, profile_incomplete, user:{id,name,role} }
```
- **ทำไมข้อความ error ทั้งสองกรณีเหมือนกัน:** ไม่บอกว่า "ไม่มีบัญชีนี้" กับ "รหัสผิด" → ผู้โจมตีไล่เดาว่ามีรหัสผู้ใช้ไหนอยู่จริงไม่ได้ (กัน user enumeration)
- **`profile_incomplete`:** นักศึกษาที่ officer นำเข้า (มีแค่รหัส+เลขบัตร) ยังไม่มีแถวใน `students` → frontend พาไปหน้าตั้งโปรไฟล์
- **รหัสผ่านเริ่มต้นของนักศึกษา = เลขบัตรประชาชน** (ตัดสินใจแล้ว) — เก็บเป็น bcrypt hash เหมือนรหัสอื่น ไม่มี plain text ใน DB; export Excel จึง **ห้ามมีเลขบัตร** (มีเทสตรวจ)
- **เจ้าหน้าที่/ผู้บริหาร/ผู้ตรวจ:** เจ้าหน้าที่ตั้งรหัสชั่วคราวให้ตอนสร้างบัญชี → `must_change_password: true` → login ครั้งแรกใช้งานอะไรไม่ได้จนกว่าจะเปลี่ยนรหัสเอง (`PATCH /api/auth/password`)

### 2.2 `authenticate` — 3 ด่านหลักทุก request (`middlewares/auth.js`)
> โค้ดจริงแยก "ไม่มี cookie" เป็นด่านก่อนสุด และมีด่าน "นักศึกษายังไม่กรอกโปรไฟล์" ต่อท้ายด่าน 3 (ใช้ได้แค่ `/me`, `/complete-profile`, `/api/rooms`) — 401 ทุกตัวจากไฟล์นี้มี `code: "auth_required"` ให้หน้าเว็บรู้ว่าต้องเด้งไปหน้า login (ไล่ทีละบรรทัดใน `09` หัวข้อ 2)

1. **ตรวจลายเซ็น JWT** (`jwt.verify`) — ไม่มี/ผิด/หมดอายุ → 401
2. **เช็คกับ DB ว่าเจ้าของ token ยังมีอยู่และยังใช้งานได้** — ปิดช่องโหว่ 2 เรื่อง: (ก) token เก่าของ user ที่ถูกลบ/ถูกถอนสิทธิ์ (ข) token ค้างหลัง seed ใหม่ (id ไม่ตรง → เดิมพังเป็น FK error 500)
   และ **สร้าง `req.user` จาก DB ไม่ใช่จากค่าใน token** → เปลี่ยน role ให้ใครแล้วมีผลทันที
3. **ด่าน mustChangePassword** — ถ้ายังต้องเปลี่ยนรหัส ใช้ได้แค่ `/api/auth/me` กับ `/api/auth/password` นอกนั้น 403
ต้นทุน: เพิ่ม query 1 ครั้ง/request — ยอมรับได้ในระบบขนาดนี้แลกกับความถูกต้องด้านสิทธิ์

### 2.3 `requireRole("officer", "reviewer")`
`(...allowedRoles)` = rest parameter. ไม่ login → 401, role ไม่อยู่ในรายการ → 403. **role อ่านจาก `req.user` (มาจาก DB) เท่านั้น ห้ามเชื่อ role ที่ client ส่งใน body** (ข้อแรกของ Security Checklist)

### 2.4 ข้อจำกัดของ JWT ที่ต้องตอบได้
JWT เป็น stateless: logout ลบแค่ cookie ฝั่งเบราว์เซอร์ ตัว token ยังใช้ได้จนหมดอายุถ้ามีคนก๊อปไว้. **ด่าน 2 ของ authenticate คือสิ่งที่ปิดช่องนี้** (เช็ค DB ทุกครั้ง ผู้ใช้ที่ถูกถอนสิทธิ์ถูกตัดทันที). ถ้าต้อง revoke ละเอียดกว่านี้ต้องมีตาราง session (ยังไม่ทำ)

**คำถามกรรมการ:** ทำไมเก็บ token ใน cookie ไม่ใช่ localStorage? → httpOnly cookie JS อ่านไม่ได้ กัน XSS ขโมย token; `sameSite: lax` กัน CSRF

## 3. Rate limit (`middlewares/rateLimit.js`)
- **ปัญหา:** ใครก็ยิง `/auth/login` ได้โดยไม่ต้องมี token → เดารหัสรัว ๆ ได้
- **วิธี:** เก็บตัวนับใน `Map` ในหน่วยความจำ key = `path + (psu_passport_id หรือ IP)`; เกินโควตา → 429 พร้อมบอกว่าต้องรอกี่วินาที
- **ค่าปัจจุบัน:** login 10 ครั้ง/15 นาที ต่อรหัสผู้ใช้ + 60 ครั้ง/15 นาที ต่อ IP (2 ชั้น) · เปลี่ยนรหัสผ่าน (`PATCH /auth/password`) 10 ครั้ง/15 นาที ต่อ IP (ต้องกรอกรหัสเดิม = เดาได้เหมือนกัน)
- **ทำไมแยกตามรหัสผู้ใช้ ไม่ใช่แค่ IP:** คนใช้ Wi-Fi เดียวกัน (ห้อง lab) จะไม่โดนบล็อกไปด้วยกัน
- **ข้อจำกัด (ตอบตรง ๆ ได้เลย):** เก็บใน memory ของ process เดียว — รีสตาร์ท server = ตัวนับล้าง, ถ้ามีหลายเครื่องต้องย้ายไป Redis. นี่คือเหตุที่สคริปต์ทดสอบเปิด server ใหม่ทุกไฟล์ (ไม่งั้นเจอ 429)

## 4. รอบการกรอกผลสอบ (`modules/rounds/`, `utils/roundPhase.js`)

### 4.2 phase (สถานะจริง) — ดู `02` หัวข้อ 5.2
สูตร: `status ≠ open → closed` · `now < open_date → scheduled` · `now > close_date → expired` · นอกนั้น `active`
**สำคัญ:** เงื่อนไขต้องตรงกับ `rounds.repository.js → findActive()` (status = open และ open_date ≤ now ≤ close_date) ไม่งั้นหน้าจอจะ "โกหก" (เคยมีบั๊กนี้ → บันทึกเป็นบทเรียนไว้)

### 4.3 เวลาไทย (ICT) — กับดักที่พังง่ายมาก
ไทยเป็น UTC+7 ตายตัว ไม่มี daylight saving → โค้ดใช้ `ICT_OFFSET_MS = 7*3600*1000` บวกลบเอง **ห้ามใช้ `setHours()`** เพราะใช้ timezone ของเครื่อง server: ถ้า deploy บนเครื่องตั้ง UTC แล้วตั้ง "ปิดรับ 23:59" จะกลายเป็น 06:59 เช้าวันถัดไปเวลาไทย
- วันที่ไม่มีเวลา: เปิด = ต้นวัน (00:00:00), ปิด = ท้ายวัน (23:59:59.999)
- ปิดรับ 23:59 → เก็บเป็น 23:59:59.999 (รับถึงสิ้นนาทีนั้น ไม่งั้นคนส่งตอน 23:59:30 ถูกปฏิเสธทั้งที่จอบอกยังไม่ปิด)

### 4.4 `findActive` กับ `findOpenForYear`
- `findActive(year)` — **ใช้ตอนรับผลจริง**: กรองวันที่ด้วย (ส่งก่อนถึงวันเปิดถูกปฏิเสธ)
- `findOpenForYear(year)` — **ใช้ตอนแสดงผลหน้าจอ**: ไม่กรองวันที่ เพื่อให้รอบที่ตั้งไว้ล่วงหน้าแสดงได้ว่า "จะเปิดวันที่ ..."
ความปลอดภัยไม่ลด เพราะตอน POST ยังผ่าน `findActive` อยู่

**คำถามกรรมการ:** ทำไมรอบผูกกับ "รุ่น" (academic_year)? → นักศึกษาเห็น/กรอกได้เฉพาะรอบของรุ่นตัวเอง กรอกข้ามรุ่นไม่ได้ตั้งแต่ต้นเพราะหารอบจากปีของนักศึกษาเลย

## 5. ปีการศึกษาที่จบ (`utils/academicYear.js`)
- สูตร: 2 หลักแรกของรหัส = ปี พ.ศ. ที่เข้า (66 → 2566); หลักสูตร 4 ปี → **ปีจบ = 2500 + หลักแรก 2 ตัว + 4** (รหัส 66… จบ 2570)
- เคสซ้ำชั้น/ลาพัก: เจ้าหน้าที่ระบุปีจบเองตอน import/แก้ข้อมูล (`users.import_academic_year`) **นักศึกษาเลือกเองไม่ได้**
- `validateGraduationYear`: ต้อง 4 หลัก และ **ห้ามน้อยกว่าปีที่คำนวณได้** (จับความผิดที่พบบ่อยสุด: พิมพ์ "ปีที่เข้า" แทน "ปีที่จบ" → นักศึกษาจะไปอยู่รุ่นที่จบไปแล้ว)
- เมื่อนักศึกษามีผลสอบแล้ว **ย้ายรุ่นไม่ได้** (ล็อก) เพราะสถิติรุ่นเดิมจะเพี้ยน

## 6. นักศึกษากรอกผลสอบ (`examResults.controller.js → create`) ★ สำคัญที่สุด

### 6.1 ลำดับตรวจ (ถ้าข้อไหนไม่ผ่านคืน error ทันที)
1. `subject_results` ต้องเป็น array ไม่ว่าง (400)
2. นักศึกษาต้องมีตัวตน (404) และ `exam_eligible` (403)
3. หารอบที่ส่งได้ของ **รุ่นตัวเอง** ด้วย `findSubmittableRound` (หัวข้อ 6.4) — รอบที่เปิดรับอยู่ (`findActive`) หรือ ถ้าไม่มี = รอบล่าสุดที่ใบของคนนี้ถูกตีกลับ (400 ถ้าไม่มีทั้งคู่)
4. ถ้ามีใบของรอบนี้แล้วและ **ยืนยันแล้ว → 409** (ล็อก) · ถ้ามาทาง "แก้หลังปิดรอบ" ใบต้อง **ยังถูกตีกลับอยู่** (`stillRejected`) ไม่งั้น 400 · ถ้ายังไม่ยืนยัน = แก้ทับ (`isRedo`)
5. ตรวจรายการที่ส่งมาทีละอัน: วิชาต้องอยู่ในรอบ · `is_passed` ต้องเป็น **boolean จริง** (ถ้าปล่อย string `"false"` จะถูกแปลงเป็น true) · วิชาซ้ำไม่ได้
6. ต้องตอบครบทุกวิชาที่ "ยังต้องตอบ"

### 6.2 กฎ carry-forward (ยกผลรอบก่อน) — หัวใจของระบบ
**ปัญหา:** รอบ 1 นักศึกษาผ่าน 5 จาก 8 วิชา รอบ 2 สอบเฉพาะ 3 วิชาที่เหลือ — ไม่ควรให้กรอก 5 วิชาเดิมซ้ำ และไม่ควรให้แก้ผลที่ผ่านไปแล้วเป็น "ไม่ผ่าน"

**วิธี:** ก่อนบันทึก หา `passedIds` = วิชาที่นักศึกษาคนนี้เคยผ่าน **จริง** (ไม่ใช่แถวที่ยกมา) ในใบ **ของรอบอื่น** ที่ไม่ถูกตีกลับ (`findPassedSubjectIds(studentId, excludeRoundId)`)
- วิชาที่ใน `passedIds` → **บังคับเป็นผ่าน** ไม่สนค่าที่ client ส่งมา + ติดธง `carried_forward = true`
- วิชาอื่น → ใช้คำตอบที่กรอก `carried_forward = false`
- `mustAnswer = วิชาของรอบ − passedIds` ต้องตอบครบเฉพาะชุดนี้

**ตัวอย่าง (เหมือนเทส `smoke-phase24`):** S2 รอบ 1 ได้ [ผ่าน, ตก, ตก] ยืนยันแล้ว → รอบ 2 ส่ง [ตก(พยายามแก้), ผ่าน, ผ่าน] → ผลที่บันทึก = [ผ่าน(ยกมา, carried), ผ่าน(จริง), ผ่าน(จริง)] (วิชา 1 ไม่เปลี่ยนเป็นตก)

**รายละเอียดที่ละเอียดอ่อน (พูดให้ได้):**
| เรื่อง | กฎ | เหตุผล |
|---|---|---|
| ใบที่ถูกตีกลับ | ไม่นับเป็น "ผ่านแล้ว" (`staff_status: { not: "rejected" }`) | ผลในใบนั้นเชื่อยังไม่ได้ ไม่งั้นใบรอบก่อนที่โดนตีกลับจะย้อนมาล็อกวิชารอบถัดไปจนแก้ไม่ได้ |
| ใบรอตรวจ (pending) | นับเป็นผ่านให้ | ไม่งั้นเปิดรอบถัดไปก่อนตรวจครบ นักศึกษาต้องกรอกวิชาที่เพิ่งผ่านซ้ำ |
| **แถวที่ยกมา (`carried_forward = true`)** | **ไม่นับ** (แก้บั๊ก B1 — 1 ต.ค.) | แถวยกมาเป็นสำเนา ถ้าใบต้นทางถูกตีกลับภายหลัง สำเนาต้องไม่ไปล็อกรอบถัดไป · ถ้าใบต้นทางดี แถวจริงในใบต้นทางถูกนับอยู่แล้ว (ดูเรื่องเล่า B1 ใน `09` หัวข้อ 6) |
| แก้ใบเดิม (redo) | ส่ง `excludeRoundId` ตัดใบของรอบนี้ออก | วิชาที่ผ่านในใบที่ถูกตีกลับต้องกลับมาแก้ได้ |
| ส่งใหม่ | ใช้ `resubmitWithSubjects` ทับใบเดิม (result_id เดิม) | ไม่สร้าง 2 ใบในรอบเดียว + มี unique(student_id, round_id) กันที่ DB อีกชั้น |
| บันทึก | ใช้ `$transaction` ทั้งใบ + ผลรายวิชา | เขียนครบหรือไม่เขียนเลย ไม่ค้างครึ่ง ๆ |

**ทำไมถึงไม่เชื่อค่าจาก client:** ผู้ใช้แก้โค้ดในเบราว์เซอร์/ยิง API เองได้ — กฎธุรกิจสำคัญต้องบังคับที่ backend เสมอ

### 6.3 ไฟล์หลักฐาน (`certificates.controller.js`, `middlewares/upload.js`) — **เปลี่ยนใหญ่ 1 ต.ค.**
**เดิม:** 1 ไฟล์ PDF ต่อชนิดเอกสาร อัปโหลดใหม่ = แทนที่ไฟล์เดิม
**ตอนนี้:** หลายไฟล์ **PDF / JPG / PNG สูงสุด 5 ไฟล์ต่อใบ** (`MAX_FILES_PER_RESULT`) ไฟล์ละ ≤ 10 MB · แนบเพิ่ม = ต่อท้าย · ลบทีละไฟล์ด้วย `DELETE /api/certificates/:id` · ไม่ต้องแก้ schema (ตาราง `certificates` เป็น 1:M อยู่แล้ว)

**ด่านตรวจตอนแนบ (`upload`) เรียงตามลำดับ**
1. **multer** (`upload.js → uploadEvidence`): ชนิดที่เบราว์เซอร์บอก (`EVIDENCE_TYPES`) ต้องเป็น pdf/jpeg/png + ขนาด ≤ 10 MB · ตั้งชื่อไฟล์บนดิสก์เอง (`เวลา-เลขสุ่ม.นามสกุล`) ไม่ใช้ชื่อจากผู้ใช้ (กัน path traversal)
2. ต้องมีไฟล์ + `certificate_type` ต้องเป็นค่าที่รู้จัก (`exam_result` / `license`)
3. **`ensureCanChangeEvidence`** (ใช้ทั้งแนบและลบ): เป็นเจ้าของใบ (403) · ใบยังไม่ยืนยัน (409) · ใบต้องเป็นใบของรอบที่ `findSubmittableRound` คืนมา (409) — เท่ากับ "รอบเปิดอยู่ หรือ ใบถูกตีกลับของรอบล่าสุด"
4. **`detectFileType`** อ่าน 8 ไบต์แรกเทียบ **magic bytes** (`%PDF-`, `FF D8 FF`, `89 50 4E 47 …`) — ไม่ตรง → 400 (กันไฟล์ปลอมที่เปลี่ยนนามสกุล) · เก็บ `file_type` ตามเนื้อไฟล์จริง
5. นับไฟล์ในใบ ≥ 5 → 400
6. บันทึกแถว → **นับซ้ำหลังบันทึก** ถ้าเกิน 5 (กดแนบพร้อมกันหลายไฟล์) หรือใบถูกยืนยันระหว่างอัปโหลด → ถอนแถวที่เพิ่งบันทึก + error
7. ทุกทางที่ล้มก่อนบันทึกสำเร็จ (ตัวแปร `saved`) → ลบไฟล์บนดิสก์ทิ้ง (`discard`) ไม่มีไฟล์กำพร้า
(ไล่ทีละบรรทัด + ตาราง trace ใน `09` หัวข้อ 8)

**ลบไฟล์ (`remove`):** กฎเดียวกับตอนแนบ (`ensureCanChangeEvidence`) · ลบแถวใน DB ก่อน แล้วค่อยลบไฟล์บนดิสก์ (ถ้ากลับกันแล้ว DB พัง จะเหลือแถวที่ชี้ไปไฟล์ที่ไม่มี) · เจ้าหน้าที่/ผู้ช่วยลบไม่ได้ (route `requireRole("student")`) — ไฟล์ผิดให้ตีกลับแทน

**เปิดไฟล์ (`serveFile`):** ต้อง login + (เป็นเจ้าของใบ **หรือ** officer/reviewer) — ผู้บริหาร 403 · ส่ง `Content-Type` ตาม `file_type` (รูปเปิดเป็นรูป PDF เปิดเป็น PDF) · ชื่อไฟล์ไทยใช้ `filename*=UTF-8''…`

**อื่น ๆ:** ชื่อไฟล์ไทย multer อ่านเป็น latin1 → `Buffer.from(name,"latin1").toString("utf8")` · DB เก็บ `file_path` แบบ `/` เสมอ · รูปประกาศใช้ multer อีกตัว (`uploadImage` ≤ 5 MB jpeg/png/webp/gif)

**บั๊กที่ security review เจอและแก้แล้ว (เทส `smoke-phase27-security.mjs`):** (ก) แนบพร้อมกัน 10 คำขอเคยได้ 6 ไฟล์ → นับซ้ำหลังบันทึก (ข) ใบที่ถูกตีกลับของ **รอบเก่า** (มีรอบใหม่กว่าแล้ว) เคยเปลี่ยนหลักฐานได้ตลอดไป → ใช้ `findSubmittableRound` ตัวเดียวกับตอนส่งผล (ค) เลขใบแปลก ๆ ทำให้ไฟล์ค้างที่ดิสก์ → ตัวแปร `saved` (ง) id ใหญ่เกินคอลัมน์เคยได้ 500 → `errorHandler` แปลงเป็น 400

### 6.4 แก้ใบที่ถูกตีกลับหลังปิดรอบ — `findSubmittableRound` (`examResults.service.js`) — **ใหม่ 1 ต.ค.**
**ปัญหา:** เจ้าหน้าที่ตรวจได้หลังปิดรอบ ถ้าตีกลับตอนนั้น นักศึกษาแก้ไม่ได้ (เดิมส่งได้เฉพาะรอบเปิด) ต้องเลื่อนวันปิดทั้งรอบ ซึ่งทำไม่ได้ถ้ารอบถัดไปเปิดอยู่
**ตัดสินใจ (เจ้าของงาน):** ยอมให้เฉพาะ **ใบที่ถูกตีกลับ** แก้ส่งใหม่ได้แม้รอบปิด
```
ขั้น 1: รอบของรุ่นที่เปิดรับอยู่จริง (findActive) → ใช้รอบนั้น (fixingRejected = false)
ขั้น 2: ไม่มี → รอบล่าสุดของรุ่นที่ถึงวันเปิดแล้ว (findLatestStarted) · ไม่มี → null
ขั้น 3: ใบของคนนี้ในรอบนั้นถูกตีกลับ → ใช้รอบนั้น (fixingRejected = true) · ไม่งั้น → null
```
- ใช้ **3 ที่** ให้ตัดสินตรงกัน: ส่งผล (`create`), หน้ากรอก (`getActive` → ส่ง `can_fix_rejected`), แนบ/ลบไฟล์ (`ensureCanChangeEvidence`)
- ดูแค่ **รอบล่าสุด** ไม่ย้อนรอบเก่า (ผลที่ยกไปรอบหลังจะเพี้ยน) · ใบรอตรวจ/ไม่เคยส่ง หลังปิดรอบ ยังส่งไม่ได้
- หน้าเว็บ (`examFormReal.jsx`) เปิดฟอร์มเมื่อ `phase === 'active'` **หรือ** `can_fix_rejected === true` และเขียนเตือน "รอบนี้ปิดรับแล้ว แต่ใบที่ถูกตีกลับยังแก้ไขและส่งใหม่ได้ กรุณาส่งโดยเร็ว"
- ข้อจำกัด: ยังไม่มีเส้นตาย (แก้ได้จนกว่าจะมีรอบใหม่) · เทสคุม: `phase25` (PH25-05), `phase26` (PH26-24 ถึง 27), หน้าเว็บ WEB-13
(ตาราง trace 6 กรณีใน `09` หัวข้อ 5)

## 7. เจ้าหน้าที่ตรวจ: ยืนยัน / ตีกลับ / ถอนการยืนยัน

### 7.1 อัลกอริทึม `reviewExamResult` (ใช้ร่วมกัน approve/reject)
```
1. หาใบ (404)           2. ถ้า staff_status ≠ pending → 409 "ใบนี้ถูกตรวจไปแล้ว"
3. ตีกลับต้องมี remark (400)
4. updateMany({ where: { result_id, staff_status: "pending" }, data: {...confirmed_by: req.user.userId} })
5. ถ้า count === 0 → 409 (มีคนตัดหน้าไปก่อน)
6. สร้าง review_logs (ถ้าพลาดแค่ log error ไม่ทำให้การตรวจล้ม)
7. สร้าง notification ให้นักศึกษา — **รอให้บันทึกเสร็จก่อนตอบ (`await`) แต่ห่อ try/catch** พลาดไม่ทำให้การตรวจล้ม (ปรับ 1 ต.ค.: เดิมยิงแบบไม่รอ ทำให้นักศึกษาเปิดดูทันทีแล้วยังไม่เห็น เทส phase20 สะดุดเป็นครั้งคราว)
```
### 7.2 Optimistic guard — จุดที่กรรมการชอบถาม
**ปัญหา (race condition):** เจ้าหน้าที่ 2 คนเปิดใบเดียวกัน กด "ยืนยัน" กับ "ตีกลับ" เกือบพร้อมกัน → ถ้าเช็คสถานะแล้วค่อยเขียนแยกกัน (check-then-act) ทั้งคู่ผ่านด่าน 2 แล้วคนหลังทับคนแรก
**ทางแก้:** ย้ายเงื่อนไขไปอยู่ใน `UPDATE ... WHERE staff_status = 'pending'` — DB ทำให้เป็นอะตอมิก คนแรกได้ `count=1` คนที่สองได้ `count=0` → ตอบ 409
ด่าน 2 (เช็คก่อน) มีไว้ให้ข้อความ error ชัดเจนในกรณีทั่วไป ส่วน `updateMany` คือตัวกันจริง
ชื่อเรียก: **optimistic concurrency control** (คาดว่าไม่ชนกัน แต่ตรวจตอนเขียน)

### 7.3 ถอนการยืนยัน (`revokeApproval`) — เฉพาะ officer
ยืนยันผิดแล้วแก้ไม่ได้ (ใบที่ approved ล็อก) → officer "ถอน" ได้ **ต้องใส่เหตุผลเสมอ (≤ 500 ตัว)** ใบกลับเป็น pending + ล้าง `confirmed_by/at` + บันทึก `review_logs` (action = revoked) + แจ้งนักศึกษา. เหตุที่ reviewer ทำไม่ได้: ไม่ควรกลับคำตัดสินของคนอื่น

### 7.4 review_logs = insert-only
ไม่ UPDATE ไม่ DELETE → ตรวจย้อนหลังได้ว่าใครตัดสินอะไรเมื่อไหร่ แม้ผลในใบจะถูกทับภายหลัง

## 10. สถิติ Dashboard (`dashboard.service.js`) ★ กรรมการชอบถามตัวเลข

### 10.1 กฎเหล็กข้อเดียวที่ทำให้ตัวเลขไม่ขัดกันเอง
> ตัวเลขทุกตัวที่แปลว่า **"ผ่าน"** นับเฉพาะใบที่ **ยืนยันแล้ว (approved)**
(ผ่านครบ, ผ่านครั้งแรก, ผ่านภายในปีแรก, ผ่านรายวิชา, ตารางผ่านกี่วิชา, ยอดแยกห้อง)

**เหตุผล:** ผลที่นักศึกษากรอกเองยังไม่มีใครเทียบกับใบรายงานผลสอบจริง เชื่อยังไม่ได้. ใบรอตรวจไม่หายไปไหน — ยังนับเป็น "ส่งผลแล้ว" และจอแสดงแถบเหลืองบอกว่า "ยังมีใบรอตรวจ N ใบ ยังไม่นับ"
**ตัวหาร** ของ % คือ "นักศึกษาทั้งรุ่น" (ไม่ใช่เฉพาะคนที่ส่ง) — บอกไว้ใต้ตัวเลขทุกใบ เพราะตัวเลขสองตัวที่หารคนละฐานเทียบกันไม่ได้
**"นักศึกษาทั้งรุ่น" = คนที่กรอกโปรไฟล์แล้ว + บัญชีที่นำเข้าแล้วแต่ยังไม่เคยเข้าระบบ** (ตัดสินใจ 5 ต.ค. 2569 — คนกลุ่มหลังนับเป็น "ยังไม่กรอก" ไม่งั้นตัวหารต่ำเกินจริง % ผ่านสูงเกินจริง) โค้ด: `dashboard.repository.js → findPendingStudentIdsByYear / countStudentsByYear` (ปีของรุ่น = `import_academic_year` ถ้ามี ไม่งั้นรหัส+4) · รายชื่อ "ไม่ผ่าน" ที่ส่งออกมีคนกลุ่มนี้ (ช่องชื่อ/ห้องว่าง)

### 10.2 นิยามตัวเลขหลัก (ท่องได้)
| ตัวเลข | นิยาม | ตัวหาร |
|---|---|---|
| **ผ่านครั้งแรก** | ใบของ **รอบที่ 1** ของปีนั้น **ยืนยันแล้ว** และผ่านครบทุกวิชาของรอบ | นักศึกษาทั้งรุ่น |
| **ผ่านภายในปีแรก** | ผ่านครบทุกวิชา **โดยนับผลสะสมทุกรอบของปีนั้น** (นับรายคน คนเดียวนับครั้งเดียว) · นับเฉพาะวิชาที่ "สอบจริงแล้วผ่าน" ในใบที่ยืนยันแล้ว **ไม่นับแถวที่ยกมา** (`addConfirmedRealPasses` — แก้ B1) · วิชาที่ต้องผ่าน = วิชาของรอบ 1 | นักศึกษาทั้งรุ่น |
| **ผ่านครบ (รอบ)** | ทุกวิชาของรอบนั้นมีผลและผ่านหมด (ใบยืนยันแล้ว) | คนที่ยืนยันแล้วของรอบ |
| **อัตราผ่านรายวิชา** | ผ่าน ÷ (ผ่าน+ไม่ผ่าน) เฉพาะคน "สอบวิชานั้นจริง" | คนที่สอบจริง |
| **ตารางสภา (ผลรายวิชารอบแรก)** | ผ่าน/ไม่ผ่าน ÷ ทั้งรุ่น (ช่อง "ไม่ส่งผล" ไม่แสดง → ผ่าน%+ไม่ผ่าน% ไม่ครบ 100%) | นักศึกษาทั้งรุ่น |

ตัวอย่างจากเทสวงจรเต็ม (รุ่น 5 คน): S1 ผ่านรอบ 1, S3 ถูกตีกลับแล้วส่งใหม่ผ่านรอบ 1, S2 แก้รอบ 2, S4 สอบรอบ 3, S5 ไม่ส่ง →
**ผ่านครั้งแรก = 2/5 (S1,S3)** · **ผ่านภายในปีแรก = 4/5 (S1,S2,S3,S4)** — ตัวเลขนี้ตรงกับรายงานที่ส่งสภา

### 10.3 จุดที่ทำให้ตัวเลขผิดได้ (และระบบกันไว้ยังไง)

### 10.4 ที่มาของตัวเลขสองชั้น
`buildStats(roundId)` = ระดับ **รอบ** · `buildHistory/buildYearSummary` = ระดับ **ปี** (รวมหลายรอบ นับรายคน). ตัวเลขในไฟล์ส่งออก "ผ่าน/ไม่ผ่านครั้งแรก" ใช้กฎเดียวกับตัวเลขบนการ์ดเป๊ะ (`buildFirstAttemptList`) และ **ผ่าน + ไม่ผ่าน = ทั้งรุ่นเสมอ** (เทส `phase22` เทียบกับ `/history` ตรง ๆ)
**ใหม่ 1 ต.ค.:** ไฟล์ "ผ่าน/ไม่ผ่าน **ภายในปีแรก**" (`buildFirstYearList`, `GET /api/dashboard/export-first-year`) เรียก helper ชุดเดียวกับการ์ด (`addConfirmedRealPasses`, `getRequiredSubjectIds`, `hasPassedAll`) — แก้กฎที่เดียว การ์ดกับไฟล์เปลี่ยนพร้อมกัน · ไฟล์ทั้ง 2 แบบมีชื่อ-นามสกุลไทย/อังกฤษ ห้อง เบอร์ อีเมล (`studentContactColumns`) ไม่มีเลขบัตร (เทส PH25-07, PH26-39 ถึง 42)

## 11. การนำเข้านักศึกษา (`student.controller.js → bulkImport`)
**ปัญหา:** เจ้าหน้าที่ได้ไฟล์ Excel/CSV จากหลายแหล่ง หัวคอลัมน์ไม่เหมือนกัน เลขบัตรมีเลขไทย/ขีด/จุดทศนิยม Excel ตัดเลข 0 หรือแปลงเป็น E+

**ขั้นตอน:**
1. รับไฟล์ที่ memory (multer `memoryStorage`) — เช็คว่าเป็น xlsx จาก **เนื้อไฟล์** (ขึ้นต้น `PK` = zip) ไม่เชื่อนามสกุล
2. CSV ภาษาไทย: ลอง decode เป็น UTF-8 แบบเข้มงวด (`fatal: true`) ถ้าไม่ได้ถือว่าเป็น Windows-874
3. **เดาคอลัมน์ (`guessColumns`):** เทียบชื่อหัวที่ normalize แล้วกับ keyword (เช่น "รหัสนักศึกษา", "เลขบัตร") — ตรง 1 คอลัมน์ = ใช้; **กำกวม (ตรงหลายอัน) = ไม่เดา ให้เจ้าหน้าที่เลือกเอง** (ดีกว่าเดาผิดเงียบ ๆ) ตอบ `code: "missing_columns"` พร้อมรายชื่อคอลัมน์ให้หน้าจอทำ dropdown
4. **ล้างข้อมูล (`cleanIdText`):** เลขไทย→อารบิก, เลขเต็มความกว้าง, ตัด `-`/ช่องว่าง/`'`, `1929….0`→ตัด `.0`; ถ้าเป็น `1.23E+12` (Excel ทำเลขหาย) **ไม่เดา** แจ้งสาเหตุ; ตัวอักษรไม่ตัดทิ้ง ให้ด่าน regex `^\d{13}$` ปฏิเสธ
5. ตรวจรายแถว: รหัส `^\d{2,}$`, เลขบัตร 13 หลัก, ปีจบ (ถ้ามี) ผ่าน `validateGraduationYear`, รหัสซ้ำในไฟล์/ซ้ำกับในระบบ → **ข้ามแถวนั้น** ไม่ล้มทั้งไฟล์
6. **`?dry_run=true`:** ตรวจอย่างเดียวไม่บันทึก → หน้าจอโชว์สรุป "นำเข้า N / ข้าม M / ปีจบไม่ตรงรหัส K" ให้กดยืนยันก่อน
7. บันทึก: hash เลขบัตรด้วย bcrypt แล้วสร้าง `users` (role student) — **ยังไม่สร้างแถว `students`** จนกว่านักศึกษาจะ login แล้วกรอกโปรไฟล์ (`complete-profile` สร้างแถว students + คำนวณปีจบจาก `import_academic_year ?? calcGraduationYear`)

## 13. จัดการผู้ใช้ (`modules/users/`)
- สร้างบัญชีได้ role officer/executive/reviewer (ไม่มีสมัครเอง กันปลอมตัว) · ผู้บริหารไม่ต้องกรอกอีเมล/เบอร์ · บทบาท `reviewer` แสดงบนจอว่า **"ผู้ช่วยตรวจสอบ"** (`i18n.js → role.reviewer`, seed ใช้คำนี้ด้วย) เมนูชื่อ "จัดการผู้ใช้งาน" และฟอร์มเพิ่มผู้ใช้มีคำอธิบายสิทธิ์ของแต่ละบทบาท (`usersMgmt.roleHint.*`)
- กันตัวเอง: ห้ามลบ/ถอนสิทธิ์/เปลี่ยน role ของตัวเอง (กันล็อกตัวเองออก)
- **ลบบัญชี:** ทุก FK ไปยัง users เป็น `ON DELETE RESTRICT` (ยกเว้น `exam_results.confirmed_by` = SET NULL) → บัญชีที่เคยสร้างรอบ/โพสต์ข่าว/ตรวจผล **ลบไม่ได้** ตอบ 409 ให้ใช้ "ถอนสิทธิ์" แทน
  - ต้องเช็คเองก่อน (`countLinkedHistory`) ห้ามพึ่ง catch error: Postgres ตอบ SQLSTATE `23001` (restrict_violation) ซึ่ง Prisma **ไม่แปลงเป็น P2003** → เคยหลุดเป็น 500 พร้อม raw SQL error (แก้แล้ว มีเทส `phase23`)
  - ถอนสิทธิ์ = ล้าง `password_hash` (login ไม่ได้ ประวัติอยู่ครบ)
- รีเซ็ตรหัส = ตั้งรหัสชั่วคราวใหม่ให้ทันที + บังคับเปลี่ยนตอน login ครั้งต่อไป (เจ้าหน้าที่ไม่เคยเห็นรหัสผ่านจริงของใคร)

### 14.2 `npm run test:clean` (ท่าที่ถูก)
สร้าง PostgreSQL schema ชั่วคราว `verify_tmp` → migrate → seed → เปิด server พอร์ต 3100 → รันทีละไฟล์ (เปิด server ใหม่ทุกไฟล์ เพราะ rate limiter นับใน memory) → ลบ schema ทิ้ง ไม่แตะข้อมูลจริง
- **ทำไมไม่รัน `npm test` ใส่ DB จริง:** DB จริงมีนักศึกษา 928 คน เทสหลายตัวคาดว่า "ต้องมีนักศึกษา 1 คน" จึง fail ทั้งที่โค้ดไม่พัง แยกบั๊กจริงออกไม่ได้
- รันไฟล์เดียว: `ONLY=phase24 npm run test:clean`
- ปีที่เทสสร้างใช้ ≥ 2590 แล้วล้างด้วย `cleanupYears` (ห้ามส่งปีจริง — โค้ดปฏิเสธ)

### 14.3 บั๊กจริงที่เจอจากการทดสอบ (เล่าได้ว่า "เราเจอและแก้แล้ว")
- ลบบัญชีที่มีประวัติ → 500 พร้อม SQL ดิบ (แก้เป็น 409)
- รอบที่ปิดแล้วแต่หน้าจอยังเขียน "เปิดรับ" (phase ไม่ตรงกับ `findActive`)
- ตัวเลขสถิติขัดกันในหน้าเดียว (ผ่านรายวิชา 40 แต่ผ่านครบ 45) → รวมกฎ "นับเฉพาะยืนยันแล้ว"
- นับสอบซ้ำหลายรอบเกินจำนวนคน → นับรายคน
- PDF ตัวอักษรทับ/แถวหาย (letter-spacing และแอนิเมชันระหว่างถ่ายภาพ)
- **B1 (1 ต.ค.)** "ผ่านภายในปีแรก" นับวิชาที่ยกมาจากใบที่ถูกตีกลับภายหลัง → ไม่นับแถว `carried_forward` (พบจากการไล่ flow จริงใน `docs/test-plan.md` ก่อนเขียนเทส)
- **ใบรอตรวจเพิ่มไฟล์ได้หลังปิดรอบ** → แนบ/ลบได้เฉพาะรอบ active หรือใบถูกตีกลับ

## 15. สรุปกฎธุรกิจทั้งหมดในหน้าเดียว (ไว้ทบทวนก่อนสอบ)
1. role มาจาก DB ผ่าน JWT เท่านั้น ห้ามเชื่อ client · `authenticate` ก่อน `requireRole` เสมอ
2. รหัสผ่านเก็บ bcrypt hash · token อยู่ใน httpOnly cookie อายุ 1 วัน
3. นักศึกษากรอกได้เมื่อ: เปิดสิทธิ์ + (มีรอบ active ของรุ่นตัวเอง **หรือ** ใบของรอบล่าสุดถูกตีกลับ) + ใบยังไม่ยืนยัน — `findSubmittableRound` ตัวเดียวใช้ทั้งส่งผล หน้ากรอก และแนบไฟล์
4. วิชาที่ผ่าน **จริง** แล้ว (ใบไม่ถูกตีกลับ, ไม่ใช่แถวที่ยกมา) ล็อกเป็นผ่าน ติดธง carried_forward
4ข. หลักฐาน PDF/JPG/PNG ≤ 5 ไฟล์ ≤ 10 MB ตรวจชนิดจากไบต์ต้นไฟล์ · แนบ/ลบได้เฉพาะเจ้าของ + ใบยังไม่ยืนยัน + ใบอยู่ในรอบที่ส่งได้
5. ตรวจใบได้เฉพาะ pending (กันทับด้วย UPDATE … WHERE) · ตีกลับต้องมี remark · ถอนการยืนยันเฉพาะ officer ต้องมีเหตุผล
6. เปิดรอบได้ทีละรอบ · ปี+ครั้งที่ไม่ซ้ำ · เปิดแล้วห้ามแก้วิชา · ลบรอบได้เมื่อไม่มีผลสอบ/ประกาศ
7. สถิติ "ผ่าน" ทุกตัวนับเฉพาะใบยืนยันแล้ว · ตัวหารคือทั้งรุ่น · ไม่นับวิชา carried เป็นคนสอบ และไม่นับเป็น "ผ่านจริง" (B1) · ไฟล์ส่งออกใช้ฟังก์ชันเดียวกับการ์ด
8. ผู้บริหารอ่านภาพรวมอย่างเดียว · ไม่เห็นรายบุคคล/ไฟล์หลักฐาน
9. ไฟล์เก็บบนดิสก์ DB เก็บ path · ไม่มีเลขบัตรในไฟล์ส่งออก
10. ลบบัญชีที่มีประวัติไม่ได้ (RESTRICT) ใช้ถอนสิทธิ์
