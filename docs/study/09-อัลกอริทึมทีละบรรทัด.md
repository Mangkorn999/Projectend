# 09 — อัลกอริทึมหลักของระบบ อธิบายทีละบรรทัด

ไฟล์นี้ตอบหัวข้อ 25 คะแนน **"อธิบายหลักการ เทคนิค อัลกอริทึม … ได้อย่างลึกซึ้ง"**
อัลกอริทึม (algorithm) = **ขั้นตอนแก้ปัญหาที่เขียนเป็นลำดับชัดเจน** — ไม่จำเป็นต้องซับซ้อน แค่ต้องบอกได้ว่า "ทำไมทำขั้นนี้ และถ้าไม่ทำจะเกิดอะไร"

ทุกหัวข้อมี 7 ส่วนเหมือนกัน:
**ก.** ปัญหา → **ข.** วิธีคิด (pseudocode ภาษาไทย ใช้แค่ ถ้า/ไม่งั้น/วนซ้ำ) → **ค.** โค้ดจริง (คัดจากโปรเจกต์ + คำอธิบาย) → **ง.** ตารางไล่โค้ด (trace) → **จ.** กรณีขอบ → **ฉ.** ถ้าเปลี่ยนบรรทัดนี้ → **ช.** คำถามกรรมการ 3 ข้อ + แนวตอบ

> **ตารางไล่โค้ด (trace table) คืออะไร:** สมมติข้อมูลจริงหนึ่งชุด แล้วเดินโค้ดทีละบรรทัด จดค่าของตัวแปรทุกครั้งที่เปลี่ยน
> เป็นวิธีที่โปรแกรมเมอร์ใช้ "พิสูจน์ด้วยมือ" ว่าโค้ดทำงานถูก — ตอนสอบถ้ากรรมการถาม "ถ้าข้อมูลเป็นแบบนี้ได้ผลอะไร" ให้วาดตารางแบบนี้บนกระดาน
> คำอธิบายในโค้ดใช้เลขวงกลม ① ② ③ ชี้ไปที่คำอธิบายใต้โค้ด (โค้ดจริงไม่มีเลขพวกนี้)

## สารบัญ
1. เส้นทางของ request + สายพาน middleware
2. เข้าสู่ระบบ: bcrypt → JWT → cookie และด่านของ `authenticate`
3. จำกัดจำนวนครั้ง (rate limit) ด้วย Map
4. สถานะจริงของรอบ (phase)
5. หารอบที่ส่งผลได้ `findSubmittableRound`
6. ตรวจผลสอบที่ส่งมา + ยกผลรอบก่อน (carry-forward) + เรื่องบั๊ก B1
7. กันสองคนตรวจใบเดียวกันพร้อมกัน (optimistic guard)
8. ตรวจชนิดไฟล์จากไบต์ต้นไฟล์ (magic bytes) + จำกัดจำนวนไฟล์
9. "ผ่านครั้งแรก" กับ "ผ่านภายในปีแรก"
10. นำเข้าไฟล์: เดาคอลัมน์ + ล้างเลขบัตร
11. แบ่งหน้า + "แสดง N จาก M"
12. รวมแจ้งเตือนหลายแหล่ง + กุญแจ (key) ของแจ้งเตือน

# 1. เส้นทางของ request + สายพาน middleware

### ก. ปัญหา
ทุก request ต้องผ่านการตรวจหลายอย่างก่อนถึงตัวทำงานจริง (อ่าน JSON, อ่าน cookie, ตรวจตัวตน, ตรวจสิทธิ์) ถ้าเขียนการตรวจซ้ำในทุก controller จะยาวและลืมง่าย

### ข. วิธีคิด
```
รับ request
วนผ่านฟังก์ชันตรวจทีละตัวตามลำดับที่ลงทะเบียนไว้:
    ถ้าตัวนี้ตอบกลับเอง (เช่น 401) → จบ ไม่ไปตัวถัดไป
    ไม่งั้น เรียก next() → ไปตัวถัดไป
ถึง controller → ทำงาน → ตอบ { success: true, data }
ถ้าระหว่างทางมี error → โยนไปให้ errorHandler ตัวสุดท้ายตอบ { success: false, message }
```

### ค. โค้ดจริง — `backend/src/app.js` (ย่อ)
```js
app.use(helmet({ contentSecurityPolicy: false, crossOriginResourcePolicy: { policy: "cross-origin" } })); // ①
app.use(cors({ origin: allowedOrigins, credentials: true }));   // ②
app.use(express.json());                                         // ③
app.use(cookieParser());                                         // ④
app.use("/api/exam-results", examResultsRouter);                 // ⑤ (และ router อื่น ๆ)
app.use((req, res) => {                                          // ⑥
  res.status(404).json({ success: false, message: `ไม่พบ endpoint: ${req.method} ${req.originalUrl}` });
});
app.use(errorHandler);                                           // ⑦
```
และใน `backend/src/modules/examResults/examResults.routes.js`
```js
router.patch("/:id/approve", authenticate, requireRole("officer", "reviewer"), approve); // ⑧
```
① **helmet** ใส่ header ความปลอดภัยมาตรฐานให้ทุกคำตอบ (เช่น ห้ามเบราว์เซอร์เดาชนิดไฟล์เอง) — อยู่บนสุดเพื่อครอบทุกคำตอบ
② **cors** อนุญาตเฉพาะ origin ที่ระบุใน `.env` (`CORS_ORIGIN`) และอนุญาตให้ส่ง cookie (`credentials: true`)
③ แปลง body ที่เป็นข้อความ JSON → object ให้อยู่ใน `req.body`
④ อ่าน cookie → `req.cookies` (ถ้าไม่มีบรรทัดนี้ `authenticate` หา token ไม่เจอ → 401 ทุก request)
⑤ จับคู่คำนำหน้า URL กับ router ของแต่ละเรื่อง
⑥ ไม่ตรงอะไรเลย → 404 เป็น JSON (ไม่ปล่อยให้ Express ตอบเป็นหน้า HTML ซึ่งหน้าเว็บอ่านไม่ได้)
⑦ ตัวจัดการ error — Express รู้ว่าเป็นตัวจัดการ error เพราะรับ 4 ตัว `(err, req, res, next)` ต้องอยู่ท้ายสุด
⑧ สายพานของ endpoint เดียว: ใครน่ะ (`authenticate`) → มีสิทธิ์ไหม (`requireRole`) → ทำงาน (`approve`)

`errorHandler` (`middlewares/errorHandler.js`) เลือก status code ตามลำดับ: มี `err.statusCode` ใช้ค่านั้น → `MulterError` = 400 → Prisma `P2002` (ซ้ำ) = 409 → `P2025` (ไม่พบ) = 404 → `P2003` (อ้างอิงผิด) = 409 → ข้อมูลผิดชนิด = 400 → นอกนั้น 500 (และซ่อนข้อความดิบ)

### ง. ตารางไล่โค้ด — เจ้าหน้าที่กด "ยืนยัน" ใบที่ 12
| ลำดับ | ด่าน | สิ่งที่เช็ค | ผล |
|---|---|---|---|
| 1 | helmet | — | ใส่ header แล้ว `next()` |
| 2 | cors | origin = `http://localhost:5174` อยู่ใน `allowedOrigins`? | ใช่ → `next()` |
| 3 | express.json | body ว่าง | `req.body = {}` |
| 4 | cookieParser | มี cookie `token=eyJ...` | `req.cookies.token = "eyJ..."` |
| 5 | router `/api/exam-results` | path ที่เหลือ = `/12/approve` ตรงกับ `/:id/approve` | `req.params.id = "12"` |
| 6 | authenticate | token ถูก + ผู้ใช้ยังอยู่ | `req.user = { userId: 2, role: "officer", ... }` |
| 7 | requireRole("officer","reviewer") | `"officer"` อยู่ในรายการ? | ใช่ → `next()` |
| 8 | approve → reviewExamResult | ดูหัวข้อ 7 | ตอบ 200 `{ success: true, data }` |

ถ้าเป็นผู้บริหารกด: ลำดับ 7 → `"executive"` ไม่อยู่ในรายการ → **403** จบตรงนั้น ไม่ถึง controller เลย

### จ. กรณีขอบ
- `cookieParser` อยู่หลัง router → ทุก request 401 (ไม่ error แต่ใช้งานไม่ได้เลย)
- ลืม `errorHandler` → error ที่ `next(err)` จะได้หน้า HTML error ของ Express
- ลำดับ `requireRole` ก่อน `authenticate` → `req.user` ยังไม่มี → `requireRole` ตอบ 401 ทุกครั้ง (โค้ดเช็ค `if (!req.user)` ไว้)

### ฉ. ถ้าเปลี่ยนบรรทัดนี้
| เปลี่ยน | ผล |
|---|---|
| `cors({ origin: "*" , credentials: true })` | เบราว์เซอร์ปฏิเสธ — ใช้ `*` คู่กับ cookie ไม่ได้ ต้องระบุ origin จริง |
| ลบ `requireRole(...)` ออกจาก route approve | นักศึกษาก็ยืนยันใบตัวเองได้ = ช่องโหว่ร้ายแรง |
| ย้ายบรรทัด 404 ไปไว้ก่อน router | ทุก request ได้ 404 เพราะตัวนี้ไม่เรียก `next()` |

### ช. คำถามกรรมการ
1. **middleware คืออะไร ต่างจาก controller ยังไง?** — *middleware คือฟังก์ชันที่ทำงานก่อน controller เลือกได้ว่าจะปล่อยผ่าน (`next()`) หรือตอบกลับเลย ใช้กับงานที่ทุก route ต้องทำเหมือนกัน เช่น ตรวจตัวตน ส่วน controller คือเนื้องานของ endpoint นั้น*
2. **ทำไม error ทุกตัวไปรวมที่เดียว?** — *รูปแบบคำตอบ error เหมือนกันทั้งระบบ (`{success:false, message}`) และจุดเดียวที่แปลง error ของ Prisma/multer เป็นข้อความไทย + ซ่อนข้อความดิบของ 500 ไม่ให้เผยโครงสร้างตาราง*
3. **ถ้าลืมใส่ `authenticate` ที่ route หนึ่ง จะเกิดอะไร?** — *ถ้ามี `requireRole` ตามหลัง จะได้ 401 เสมอเพราะไม่มี `req.user` (ปลอดภัยแต่ใช้งานไม่ได้) · ถ้าไม่มีทั้งคู่ route นั้นเป็นสาธารณะ — จึงตั้งกติกาว่า endpoint ที่ไม่ public ต้องมีทั้งสองเสมอ*

# 2. เข้าสู่ระบบ: bcrypt → JWT → cookie และด่านของ `authenticate`

### ก. ปัญหา
(1) เก็บรหัสผ่านยังไงให้ฐานข้อมูลรั่วแล้วรหัสไม่หลุด (2) login ครั้งเดียวแล้ว request ถัดไปรู้ได้ยังไงว่าเป็นใคร (3) ถ้าบัญชีถูกถอนสิทธิ์ระหว่างใช้งาน ต้องตัดได้ทันที

### ข. วิธีคิด
```
login:
  ถ้า รหัสผู้ใช้หรือรหัสผ่านไม่ใช่ข้อความ → 400
  หาผู้ใช้จากรหัสผู้ใช้
  ถ้า ไม่พบ → 401 "รหัสผู้ใช้หรือรหัสผ่านไม่ถูกต้อง"
  ถ้า ยังไม่มีรหัสผ่าน (ถูกถอนสิทธิ์) → 403
  ถ้า bcrypt เทียบรหัสแล้วไม่ตรง → 401 ข้อความเดิม
  สร้าง token ที่มี userId, role, ... แล้วลงลายเซ็นด้วยกุญแจลับ อายุ 1 วัน
  ใส่ token ใน cookie แบบ httpOnly → ตอบข้อมูลผู้ใช้ (ไม่ส่ง token ใน JSON)

ทุก request หลังจากนั้น (authenticate):
  ถ้า ไม่มี cookie token → 401 (code auth_required)
  ถ้า ลายเซ็นผิด/หมดอายุ → 401 (code auth_required)
  หาผู้ใช้ใน DB จาก userId ใน token
  ถ้า ไม่พบ หรือ ไม่มีรหัสผ่านแล้ว → 401 (code auth_required)
  สร้าง req.user จากข้อมูลใน DB (ไม่ใช่จาก token)
  ถ้า ต้องเปลี่ยนรหัส และ ไม่ได้เรียก /me หรือ /password → 403
  ถ้า เป็นนักศึกษา ยังไม่มีโปรไฟล์ และ ไม่ได้เรียกหน้าตั้งโปรไฟล์/รายชื่อห้อง → 403
  ไม่งั้น next()
```

### ค. โค้ดจริง
`backend/src/controllers/authController.js` → `login` (ย่อ)
```js
const user = await prisma.user.findUnique({ where: { psu_passport_id }, include: { role: true, student: true } });
const invalid = () => res.status(401).json({ success: false, message: "รหัสผู้ใช้หรือรหัสผ่านไม่ถูกต้อง" }); // ①
if (!user) return invalid();
if (!user.password_hash) { return res.status(403).json({ ... "บัญชียังไม่ได้ตั้งรหัสผ่าน กรุณาติดต่อเจ้าหน้าที่คณะ" }); } // ②
const ok = await bcrypt.compare(password, user.password_hash);   // ③
if (!ok) return invalid();
const token = jwt.sign(
  { userId: user.user_id, role: user.role.role_name, studentId: user.student?.student_id ?? null,
    mustChangePassword: user.must_change_password },
  process.env.JWT_SECRET,                                         // ④
  { expiresIn: "1d" },
);
res.cookie("token", token, TOKEN_COOKIE_OPTIONS);                 // ⑤
```
① ฟังก์ชันตอบ 401 ข้อความเดียว ใช้ทั้ง "ไม่พบบัญชี" และ "รหัสผิด" → คนนอกเดาไม่ได้ว่ารหัสผู้ใช้ไหนมีอยู่จริง (กัน user enumeration)
② `password_hash` เป็น `null` = ถูกถอนสิทธิ์ (`users.repository.js → revokeAccess` ล้างเป็น null)
③ `bcrypt.compare` เอารหัสที่พิมพ์มา hash ด้วย salt ที่ฝังอยู่ใน hash เดิม แล้วเทียบ — ไม่มีการถอด hash กลับ (ทำไม่ได้)
④ ลายเซ็นสร้างจาก `JWT_SECRET` ใน `.env` — ใครไม่รู้ secret ปลอม token ไม่ได้
⑤ `TOKEN_COOKIE_OPTIONS` = `httpOnly: true` (JavaScript อ่านไม่ได้) · `sameSite: "lax"` (เว็บอื่นยิงข้ามมา ไม่แนบ cookie) · `secure` จาก `COOKIE_SECURE` · `maxAge` 1 วัน

`backend/src/middlewares/auth.js` → `authenticate` (ย่อ)
```js
let token = null;
if (req.cookies) { token = req.cookies.token; }
if (!token) { return res.status(401).json({ success: false, code: "auth_required", message: "กรุณาเข้าสู่ระบบก่อน" }); } // ด่าน 1
let decoded;
try { decoded = jwt.verify(token, process.env.JWT_SECRET); }                                   // ด่าน 2
catch (err) { return res.status(401).json({ ..., code: "auth_required", message: "การเข้าสู่ระบบหมดอายุแล้ว ..." }); }
const user = await prisma.user.findUnique({ where: { user_id: decoded.userId }, select: { ... } });  // ด่าน 3
if (!user || !user.password_hash) { return res.status(401).json({ ..., code: "auth_required", ... }); }
req.user = { userId: user.user_id, username: user.psu_passport_id, role: user.role.role_name,     // ⑥
             studentId: user.student?.student_id ?? null, mustChangePassword: user.must_change_password };
if (req.user.mustChangePassword && !PASSWORD_SETUP_PATHS.includes(req.path)) { return res.status(403)... } // ด่าน 4ก
if (req.user.role === "student" && !req.user.studentId
    && !PROFILE_SETUP_PATHS.includes(req.path) && !PROFILE_SETUP_ROUTERS.includes(req.baseUrl)) { return res.status(403)... } // ด่าน 4ข
next();
```
⑥ **หัวใจของไฟล์:** `req.user` สร้างจากแถวใน DB ไม่ใช่จากค่าใน token → เปลี่ยน role/ถอนสิทธิ์แล้วมีผลทันที

> **หมายเหตุความแม่นยำ:** เอกสารเดิม (`03`) เรียกว่า "3 ด่าน" (ลายเซ็น · ตรวจกับ DB · บังคับเปลี่ยนรหัส) — โค้ดจริงมีด่าน "ไม่มี cookie" แยกไว้ก่อน และมีด่าน "นักศึกษายังไม่กรอกโปรไฟล์" ต่อท้าย ตอบกรรมการแบบไหนก็ได้ แต่ต้องรู้ว่ามีครบ

`frontend/src/design/api.js` → `apiFetch` ฝั่งหน้าเว็บ: `credentials: 'include'` สั่งให้แนบ cookie · ถ้าได้ 401 **และ** `code === 'auth_required'` → `forceLogout()` (ล้าง localStorage + โหลดหน้าใหม่ → กลับหน้า login) · 401 ที่ไม่มี code (เช่น login รหัสผิด) ไม่เด้งออก

### ง. ตารางไล่โค้ด — 4 สถานการณ์
| สถานการณ์ | ด่าน 1 | ด่าน 2 | ด่าน 3 | ด่าน 4 | ผล |
|---|---|---|---|---|---|
| เจ้าหน้าที่ปกติ เรียก `/api/rounds` | มี token | ลายเซ็นถูก ยังไม่หมดอายุ | พบ มีรหัสผ่าน | ไม่ต้องเปลี่ยนรหัส | `next()` |
| ผู้ใช้ถูกถอนสิทธิ์เมื่อ 5 นาทีก่อน (token ยังไม่หมดอายุ) | มี | ถูก | พบ แต่ `password_hash = null` | — | **401** auth_required → หน้าเว็บเด้งออก |
| ผู้ช่วยตรวจสอบบัญชีใหม่ เรียก `/api/exam-results` | มี | ถูก | พบ | `mustChangePassword = true`, path ไม่ใช่ `/me` หรือ `/password` | **403** "กรุณาตั้งรหัสผ่านใหม่ก่อนใช้งานระบบ" |
| นักศึกษาเพิ่งนำเข้า เรียก `/api/rooms` | มี | ถูก | พบ | ยังไม่มี studentId แต่ `req.baseUrl = "/api/rooms"` อยู่ในรายการยกเว้น | `next()` (หน้าตั้งโปรไฟล์ต้องใช้รายชื่อห้อง) |

### จ. กรณีขอบ
- ส่ง `psu_passport_id` เป็น object → ด่านแรกของ `login` ตอบ 400 (เดิมทำ Prisma พังเป็น 500)
- logout แล้วมีคนก๊อป token ไว้ → token ยังใช้ได้จนหมดอายุ **ถ้าบัญชียังปกติ** (JWT ไม่มีสถานะที่ server) — ด่าน 3 ตัดได้เฉพาะบัญชีที่ถูกลบ/ถอนสิทธิ์
- `changePassword` สำเร็จ → token เดิมยังมี `mustChangePassword: true` ฝังอยู่ แต่ด่าน 3 อ่านค่าจาก DB ใหม่ → จริง ๆ ใช้ต่อได้ หน้าเว็บเลือกให้ login ใหม่ (`handlePasswordChanged` ใน `app.jsx`)

### ฉ. ถ้าเปลี่ยนบรรทัดนี้
| เปลี่ยน | ผล |
|---|---|
| `req.user.role = decoded.role` (อ่านจาก token) | เปลี่ยน role ให้ใครต้องรอ token เก่าหมดอายุ 1 วัน · คนถูกลดสิทธิ์ยังทำงานด้วยสิทธิ์เดิมได้ทั้งวัน |
| ลบ `httpOnly: true` | สคริปต์อันตรายในหน้าเว็บ (XSS) อ่าน `document.cookie` ขโมย token ได้ |
| ข้อความ 401 แยก "ไม่พบบัญชี" กับ "รหัสผิด" | คนนอกไล่เช็คได้ว่ารหัสนักศึกษาไหนมีในระบบ |
| `SALT_ROUNDS = 4` | hash เร็วขึ้นมาก ถ้าฐานข้อมูลรั่ว ไล่เดารหัสได้เร็วขึ้นหลายสิบเท่า |

### ช. คำถามกรรมการ
1. **JWT กับ session ต่างกันยังไง ทำไมเลือก JWT?** — *session เก็บสถานะที่ server ต้องมีตารางหรือหน่วยความจำ · JWT เก็บข้อมูลในตัว token ที่ลงลายเซ็น server แค่ตรวจลายเซ็น — แต่ระบบเรา "ตรวจ DB ทุก request" เพิ่ม เพื่อให้ถอนสิทธิ์ได้ทันที จึงได้ข้อดีทั้งสองแบบ แลกกับ query เพิ่ม 1 ครั้งต่อ request*
2. **bcrypt ต่างจาก hash ธรรมดาอย่าง SHA-256 ยังไง?** — *bcrypt มี salt สุ่มต่อรหัส (รหัสเดียวกันได้ hash ไม่เหมือนกัน กันตารางสำเร็จรูป) และช้าโดยตั้งใจตามจำนวนรอบ (`SALT_ROUNDS = 10`) ทำให้เดารหัสจำนวนมากช้ามาก*
3. **ทำไมหน้าเว็บเก็บข้อมูลผู้ใช้ใน localStorage ด้วย ทั้งที่มี cookie แล้ว?** — *cookie เป็น httpOnly JavaScript อ่านไม่ได้ หน้าเว็บจึงไม่รู้ว่าใคร login อยู่ตอนรีเฟรช — localStorage เก็บแค่ `{id, name, role, ...}` ไว้วาดหน้าจอ (ไม่ใช่ความลับ) แล้วยิง `/auth/me` ยืนยันกับ backend อีกที (`app.jsx` → `verifyCookie`)*

# 3. จำกัดจำนวนครั้ง (rate limit) ด้วย Map

### ก. ปัญหา
endpoint `login` ใครก็ยิงได้โดยไม่ต้องมี token → ยิงเดารหัสรัว ๆ ได้ไม่จำกัด

### ข. วิธีคิด
```
มีสมุดจด (Map) : กุญแจ = "path:ตัวตน" → { จำนวนครั้ง, เวลาที่จะล้าง }
เมื่อ request มา:
    ตัวตน = ค่าใน body ตาม keyField ถ้ามี ไม่งั้น = IP
    ถ้า ยังไม่เคยจด หรือ เลยเวลาล้างแล้ว → จดใหม่ จำนวน = 1, เวลาล้าง = ตอนนี้ + ช่วงเวลา → ผ่าน
    ถ้า จำนวน >= สูงสุด → ตอบ 429 พร้อมบอกว่ารออีกกี่วินาที
    ไม่งั้น จำนวน + 1 → ผ่าน
ทุก 10 นาที วนลบรายการที่หมดเวลาแล้ว (กันหน่วยความจำโตเรื่อย ๆ)
```

### ค. โค้ดจริง — `backend/src/middlewares/rateLimit.js`
```js
const buckets = new Map();                                        // ①
export const rateLimit = ({ windowMs, max, keyField }) => {       // ②
  return (req, res, next) => {
    const identity = keyField ? req.body?.[keyField] : req.ip;    // ③
    const key = `${req.path}:${identity || req.ip}`;              // ④
    const now = Date.now();
    const bucket = buckets.get(key);
    if (!bucket || now > bucket.resetAt) {                        // ⑤
      buckets.set(key, { count: 1, resetAt: now + windowMs });
      return next();
    }
    if (bucket.count >= max) {                                    // ⑥
      const retryAfterSec = Math.ceil((bucket.resetAt - now) / 1000);
      return res.status(429).json({ success: false, message: `ลองมากเกินไป กรุณาลองใหม่ใน ${retryAfterSec} วินาที` });
    }
    bucket.count += 1;                                            // ⑦
    next();
  };
};
```
และ `backend/src/modules/auth/auth.routes.js`
```js
router.post("/login",
  rateLimit({ windowMs: 15 * 60 * 1000, max: 60 }),                               // ⑧ ชั้น IP
  rateLimit({ windowMs: 15 * 60 * 1000, max: 10, keyField: "psu_passport_id" }), // ⑨ ชั้นรหัสผู้ใช้
  login);
```
① `Map` = สมุดจด กุญแจ → ค่า (ดู `10`) อยู่ในหน่วยความจำของโปรแกรม ปิดโปรแกรมแล้วหาย
② ฟังก์ชันที่ **คืนฟังก์ชัน** — เพราะ Express ต้องการ middleware หน้าตา `(req, res, next)` แต่เราอยากตั้งค่า (`max`, `windowMs`) ได้ต่างกันในแต่ละที่
③ มี `keyField` → นับตามรหัสผู้ใช้ที่พิมพ์มา · ไม่มี → นับตาม IP
④ ใส่ `req.path` ในกุญแจ กันกรณีใช้ตัวนับเดียวกันหลาย endpoint
⑤ ยังไม่เคยมี หรือหมดรอบแล้ว → เริ่มนับรอบใหม่ (ครั้งที่ 1)
⑥ ครบโควตา → 429 · `Math.ceil` ปัดวินาทีขึ้น (เหลือ 0.2 วินาทีบอก "1 วินาที" ไม่ใช่ "0")
⑦ ยังไม่ครบ → +1 แล้วผ่าน — **นับทุกครั้งที่เรียก ไม่ว่า login สำเร็จหรือไม่**
⑧⑨ 2 ชั้นเรียงกัน: ชั้น IP กันคนหมุนเปลี่ยนรหัสผู้ใช้ไปเรื่อย ๆ · ชั้นรหัสผู้ใช้กันการเดารหัสของบัญชีเดียว โดยไม่บล็อกเพื่อนในห้อง lab ที่ใช้ IP เดียวกัน

### ง. ตารางไล่โค้ด — ชั้นรหัสผู้ใช้ (`max: 10`) เดารหัสบัญชี 6610210001, เริ่ม 10:00:00
| ครั้งที่ | เวลา | bucket ก่อน | เข้าเงื่อนไขไหน | bucket หลัง | ผล |
|---|---|---|---|---|---|
| 1 | 10:00:00 | ไม่มี | ⑤ | count 1, resetAt 10:15:00 | ผ่าน → login ตอบ 401 |
| 2 | 10:00:05 | count 1 | ⑦ | count 2 | ผ่าน → 401 |
| … | … | … | ⑦ | … | … |
| 10 | 10:01:00 | count 9 | ⑦ | count 10 | ผ่าน → 401 |
| 11 | 10:01:10 | count 10 | ⑥ (10 >= 10) | ไม่เปลี่ยน | **429** "ลองใหม่ใน 830 วินาที" |
| 12 | 10:15:01 | count 10, resetAt ผ่านไปแล้ว | ⑤ | count 1, resetAt 10:30:01 | ผ่าน |

สรุป: ช่วง 15 นาทีเดียวกัน เรียกได้ **10 ครั้ง** ครั้งที่ 11 ถูกปฏิเสธ

### จ. กรณีขอบ
- รีสตาร์ท backend → Map ว่าง ตัวนับเริ่มใหม่ (เหตุผลที่สคริปต์เทสเปิด server ใหม่ทุกไฟล์ และเป็น "แผนสำรอง" ตอนเดโมโดน 429)
- รันหลายเครื่องหลังตัวกระจายโหลด → แต่ละเครื่องนับแยก โควตาจริงคูณจำนวนเครื่อง → ต้องย้ายตัวนับไปที่เก็บกลาง เช่น Redis
- body ไม่มี `psu_passport_id` → `identity` เป็น `undefined` → กุญแจใช้ IP แทน (`identity || req.ip`)

### ฉ. ถ้าเปลี่ยนบรรทัดนี้
| เปลี่ยน | ผล |
|---|---|
| `bucket.count >= max` → `bucket.count > max` | ได้ 11 ครั้งแทน 10 (บั๊กนับเกิน 1 — off-by-one) |
| ลบ `setInterval` ที่ลบรายการหมดอายุ | Map โตเรื่อย ๆ ถ้าเปิด server นาน ๆ (memory leak) |
| เหลือแค่ชั้น IP | นักศึกษาทั้งห้อง lab ใช้ IP เดียวกัน คนหนึ่งพิมพ์ผิดรัว ๆ ทำให้ทั้งห้องโดนบล็อก |

### ช. คำถามกรรมการ
1. **ทำไมไม่ใช้ไลบรารีสำเร็จรูป?** — *เขียนเองสั้น (ไม่ถึง 50 บรรทัด) ควบคุมข้อความไทยและการนับ 2 ชั้นได้เอง และพอสำหรับ server เครื่องเดียว — ถ้าขยายหลายเครื่องจะเปลี่ยนไปใช้ Redis*
2. **ความซับซ้อนของการค้นใน Map เท่าไร?** — *ค้นด้วยกุญแจเฉลี่ยคงที่ (O(1)) ไม่ต้องวนทั้งสมุด จึงไม่ช้าลงเมื่อผู้ใช้มากขึ้น*
3. **ทำไมเปลี่ยนรหัสผ่านก็ต้องจำกัด?** — *ต้องกรอกรหัสเดิม = เดาได้เหมือน login ถ้าขโมย cookie มาได้จะนั่งเดารหัสเดิมไม่จำกัดเพื่อยึดบัญชีถาวร (`PATCH /auth/password` จำกัด 10 ครั้ง/15 นาทีต่อ IP)*

# 4. สถานะจริงของรอบ (phase)

### ก. ปัญหา
คอลัมน์ `status` ใน DB มีแค่ `open`/`closed` (เจ้าหน้าที่กดเอง) แต่ "นักศึกษากรอกได้ไหม" ขึ้นกับ **วันที่** ด้วย — รอบที่ `open` อาจยังไม่ถึงวันเปิด หรือเลยวันปิดแล้ว

### ข. วิธีคิด
```
ถ้า status ไม่ใช่ open → "closed" (ปิดแล้ว)
ไม่งั้น ถ้า ตอนนี้ < วันเปิด → "scheduled" (รอถึงกำหนดเปิด)
ไม่งั้น ถ้า ตอนนี้ > วันปิด → "expired" (เลยกำหนดปิด แต่ยังไม่ได้กดปิด)
ไม่งั้น → "active" (เปิดรับจริง)
```

### ค. โค้ดจริง — `backend/src/utils/roundPhase.js`
```js
export const getRoundPhase = (round, now = new Date()) => {      // ①
  if (round.status !== "open") return ROUND_PHASE.CLOSED;
  if (now < new Date(round.open_date)) return ROUND_PHASE.SCHEDULED;
  if (now > new Date(round.close_date)) return ROUND_PHASE.EXPIRED;
  return ROUND_PHASE.ACTIVE;
};
export const withPhase = (round) => {
  if (!round) return round;
  return { ...round, phase: getRoundPhase(round) };              // ②
};
```
คู่กับ `backend/src/modules/rounds/rounds.repository.js` → `findActive`
```js
where: { status: "open", open_date: { lte: now }, close_date: { gte: now }, academic_year: academicYear } // ③
```
① `now = new Date()` = ค่าเริ่มต้นของพารามิเตอร์ (ไม่ส่งมาก็ใช้เวลาปัจจุบัน — เทสส่งเวลาที่ต้องการทดสอบเข้ามาได้)
② คัดลอกทุกช่องของรอบ (`...`) แล้วเพิ่ม `phase` — **คำนวณตอนตอบทุกครั้ง ไม่เก็บลง DB**
③ เงื่อนไข "active" ฝั่งฐานข้อมูล: `lte` = น้อยกว่าหรือเท่ากับ, `gte` = มากกว่าหรือเท่ากับ — **ต้องตรงกับ `getRoundPhase` เป๊ะ** (เคยมีบั๊กหน้าจอเขียน "เปิดรับ" แต่ส่งไม่ได้ เพราะสองที่ไม่ตรงกัน)

**เวลาไทย:** `rounds.controller.js → parseThaiDateTime` สร้างเวลาแบบ UTC แล้วลบ 7 ชั่วโมง (`ICT_OFFSET_MS`) เอง ไม่ใช้ `setHours()` (ซึ่งใช้ timezone ของเครื่อง server) · วันปิดที่ไม่มีเวลา = 23:59:59.999 (`END_OF_DAY`)

### ง. ตารางไล่โค้ด — รอบ status `open`, เปิด 1 ต.ค. 00:00, ปิด 15 ต.ค. 23:59:59.999 (เวลาไทย)
| ตอนนี้ (เวลาไทย) | `status !== "open"`? | `now < open`? | `now > close`? | phase | `findActive` เจอไหม |
|---|---|---|---|---|---|
| 30 ก.ย. 22:00 | ไม่ | **ใช่** | — | `scheduled` | ไม่เจอ |
| 1 ต.ค. 00:00:00 | ไม่ | ไม่ (เท่ากัน) | ไม่ | `active` | เจอ (`lte` รวมเท่ากับ) |
| 15 ต.ค. 23:59:30 | ไม่ | ไม่ | ไม่ | `active` | เจอ |
| 16 ต.ค. 00:00:00 | ไม่ | ไม่ | **ใช่** | `expired` | ไม่เจอ |
| (เจ้าหน้าที่กดปิด) | **ใช่** | — | — | `closed` | ไม่เจอ |

### จ. กรณีขอบ
- วันเปิดกับวันปิดสลับกัน → ไม่มีวันไหน active เลย → `ensureValidDateRange` ใน controller กันตั้งแต่ตอนบันทึก (400)
- ฝั่งหน้าเว็บมี `frontend/src/design/roundPhase.js → phaseOf` คำนวณสำรอง **กฎเดียวกัน** เผื่อข้อมูลเก่าที่ไม่มี `phase`
- ปิดรับ 23:59 ถ้าเก็บเป็น 23:59:00 → คนส่ง 23:59:30 ถูกปฏิเสธทั้งที่จอบอกยังไม่ปิด → จึงเติม `.999` (`parseCloseDate`)

### ฉ. ถ้าเปลี่ยนบรรทัดนี้
| เปลี่ยน | ผล |
|---|---|
| `now > close` → `now >= close` แต่ไม่แก้ `findActive` | ที่วินาทีปิดพอดี จอเขียน "เลยกำหนด" แต่ backend ยังรับ = สองที่ไม่ตรงกัน |
| เก็บ phase ลง DB | ต้องมีตัวตั้งเวลาไปอัปเดตทุกนาที ถ้าตัวตั้งเวลาพลาด สถานะผิดค้าง |

### ช. คำถามกรรมการ
1. **ทำไมไม่เก็บ phase ในฐานข้อมูล?** — *ค่าเปลี่ยนเองตามเวลาโดยไม่มีเหตุการณ์ใดเกิด เก็บแล้วต้องมีงานตั้งเวลาอัปเดต · คำนวณตอนอ่านถูกเสมอและราคาถูก (เทียบวันที่ 2 ครั้ง)*
2. **ทำไมไม่ใช้ `setHours`?** — *`setHours` ใช้ timezone ของเครื่อง server ถ้าขึ้นเครื่องที่ตั้งเป็น UTC "ปิด 23:59" จะกลายเป็น 06:59 ของวันถัดไปเวลาไทย · ไทยไม่มี daylight saving จึงบวกลบ 7 ชั่วโมงเองได้ตรง ๆ*
3. **`findOpenForYear` ต่างจาก `findActive` ยังไง?** — *`findOpenForYear` ไม่ดูวันที่ ใช้ตอน "แสดงผล" ให้นักศึกษาเห็นว่ารอบจะเปิดวันไหน · `findActive` ดูวันที่ ใช้ตอน "รับผลจริง" — ความปลอดภัยไม่ลด เพราะตอนส่งผลยังผ่าน `findActive` (ผ่าน `findSubmittableRound`)*

# 5. หารอบที่ส่งผลได้ `findSubmittableRound`  (ใหม่ 1 ต.ค.)

### ก. ปัญหา
เจ้าหน้าที่ตรวจใบได้ทั้งระหว่างรอบและ **หลังปิดรอบ** — ถ้าตีกลับหลังปิดรอบ เดิมนักศึกษาแก้ไม่ได้เลย (ส่งได้เฉพาะตอนรอบเปิด) ต้องเลื่อนวันปิดทั้งรอบ ซึ่งทำไม่ได้ถ้ารอบถัดไปเปิดอยู่
**ตัดสินใจ (เจ้าของงาน 1 ต.ค. 2569):** ใบที่ถูกตีกลับ แก้ส่งใหม่ได้แม้รอบปิด — แต่คนที่ไม่เคยส่ง/ใบรอตรวจ ยังส่งหลังปิดไม่ได้

### ข. วิธีคิด
```
ขั้น 1: หารอบของรุ่นนี้ที่เปิดรับอยู่จริงตอนนี้ (findActive)
    ถ้าเจอ → คืน { รอบนั้น, แก้หลังปิดรอบ = ไม่ใช่ }
ขั้น 2: หารอบล่าสุดของรุ่นนี้ที่ถึงวันเปิดแล้ว (ปิดแล้วก็ได้)
    ถ้าไม่เจอ → คืน "ไม่มี"
ขั้น 3: หาใบของนักศึกษาคนนี้ในรอบนั้น
    ถ้ามีใบ และ ใบถูกตีกลับ → คืน { รอบนั้น, แก้หลังปิดรอบ = ใช่ }
    ไม่งั้น → คืน "ไม่มี"
```

### ค. โค้ดจริง — `backend/src/modules/examResults/examResults.service.js`
```js
export const findSubmittableRound = async (student) => {
  const activeRound = await roundsRepo.findActive(student.academic_year);          // ①
  if (activeRound) {
    return { round: activeRound, fixingRejected: false };
  }
  const latestRound = await roundsRepo.findLatestStarted(student.academic_year);   // ②
  if (!latestRound) {
    return null;
  }
  const paper = await examRepo.findByStudentAndRound(student.student_id, latestRound.round_id); // ③
  if (paper && paper.staff_status === STAFF_STATUS.REJECTED) {
    return { round: latestRound, fixingRejected: true };
  }
  return null;
};
```
`rounds.repository.js → findLatestStarted`: `where: { academic_year, open_date: { lte: new Date() } }`, `orderBy: { attempt_number: "desc" }` = รอบที่มี "ครั้งที่" สูงสุดในบรรดารอบที่ถึงวันเปิดแล้ว

① รอบเปิดมาก่อนเสมอ — ถ้ามีรอบ 2 เปิดอยู่ ใบรอบ 1 ที่ถูกตีกลับต้องไปแก้ "ในรอบ 2" (วิชาที่ยังไม่ผ่านอยู่ในฟอร์มรอบ 2 แล้ว)
② ดูเฉพาะ **รอบล่าสุด** ไม่ย้อนรอบเก่า — ถ้ามีรอบใหม่กว่าเกิดขึ้นแล้ว การย้อนไปแก้ใบเก่าจะทำให้ผลที่ยกไปรอบหลังเพี้ยน
③ ต้องเป็น "ใบที่ถูกตีกลับ" เท่านั้น

**ใช้ 3 ที่ (ตัดสินตรงกันเสมอ):**

### ช. คำถามกรรมการ
1. **ทำไมไม่ให้เจ้าหน้าที่เลื่อนวันปิดรอบแทน?** — *เลื่อนวันปิด = ทุกคนในรุ่นส่ง/แก้ได้หมด ไม่ใช่แค่คนที่ถูกตีกลับ และทำไม่ได้ถ้ารอบถัดไปเปิดอยู่ (เปิดได้ทีละรอบ) — ยกเว้นเฉพาะใบที่ถูกตีกลับตรงกว่า*
2. **ทำไมต้องใช้ฟังก์ชันเดียวกัน 3 ที่?** — *ถ้าหน้าจอใช้กฎหนึ่ง ตอนส่งใช้อีกกฎ ผู้ใช้จะเห็นฟอร์มแต่ส่งไม่ได้ (หรือกลับกัน) · และถ้าการแนบไฟล์ใช้กฎหลวมกว่า หลักฐานของใบที่ปิดไปแล้วจะถูกสลับทีหลังได้ (เป็นช่องโหว่ที่ security review เจอและแก้แล้ว — เทส `phase27`)*
3. **มีโอกาสที่นักศึกษาแก้ใบถูกตีกลับได้ตลอดไปไหม?** — *ได้ ถ้าไม่มีรอบใหม่เกิดขึ้น — เป็นข้อจำกัดที่รู้ ถ้าคณะต้องการกำหนดเส้นตาย เพิ่มเงื่อนไขจำนวนวันหลังปิดรอบในขั้น 2 ได้ (ดู `08` ข้อ C3)*

# 6. ตรวจผลสอบที่ส่งมา + ยกผลรอบก่อน (carry-forward) + บั๊ก B1

### ก. ปัญหา
1. ข้อมูลจาก client เชื่อไม่ได้: อาจส่งวิชานอกรอบ, วิชาซ้ำ, `"false"` เป็นข้อความ, ไม่ครบ
2. รอบ 2–3 นักศึกษาสอบเฉพาะวิชาที่ยังไม่ผ่าน — วิชาที่ผ่านแล้วไม่ควรต้องกรอกซ้ำ และ **ห้ามแก้ให้กลายเป็นไม่ผ่าน**

### ข. วิธีคิด
```
วิชาของรอบ = ตามที่เจ้าหน้าที่เลือก (ไม่ได้เลือก = ทุกวิชา)
วิชาที่เคยผ่าน = วิชาที่ผ่าน "จริง" ในใบของรอบอื่นที่ไม่ถูกตีกลับ
วิชาที่ต้องตอบ = วิชาของรอบ ที่ไม่อยู่ใน วิชาที่เคยผ่าน

วนทีละรายการที่ส่งมา:
    ถ้า วิชาไม่อยู่ในรอบ → 400
    ถ้า ผลไม่ใช่ true/false จริง → 400
    ถ้า วิชานี้ส่งมาแล้วในรายการ → 400 "ส่งวิชาซ้ำกัน"
    จดคำตอบ
ถ้า วิชาที่ต้องตอบ ยังขาดคำตอบ → 400 "ยังขาดอีก N วิชา"

ผลที่จะบันทึก = วนทุกวิชาของรอบ:
    ถ้า เคยผ่าน → ผ่าน + ติดธง "ยกมา"
    ไม่งั้น → ใช้คำตอบที่ส่งมา + ไม่ติดธง
ถ้า มีใบของรอบนี้อยู่แล้ว → ทับใบเดิม  ไม่งั้น → สร้างใบใหม่
```

### ค. โค้ดจริง
`backend/src/modules/examResults/examResults.controller.js → create` (ส่วนตรวจและยกผล)
```js

const passedIds = await examRepo.findPassedSubjectIds(student.student_id, round.round_id); // ②
const mustAnswer = roundSubjectIds.filter((id) => !passedIds.includes(id));        // ③

const answers = new Map();
for (const item of subject_results) {
  const subjectId = Number(item?.subject_id);
  if (!roundSubjectIds.includes(subjectId)) throw httpError("มีวิชาที่ไม่ได้อยู่ในรอบการกรอกนี้", 400);
  if (typeof item.is_passed !== "boolean") throw httpError("ผลสอบแต่ละวิชาต้องเป็นผ่านหรือไม่ผ่านเท่านั้น", 400); // ④
  if (answers.has(subjectId)) throw httpError("ส่งวิชาซ้ำกัน", 400);
  answers.set(subjectId, item.is_passed);
}
const missing = mustAnswer.filter((id) => !answers.has(id));
if (missing.length > 0) throw httpError(`กรอกผลไม่ครบ ยังขาดอีก ${missing.length} วิชา`, 400);

const finalResults = roundSubjectIds.map((id) => {                                  // ⑤
  const passedBefore = passedIds.includes(id);
  let isPassed;
  if (passedBefore) { isPassed = true; } else { isPassed = answers.get(id); }
  return { subject_id: id, is_passed: isPassed, carried_forward: passedBefore };
});
```

① วิชาของรอบ (`utils/roundSubjects.js → subjectsOfRound`: รอบเก่าที่ `subject_ids` ว่าง = ทุกวิชา)
② วิชาที่เคยผ่าน — ส่งรอบนี้ไปด้วยเพื่อ **ตัดใบของรอบนี้เองออก** (ไม่งั้นใบรอบนี้ที่ถูกตีกลับแล้วแก้ จะย้อนมาล็อกวิชาตัวเอง)
③ วิชาที่ต้องตอบ = วิชาของรอบ − วิชาที่เคยผ่าน
④ `typeof … !== "boolean"` — ถ้าปล่อย `"false"` (ข้อความ) ผ่าน `Boolean("false")` จะได้ `true` (ข้อความไม่ว่างเป็นจริงเสมอ) → ตกกลายเป็นผ่าน
⑤ สร้างผลครบทุกวิชาของรอบ — วิชาที่เคยผ่าน **บังคับเป็นผ่าน ไม่สนค่าที่ส่งมา**
⑥ นับเฉพาะแถวที่ **สอบจริงแล้วผ่าน** ไม่นับแถวที่ยกมา (ดูเรื่อง B1)
⑦ ใบที่ถูกตีกลับเชื่อไม่ได้ ไม่นับ · ใบรอตรวจนับให้ (ไม่งั้นเปิดรอบใหม่ก่อนตรวจครบ นักศึกษาต้องกรอกวิชาที่เพิ่งผ่านซ้ำ)
⑧ `buildExcludeRound` คืน `{ NOT: { round_id } }` หรือ `{}` แล้วกาง (`...`) เข้าไปในเงื่อนไข
⑨ วิชาเดียวกันอาจผ่านหลายรอบ → `Set` ตัดซ้ำ → กางกลับเป็น array

**บันทึก:** ใบใหม่ `createWithSubjects` (Prisma สร้างใบ + ผลรายวิชาพร้อมกันในคำสั่งเดียว = transaction) · ใบเดิม `resubmitWithSubjects` ใช้ `$transaction` : `updateMany` ที่มีเงื่อนไข `staff_status ≠ approved` → ถ้า `count === 0` (ถูกยืนยันไปก่อน) โยน 409 → ลบผลรายวิชาเดิม → สร้างชุดใหม่ (ทั้งหมดสำเร็จพร้อมกันหรือไม่เกิดเลย)

| ⑦ เปลี่ยนเป็น `staff_status: "approved"` | ปลอดภัยขึ้น แต่ต้องตรวจรอบก่อนให้ครบก่อนเปิดรอบใหม่ (ดู `08` D4) |
| ไม่ส่ง `round.round_id` ใน ② | ใบรอบนี้ที่ถูกตีกลับ ย้อนมาล็อกวิชาที่ตัวเองเพิ่งติ๊ก → แก้ไม่ได้ |

### ช. คำถามกรรมการ
1. **ทำไมไม่เชื่อค่าที่ client ส่งมาสำหรับวิชาที่เคยผ่าน?** — *ผู้ใช้แก้โค้ดในเบราว์เซอร์หรือยิง API เองได้ กฎ "ผ่านแล้วห้ามกลายเป็นตก" ต้องบังคับที่ backend เสมอ*
2. **ธง `carried_forward` มีไว้ทำไม?** — *แยก "ผ่านเพราะสอบรอบนี้" กับ "ผ่านเพราะยกมา" — สถิติรายวิชานับเฉพาะคนที่สอบจริง (ไม่งั้นวิชาที่ทุกคนยกมาจะขึ้น 100%) และหลังแก้ B1 ใช้ตัดแถวสำเนาไม่ให้ไปล็อกรอบถัดไป*
3. **ทำไมต้องใช้ transaction ตอนบันทึก?** — *ใบกับผลรายวิชาต้องตรงกัน ถ้าพังหลังลบผลเดิมแต่ก่อนสร้างผลใหม่ ใบจะไม่มีผลรายวิชาเลย — transaction ทำให้สำเร็จทั้งหมดหรือย้อนกลับทั้งหมด*

# 7. กันสองคนตรวจใบเดียวกันพร้อมกัน (optimistic guard)

### ก. ปัญหา (race condition = สองงานแข่งกันแตะข้อมูลเดียวกัน)
เจ้าหน้าที่ A กับผู้ช่วยตรวจสอบ B เปิดใบเดียวกัน — A กด "ยืนยัน" B กด "ตีกลับ" เกือบพร้อมกัน ถ้าโค้ด "อ่านสถานะ → ตรวจ → เขียน" แยกกัน (check-then-act) ทั้งคู่อ่านได้ pending ทั้งคู่ผ่าน คนหลังเขียนทับคนแรก

### ข. วิธีคิด
```
อ่านใบ
ถ้า ไม่พบ → 404
ถ้า สถานะไม่ใช่ pending → 409 (ด่านให้ข้อความชัดในกรณีทั่วไป)
ถ้า ตีกลับแต่ไม่มีเหตุผล → 400
สั่งฐานข้อมูล: "แก้ใบนี้ เฉพาะถ้ายัง pending อยู่"   ← ตรวจและเขียนในคำสั่งเดียว
ถ้า ฐานข้อมูลบอกว่าแก้ได้ 0 แถว → มีคนตัดหน้า → 409
บันทึกประวัติการตรวจ (พลาดได้ ไม่ทำให้การตรวจล้ม)
สร้างแจ้งเตือนให้นักศึกษา (พลาดได้ ไม่ทำให้การตรวจล้ม)
```

### ค. โค้ดจริง — `examResults.controller.js → reviewExamResult` (ย่อ)

```js
  staff_status, remark: remarkToSave, confirmed_by: req.user.userId,
```

① ด่านเช็คก่อน — มีไว้ให้ข้อความชัดในกรณีปกติ (ใบที่ตรวจไปนานแล้ว) **ไม่ใช่ตัวกันจริง**
② ③ ⑥ **ตัวกันจริง:** เงื่อนไข "ยัง pending" อยู่ใน `UPDATE … WHERE` — ฐานข้อมูลล็อกแถวตอนแก้ ทำให้ "ตรวจ + เขียน" เป็นขั้นเดียวที่แบ่งไม่ได้ (atomic) · `updateMany` คืน `{ count }` = จำนวนแถวที่แก้ได้
- ทำไมใช้ `updateMany` ไม่ใช้ `update`: `update` ของ Prisma รับ `where` เฉพาะคอลัมน์ unique ใส่เงื่อนไขสถานะเพิ่มไม่ได้
④ `review_logs` เพิ่มอย่างเดียว ไม่แก้ไม่ลบ = ประวัติตรวจย้อนหลังได้ · ห่อ try/catch เพราะการตรวจสำเร็จไปแล้ว
⑤ รอให้แจ้งเตือนบันทึกเสร็จก่อนตอบ (`await`) แต่พลาดไม่ทำให้การตรวจล้ม (เดิมยิงแบบไม่รอ ทำให้นักศึกษาเปิดดูทันทีแล้วยังไม่เห็น เทสสะดุดเป็นครั้งคราว)
- `confirmed_by: req.user.userId` — ผู้ตรวจมาจาก token+DB ไม่รับจาก body

### ง. ตารางไล่โค้ด — A ยืนยัน, B ตีกลับ ใบ 12 (เริ่ม pending)
| เวลา | A (ยืนยัน) | B (ตีกลับ) | สถานะในฐานข้อมูล |
|---|---|---|---|
| t1 | ① อ่านได้ pending → ผ่าน | | pending |
| t2 | | ① อ่านได้ pending → ผ่าน | pending |
| t3 | ② UPDATE … WHERE pending → **count = 1** | | approved |
| t4 | | ② UPDATE … WHERE pending → ไม่มีแถวตรง → **count = 0** | approved |
| t5 | ตอบ 200 | ③ ตอบ **409** "ใบนี้ถูกตรวจไปแล้ว" | approved (ไม่ถูกทับ) |
ถ้าไม่มีเงื่อนไขใน ⑥: ที่ t4 B จะเขียนทับเป็น rejected → ผลสุดท้ายขึ้นกับว่าใครช้ากว่า (เทสคุม: `phase15` PH15-02, `phase25` PH25-04)

### จ. กรณีขอบ
- ใบที่ยืนยันแล้ว ตรวจซ้ำตรง ๆ ไม่ได้ (409) — ต้อง "ถอนการยืนยัน" (`revokeApproval` ใช้ท่าเดียวกัน: `revokeApprovalIfApproved` = `updateMany … WHERE staff_status = approved`) หรือให้นักศึกษาส่งใหม่
- ใบที่ถูกตีกลับ → นักศึกษาส่งใหม่ → `resubmitWithSubjects` ตั้งกลับเป็น pending + ล้าง `remark`, `confirmed_by`, `confirmed_at` → ตรวจได้อีกครั้ง
- เจ้าหน้าที่ยืนยันขณะนักศึกษากำลังส่งแก้ → ฝั่งนักศึกษาได้ 409 จาก `resubmitWithSubjects` (ท่าเดียวกัน กลับด้าน)

### ฉ. ถ้าเปลี่ยนบรรทัดนี้
| เปลี่ยน | ผล |
|---|---|
| ลบ ① แต่เก็บ ⑥ | ยังปลอดภัย แค่ข้อความในกรณีทั่วไปมาจาก ③ แทน (ข้อความเดียวกัน) |
| ลบ ⑥ (ใช้ `update` ธรรมดา) แต่เก็บ ① | ปลอดภัยเกือบทุกครั้ง ยกเว้นกดพร้อมกันพอดี = บั๊กที่เกิดนาน ๆ ครั้ง หายาก |
| ⑤ ไม่ห่อ try/catch | แจ้งเตือนพลาด → เจ้าหน้าที่เห็น error ทั้งที่การตรวจบันทึกสำเร็จแล้ว |

### ช. คำถามกรรมการ
1. **optimistic กับ pessimistic locking ต่างกันยังไง?** — *pessimistic = ล็อกใบตั้งแต่ตอนเปิดอ่าน คนอื่นต้องรอ · optimistic = ไม่ล็อกล่วงหน้า (คาดว่าชนกันน้อย) แต่ตรวจตอนเขียนว่าสถานะยังเหมือนที่คาดไว้ไหม ถ้าไม่ก็ปฏิเสธ — เหมาะกับระบบที่ชนกันนาน ๆ ครั้งอย่างของเรา*
2. **ทำไมไม่ใช้ transaction แทน?** — *transaction ระดับปกติของ Postgres (read committed) ไม่กัน "อ่านแล้วค่อยเขียน" ของสองคนได้โดยตัวเอง ต้องล็อกเพิ่ม · การใส่เงื่อนไขใน UPDATE ง่ายกว่าและได้ผลเท่ากันในกรณีนี้*
3. **review_logs กับ confirmed_by ต่างกันยังไง?** — *`confirmed_by` เก็บแค่ผู้ตัดสินล่าสุด และถูกล้างเมื่อส่งใหม่/ถอนการยืนยัน · `review_logs` เก็บทุกการตัดสินแบบเพิ่มอย่างเดียว ตรวจย้อนหลังได้ว่าใครตัดสินอะไรเมื่อไร*

# 8. ตรวจชนิดไฟล์จากไบต์ต้นไฟล์ (magic bytes) + จำกัดจำนวนไฟล์  (ใหม่ 1 ต.ค.)

### ก. ปัญหา
นามสกุลไฟล์ (`.pdf`) และชนิดที่เบราว์เซอร์บอก (mimetype) **ปลอมได้ทั้งคู่** — เปลี่ยนชื่อไฟล์ HTML เป็น `ใบคะแนน.pdf` ก็ผ่าน ถ้าเจ้าหน้าที่เปิดไฟล์ปลอมอาจอันตราย และนักศึกษาอาจกดแนบรัว ๆ จนเกิน 5 ไฟล์

### ข. วิธีคิด
```
ด่าน multer (upload.js): ชนิดที่เบราว์เซอร์บอก ต้องเป็น PDF/JPG/PNG และขนาด ≤ 10 MB (ด่านหยาบ)
ด่าน controller:
    อ่าน 8 ไบต์แรกของไฟล์
    วนทีละชนิดที่รู้จัก (PDF, JPG, PNG):
        ถ้า ไฟล์สั้นกว่าหัวของชนิดนี้ → ข้าม
        วนเทียบทีละไบต์ ถ้าไม่ตรงสักไบต์ → ไม่ใช่ชนิดนี้
        ถ้าตรงทุกไบต์ → ได้ชนิดนี้
    ถ้าไม่ตรงชนิดไหนเลย → 400
    นับไฟล์ในใบ ถ้า ≥ 5 → 400
    บันทึกแถวไฟล์
    นับซ้ำหลังบันทึก ถ้า > 5 (มีคนแนบพร้อมกัน) หรือใบถูกยืนยันระหว่างนั้น → ถอนแถวที่เพิ่งบันทึก → error
    ถ้าพังก่อนบันทึกสำเร็จ → ลบไฟล์บนดิสก์ทิ้งเสมอ
```

### ค. โค้ดจริง — `backend/src/modules/certificates/certificates.controller.js`
```js
const FILE_SIGNATURES = [
  { fileType: "pdf", bytes: [0x25, 0x50, 0x44, 0x46, 0x2d] },                 // "%PDF-"
  { fileType: "jpg", bytes: [0xff, 0xd8, 0xff] },
  { fileType: "png", bytes: [0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a] },
];
const detectFileType = async (filePath) => {
  const head = Buffer.alloc(8);                                  // ①
  const fileHandle = await fs.open(filePath, "r");
  let bytesRead = 0;
  try {
    const readResult = await fileHandle.read(head, 0, 8, 0);     // ②
    bytesRead = readResult.bytesRead;
  } finally {
    await fileHandle.close();                                    // ③
  }
  for (const signature of FILE_SIGNATURES) {
    if (bytesRead < signature.bytes.length) { continue; }        // ④
    let allMatch = true;
    for (let i = 0; i < signature.bytes.length; i++) {           // ⑤
      if (head[i] !== signature.bytes[i]) { allMatch = false; break; }
    }
    if (allMatch) { return signature.fileType; }
  }
  return null;
};
```

① จองพื้นที่ 8 ไบต์ (หัวที่ยาวที่สุดคือ PNG = 8 ไบต์) — ไม่อ่านทั้งไฟล์ 10 MB
② อ่าน 8 ไบต์จากตำแหน่ง 0 · `bytesRead` = อ่านได้จริงกี่ไบต์ (ไฟล์ 0 ไบต์ได้ 0)
③ `finally` = ทำเสมอไม่ว่าอ่านสำเร็จหรือ error → ปิดไฟล์ทุกครั้ง (บน Windows ไฟล์ที่เปิดค้างลบไม่ได้)
④ ไฟล์สั้นกว่าหัวของชนิดนี้ → ไม่ใช่ชนิดนี้แน่นอน
⑤ วนเทียบทีละไบต์ ไม่ตรงไบต์ไหน `break` ออกทันที
⑥ ธง "บันทึกสำเร็จแล้วหรือยัง" — ใช้ตัดสินตอน error ว่าต้องลบไฟล์บนดิสก์ไหม
⑦ ตรวจสิทธิ์: เป็นเจ้าของใบ · ใบยังไม่ยืนยัน · ใบอยู่ในรอบที่ `findSubmittableRound` คืนมา (หัวข้อ 5)
⑧ เก็บ `file_type` จาก **เนื้อไฟล์** ไม่ใช่จากนามสกุล — ตอนเปิดไฟล์ `serveFile` ส่ง Content-Type ตามค่านี้
⑨ **นับซ้ำหลังบันทึก** — กดแนบ 10 ไฟล์พร้อมกัน ทุก request นับได้ 4 พร้อมกันจึงผ่านด่านก่อนหน้าหมด (เทส `phase27` เดิมได้ 6 ไฟล์) → request ไหนนับแล้วเกิน ถอนแถวตัวเอง สุดท้ายเหลือ ≤ 5
⑩ ทุกทางที่ล้มก่อนบันทึก → ลบไฟล์ที่ multer เขียนลงดิสก์ไปแล้ว ไม่ให้มีไฟล์กำพร้า

### ง. ตารางไล่โค้ด — `detectFileType`
| ไฟล์ | 8 ไบต์แรก (เลขฐาน 16) | bytesRead | เทียบ PDF (5 ไบต์) | เทียบ JPG (3) | เทียบ PNG (8) | ผล |
|---|---|---|---|---|---|---|
| ใบคะแนน.pdf ของจริง | 25 50 44 46 2D 31 2E 34 | 8 | ตรงครบ 5 | — | — | `"pdf"` |
| รูป.jpg | FF D8 FF E0 00 10 4A 46 | 8 | ไบต์แรก 25≠FF → break | ตรงครบ 3 | — | `"jpg"` |
| หน้าเว็บ.html เปลี่ยนชื่อเป็น .pdf | 3C 21 44 4F 43 54 59 50 (`<!DOCTYP`) | 8 | 25≠3C | FF≠3C | 89≠3C | `null` → **400** |
| ไฟล์ว่าง.pdf | — | 0 | 0<5 ข้าม | 0<3 ข้าม | 0<8 ข้าม | `null` → 400 (เทส PH26-09) |
| รูป GIF ที่อ้างเป็น PNG | 47 49 46 38 39 61 … | 8 | ไม่ตรง | ไม่ตรง | 89≠47 | `null` → 400 (PH26-10) |

### จ. กรณีขอบ
- ไฟล์ใหญ่เกิน 10 MB → multer ตัดตั้งแต่ด่านแรก (`MulterError LIMIT_FILE_SIZE`) → `errorHandler` แปลเป็น "ไฟล์ใหญ่เกินกำหนด…" (PH26-08)
- ชื่อไฟล์ภาษาไทย multer อ่านเป็น latin1 → `Buffer.from(name, "latin1").toString("utf8")` แปลงกลับ
- ชื่อไฟล์บนดิสก์ตั้งเอง (`เวลา-เลขสุ่ม.นามสกุล` ใน `upload.js`) ไม่ใช้ชื่อจากผู้ใช้ → กัน path traversal (ชื่อแบบ `../../server.js`)
- ลบไฟล์ (`remove`): ลบแถวใน DB ก่อน แล้วค่อยลบไฟล์บนดิสก์ — ถ้ากลับกันแล้ว DB พัง จะเหลือแถวที่ชี้ไปหาไฟล์ที่ไม่มีอยู่

### ฉ. ถ้าเปลี่ยนบรรทัดนี้
| เปลี่ยน | ผล |
|---|---|
| ลบ ④ | ไฟล์สั้น `head[i]` ส่วนที่อ่านไม่ได้เป็น 0 — PNG ไม่ผิดพลาดเพราะไบต์ไม่ใช่ 0 แต่โค้ดอ่านยากและพึ่งโชค |
| ลบ ⑨ | กดแนบพร้อมกันได้เกิน 5 ไฟล์ (บั๊กที่ `phase27` เจอ) |
| ลบ `finally` แล้ว close หลัง read | ถ้า read error ไฟล์ค้างเปิด → Windows ลบไม่ได้ ไฟล์กำพร้า |

### ช. คำถามกรรมการ
1. **magic bytes คืออะไร?** — *ไบต์ชุดแรกของไฟล์ที่มาตรฐานของไฟล์แต่ละชนิดกำหนดไว้ เช่น PDF ขึ้นต้น `%PDF-` · ผู้ใช้เปลี่ยนชื่อไฟล์ได้แต่เปลี่ยนเนื้อไฟล์ไม่ได้โดยไม่ทำให้ไฟล์เสีย จึงเชื่อถือได้กว่านามสกุล*
2. **ตรวจแค่หัวไฟล์พอไหม?** — *กันการเปลี่ยนนามสกุลได้ แต่ไม่รับประกันว่าเนื้อในปลอดภัย 100% (เช่น PDF ที่มีสคริปต์) — ระบบลดความเสี่ยงเพิ่มด้วย: ให้เปิดเฉพาะเจ้าของ/ผู้ตรวจ, ส่ง Content-Type ตามชนิดจริง, helmet ใส่ header ห้ามเบราว์เซอร์เดาชนิดเอง (nosniff)*
3. **ทำไมต้องนับไฟล์ซ้ำหลังบันทึก?** — *การนับก่อนบันทึกเป็น check-then-act แบบเดียวกับหัวข้อ 7 — สองคำขอพร้อมกันนับได้ค่าเดียวกัน · นับซ้ำหลังบันทึกแล้วถอนตัวเองถ้าเกิน ทำให้ผลสุดท้ายถูกเสมอ*

# 9. "ผ่านครั้งแรก" กับ "ผ่านภายในปีแรก"

### ก. ปัญหา
คณะต้องรายงานสภาการพยาบาล 2 ตัวเลข ที่คนมักสับสน และนักศึกษาคนเดียวมีหลายใบในปีเดียว (หลายรอบ) ถ้านับ "ตามใบ" ตัวเลขจะเกินจำนวนคน

### ข. วิธีคิด
```

ผ่านครั้งแรก:
    เอาเฉพาะใบของรอบที่ 1 ที่ยืนยันแล้ว
    นับคนที่ ทุกวิชาของรอบ 1 มีผล "ผ่าน"

    สมุด passedByStudent: รหัสนักศึกษา → ชุดวิชาที่ผ่านจริง
    วนทุกรอบของปี:
        วนทุกใบ:
            ถ้า ใบยังเป็นร่าง หรือ ยังไม่ยืนยัน → ข้าม
            วนทุกวิชาในใบ:
                ถ้า ไม่ผ่าน หรือ เป็นแถวยกมา → ข้าม
                เพิ่มวิชานี้ในชุดของคนนี้
    วิชาที่ต้องผ่าน = วิชาของรอบ 1 (ไม่มีรอบ 1 = ทุกวิชา)
    นับคนที่ชุดวิชาครอบคลุมวิชาที่ต้องผ่านทั้งหมด
```

```js
const onlyConfirmed = (results) => results.filter((r) => r.staff_status === "approved"); // ①

const countFullyPassed = (sent, subjectIds) =>                                            // ②
  sent.filter((r) =>
    subjectIds.every((id) =>
      r.subject_results.some((sr) => sr.subject_id === id && sr.is_passed),
    ),
  ).length;

function addConfirmedRealPasses(passedByStudent, results) {                               // ③
  for (const r of results) {
    if (r.student_status === "draft") continue;
    if (r.staff_status !== "approved") continue;
    if (!passedByStudent.has(r.student_id)) {
      passedByStudent.set(r.student_id, new Set());
    }
    const passedSet = passedByStudent.get(r.student_id);
    for (const sr of r.subject_results) {
      if (!sr.is_passed) continue;
      if (sr.carried_forward) continue;                                                   // ④ (B1)
      passedSet.add(sr.subject_id);
    }
  }
}

function hasPassedAll(passedSet, requiredSubjectIds) {                                    // ⑤
  if (!passedSet) return false;
  for (const id of requiredSubjectIds) {
    if (!passedSet.has(id)) return false;
  }
  return true;
}
```

3. **ความซับซ้อนของการคำนวณ?** — *วนทุกใบ × ทุกวิชาในใบ ครั้งเดียว = เชิงเส้นตามจำนวนผลรายวิชา (รุ่นละ ~200 คน × 8 วิชา × 3 รอบ ≈ 5,000 แถว) — การค้น `Map/Set` เป็นค่าคงที่ จึงไม่ต้องวนซ้อนหาคน*

# 10. นำเข้าไฟล์: เดาคอลัมน์ + ล้างเลขบัตร

### ก. ปัญหา

```js
const normalizeHeader = (raw) => String(raw ?? "").trim().toLowerCase().replace(/[\s-]+/g, "_");   // ①
const guessColumns = (headers) => {
  const guess = {};
  const used = new Set();
  for (const field of COLUMN_FIELDS) {                                                            // ["student_id","national_id","academic_year"]
    const exactNames = [field, ...(EXACT_NAMES[field] ?? [])];                                    // ②
    const exact = headers.filter((h) => exactNames.includes(normalizeHeader(h)));
    const matches = exact.length
      ? exact
      : headers.filter((h) => COLUMN_KEYWORDS[field].some((k) => normalizeHeader(h).includes(k))); // ③
    const free = matches.filter((h) => !used.has(h));                                             // ④
    guess[field] = free.length === 1 ? free[0] : null;                                            // ⑤
    if (guess[field]) used.add(guess[field]);
  }
  return guess;
};

const cleanIdText = (value) => {
  if (typeof value !== "string") return value;
  const asArabic = value.trim()
    .replace(/[๐-๙]/g, (d) => String(THAI_DIGITS.indexOf(d)))                                    // ⑥
    .replace(/[０-９]/g, (d) => String(d.charCodeAt(0) - 0xff10));
  const plain = plainNumberText(asArabic);                                                        // ⑦
  if (SCIENTIFIC_NOTATION_PATTERN.test(plain)) return plain;                                      // ⑧
  return plain.replace(/[^\p{L}\p{N}]/gu, "");                                                    // ⑨
};

const plainNumberText = (text) => {
  if (typeof text !== "string") return text;
  const t = text.trim();
  if (/^\d+\.0+$/.test(t)) return t.replace(/\.0+$/, "");                                         // ⑩
  const m = t.match(/^(\d+)\.(\d+)e\+?(\d+)$/i);
  if (m && m[2].length === Number(m[3])) return m[1] + m[2];                                      // ⑪
  return t;
};
```

# 11. แบ่งหน้า + "แสดง N จาก M"

### ก. ปัญหา
รายชื่อ 928 คนแสดงทีละหน้า — ต้องรู้ว่าหน้าไหนแสดงแถวไหน และตัวนับต้องถูกเสมอ (หน้าสุดท้ายแถวไม่เต็ม)

### ข. วิธีคิด
```
จำนวนหน้า = ปัดขึ้น( จำนวนแถว ÷ แถวต่อหน้า )
แถวของหน้า p (เริ่มนับ 0) = ตัดจากตำแหน่ง p × แถวต่อหน้า ถึงก่อน (p+1) × แถวต่อหน้า
แสดง N = น้อยกว่าระหว่าง (p+1) × แถวต่อหน้า กับ จำนวนแถวทั้งหมด
ถ้าตัวกรองเปลี่ยน → กลับหน้าแรก
```

### ค. โค้ดจริง
`frontend/src/design/officerStudentsReal.jsx`
```js
const per = 10;
const pageRows = filtered.slice(page * per, (page + 1) * per);           // ①
const pages = Math.ceil(filtered.length / per);                          // ②
useEffect(() => setPage(0), [q, status, room, year, eligible, subjectFilter, firstAttemptFilter]); // ③
// หัวหน้า:
tt(filtered.length < students.length ? 'officer.students.subFiltered' : 'officer.students.sub',
   { shown: Math.min((page + 1) * per, filtered.length), found: filtered.length, total: students.length }) // ④
```
`frontend/src/design/usePagedList.js` (ใช้ในหน้าจัดการผู้ใช้งาน)
```js
export function usePagedList(items, per = 20, resetKey = '') {
  const [page, setPage] = useState(0);
  const [seenKey, setSeenKey] = useState(resetKey);
  if (seenKey !== resetKey) { setSeenKey(resetKey); setPage(0); }        // ⑤
  const pages = Math.max(1, Math.ceil(items.length / per));
  const safePage = Math.min(page, pages - 1);                            // ⑥
  const rows = items.slice(safePage * per, (safePage + 1) * per);
  return { page: safePage, setPage, pages, rows };
}
```
① `slice(เริ่ม, จบ)` ได้แถวตั้งแต่ "เริ่ม" ถึงก่อน "จบ" — เกินท้ายลิสต์ก็ไม่ error แค่ได้น้อยลง
② ปัดขึ้น: 23 แถว ÷ 10 = 2.3 → 3 หน้า
③ ตัวกรองตัวใดตัวหนึ่งเปลี่ยน → กลับหน้า 1 (ลืมใส่ตัวกรองใหม่ในรายการนี้ = กรองแล้วค้างหน้าว่าง)
④ "แสดง N" = แถวสุดท้ายของหน้าปัจจุบัน แต่ไม่เกินจำนวนที่กรองได้ · ถ้ากรองอยู่ ข้อความเพิ่ม "(นักศึกษาทั้งหมด M คน)"
⑤ อีกแบบหนึ่ง: รีเซ็ต **ระหว่างวาดจอ** — เทียบกุญแจเก่า/ใหม่ แล้วตั้ง state ทันที React จะวาดใหม่ก่อนแสดงผล จึงไม่เห็นหน้าว่างแวบหนึ่งเหมือนแบบ `useEffect` (ซึ่งทำงานหลังวาดจอแล้ว)
⑥ กันหน้าเกินช่วง (ลบแถวสุดท้ายของหน้าสุดท้ายทิ้ง → หน้านั้นไม่มีแล้ว)

> **ความจริงที่ต้องรู้:** หน้าข้อมูลนักศึกษาใช้แบบ ③ (`useEffect`) ส่วน `usePagedList` (แบบ ⑤) ใช้ในหน้าจัดการผู้ใช้งาน — โค้ดสองแบบอยู่ร่วมกัน (เอกสาร `04` เขียนถึงแบบ ⑤ เป็นหลัก)
> `components.jsx → Pagination` แสดงปุ่มหน้าและ "หน้า X จาก Y" — ซ่อนตัวเองเมื่อมีหน้าเดียว (`if (pages <= 1) return null;`)

### ง. ตารางไล่โค้ด — กรองได้ 23 คน (ทั้งหมด 928), per = 10
| page (ภายใน) | slice | แถวที่ได้ | shown = min((page+1)×10, 23) | ข้อความ |
|---|---|---|---|---|
| 0 | (0, 10) | 10 แถว | min(10, 23) = 10 | แสดง 10 จาก 23 คน (นักศึกษาทั้งหมด 928 คน) |
| 1 | (10, 20) | 10 แถว | min(20, 23) = 20 | แสดง 20 จาก 23 คน … |
| 2 | (20, 30) | 3 แถว | min(30, 23) = 23 | แสดง 23 จาก 23 คน … |
ปุ่มหน้าที่ผู้ใช้เห็นเป็น 1, 2, 3 (`n + 1`) — ข้างในเริ่มนับที่ 0

### จ. กรณีขอบ
- ไม่มีแถวเลย → `pages = 0` (แบบ ③) หรือ 1 (แบบ ⑤ ใช้ `Math.max(1, …)`) · ตารางขึ้นข้อความ "ไม่พบ…" แยก
- หน้าเยอะกว่า 7 → `pageNumbers` ย่อเป็น `…` และมีช่องพิมพ์เลขหน้า (`PageJump`) กด Enter ถึงกระโดด
- "เลือกทั้งหมด" ในหน้าข้อมูลนักศึกษาเลือก **ทุกคนที่ผ่านตัวกรอง ข้ามทุกหน้า** (`toggleAllFiltered` ใช้ `filtered` ไม่ใช่ `pageRows`) — ข้อจำกัดที่ต้องบอก

### ฉ. ถ้าเปลี่ยนบรรทัดนี้
| เปลี่ยน | ผล |
|---|---|
| ② ใช้ `Math.floor` | 23 แถวได้ 2 หน้า — 3 คนสุดท้ายหายจากการแสดงผล |
| ④ ใช้ `(page + 1) * per` ไม่มี `Math.min` | หน้าสุดท้ายเขียน "แสดง 30 จาก 23" |
| ลบ ③ | กรองตอนอยู่หน้า 7 → ตารางว่าง ผู้ใช้นึกว่าไม่มีข้อมูล |

### ช. คำถามกรรมการ
1. **ทำไมแบ่งหน้าฝั่งหน้าเว็บ ไม่ใช่ฝั่ง backend?** — *ข้อมูลหลักร้อยถึงพันคน เครื่องรับไหว และกรอง/ค้นหาได้ทันทีไม่ต้องรอ server · ถ้าเป็นหมื่นคนต้องย้ายไปแบ่งหน้าที่ backend (ส่ง page/limit ไปใน query)*
2. **`slice` เกินท้ายลิสต์ error ไหม?** — *ไม่ ได้เท่าที่มี — จึงไม่ต้องเขียนเงื่อนไขหน้าสุดท้ายแยก*
3. **ทำไม `usePagedList` รีเซ็ตตอนวาดจอแทน `useEffect`?** — *`useEffect` ทำงานหลังวาดจอ ผู้ใช้เห็นหน้าว่างแวบหนึ่งก่อนเด้งกลับหน้า 1 · ตั้ง state ระหว่างวาด React วาดซ้ำทันทีก่อนแสดงผล*

# 12. รวมแจ้งเตือนหลายแหล่ง + กุญแจ (key) ของแจ้งเตือน

### ก. ปัญหา
แจ้งเตือนมี 3 แหล่ง รูปแบบไม่เหมือนกัน: (1) ตาราง `notifications` ของนักศึกษา (2) alert สดของเจ้าหน้าที่/ผู้บริหาร (`/dashboard/alerts`) คำนวณทุกครั้ง ไม่เก็บ DB (3) ประกาศ (`/news`) — และต้องจำว่าอันไหน "อ่านแล้ว/ปัดทิ้งแล้ว" โดยไม่ให้ของใหม่ถูกซ่อนไปด้วย

### ข. วิธีคิด
```
ดึงพร้อมกัน 3 แหล่ง (แหล่งไหนล้มให้เป็นรายการว่าง ไม่ทำให้กระดิ่งว่างทั้งอัน)
แปลงทุกแหล่งเป็นรูปเดียว { key, tone, icon, page, title, sub, at }
    key ต้อง "คงที่" สำหรับเรื่องเดิม และ "เปลี่ยน" เมื่อเป็นเรื่องใหม่

ตัดอันที่ผู้ใช้ปัดทิ้งแล้ว (เทียบ key กับรายการที่จำไว้ใน localStorage)
นับยังไม่อ่าน: ถ้ามี is_read จาก server ใช้อันนั้น ไม่งั้นดูรายการ key ที่อ่านแล้วใน localStorage
เด้ง popup เฉพาะที่ยังไม่อ่านและยังไม่เคยเด้งใน session นี้ ไม่เกิน 3 อัน
ทำซ้ำทุก 30 วินาที และทุกครั้งที่เปลี่ยนหน้า
```

### ค. โค้ดจริง
`frontend/src/design/notifications.js`

```js
export function fromServer(rows = []) {
  return rows.map((n) => {
    const style = SERVER_TYPES[n.type] || FALLBACK_TYPE;                          // ①
    const [mainLine, ...subLines] = n.message.split("\n");                        // ②
    return { ...style, key: `notif:${n.notification_id}`, title: mainLine,
             sub: subLines.join(" ") || undefined, at: n.created_at, is_read: n.is_read };
  });
}
export function fromAlerts(alerts = [], role = 'officer') {
  return alerts.map((a) => ({
    key: `alert:${a.key}:${a.count ?? a.detail ?? ''}`,                            // ③
    tone: a.tone, icon: a.icon,
    page: role === 'executive' ? 'dashboard' : (ALERT_PAGES[a.type] || 'dashboard'),
    title: a.title, sub: a.detail, at: null, live: true,
  }));
}
export function countUnread(items, read = []) {
  return items.filter((n) => n.is_read === undefined ? !read.includes(n.key) : !n.is_read).length; // ④
}
```

### จ. กรณีขอบ
- login ครั้งแรกทุกอย่าง "ยังไม่อ่าน" → เด้งได้สูงสุด `MAX_TOASTS = 3` (2 อัน + การ์ด "มีแจ้งเตือนอีก N รายการ") แล้วจำว่าเด้งแล้วทุกตัวใน sessionStorage (ปิดแท็บแล้วล้าง)
- กดแจ้งเตือนแล้วพาไปหน้าที่บทบาทนี้เข้าไม่ได้ → `openNotifItem` ตรวจ `ROLE_PAGES[role]` ก่อน (เคยพาเจ้าหน้าที่ไปหน้าประกาศของนักศึกษา เจอ "ไม่พบหน้า")
- ประกาศที่ตัวเองโพสต์ ไม่แจ้งตัวเอง (`buildNotifications` ตัดด้วย `posted_by !== userId` **ก่อน** ตัดเหลือ 5 อัน)
- localStorage เสีย/ถูกแก้ → `try/catch` คืนรายการว่าง (ถือว่ายังไม่เคยอ่าน) ดีกว่าหน้าพัง
- เก็บกุญแจไว้ไม่เกิน 200/300 อันล่าสุด (`slice(-200)`) ไม่ให้ localStorage โตไม่จำกัด

### ฉ. ถ้าเปลี่ยนบรรทัดนี้
| เปลี่ยน | ผล |
|---|---|
| ③ ใช้ `alert:${a.key}` (ไม่มีตัวเลข) | ปัดทิ้งครั้งเดียว ซ่อนถาวร — ค้างตรวจเพิ่มเป็น 50 ใบ เจ้าหน้าที่ไม่รู้ |
| ลบ ⑥ | เปลี่ยนหน้าเร็ว ๆ ผลของคำขอเก่ามาทับ — กระดิ่งแสดงข้อมูลผิดบทบาท/ผิดเวลา |
| ⑤ ไม่มี `.catch` | ผู้ช่วยตรวจสอบไม่มีสิทธิ์ `/dashboard/alerts` (ถ้าเผลอเรียก) → ทั้งกระดิ่งว่าง |

### ช. คำถามกรรมการ
1. **ทำไม alert ของเจ้าหน้าที่ไม่เก็บลงตาราง?** — *เป็น "สถานะตอนนี้" (เหลือกี่วัน ค้างกี่ใบ) ไม่ใช่เหตุการณ์ — เก็บแล้วต้องมีตัวตั้งเวลาอัปเดต และจะมีแจ้งเตือนเก่าที่ไม่จริงค้างอยู่ · คำนวณสดถูกเสมอ (`dashboard.service.js → buildAlerts`)*
2. **ทำไมแจ้งเตือนนักศึกษาต้องมีตาราง?** — *"เจ้าหน้าที่เปิดสิทธิ์ให้แล้ว" ไม่มีข้อมูลอื่นให้ประกอบย้อนหลังได้ (ไม่มีเวลาที่กดเก็บไว้ที่ไหน) และสถานะอ่านแล้วต้องตามผู้ใช้ข้ามเครื่อง จึงเก็บ `is_read` ที่ server*
3. **polling ทุก 30 วินาที เปลืองไหม มีทางที่ดีกว่าไหม?** — *สำหรับผู้ใช้หลักสิบคนพร้อมกันถือว่าน้อย (3 คำขอเล็ก ๆ ต่อ 30 วินาที) · ทางที่ดีกว่าคือ server ส่งเอง (WebSocket/Server-Sent Events) แต่เพิ่มความซับซ้อนมาก ไม่คุ้มกับขนาดระบบนี้*

## แบบฝึกท้ายบท (เฉลยอยู่ท้ายไฟล์)
**คำถามเช็คความเข้าใจ**
1. ใน rate limit ชั้นรหัสผู้ใช้ ครั้งที่ 11 ภายใน 15 นาทีได้ status อะไร และ `bucket.count` ตอนนั้นเป็นเท่าไร
2. นักศึกษารอบ 1 ปิดแล้ว ใบรอตรวจ — `findSubmittableRound` คืนอะไร เพราะอะไร
3. ไฟล์ที่ขึ้นต้นด้วยไบต์ `25 50 44 46 2D` แต่ชื่อ `รูป.png` — `detectFileType` คืนอะไร และ `serveFile` จะส่ง Content-Type อะไร

**แบบฝึกแก้โค้ด**
ให้ "ผ่านภายในปีแรก" ไม่นับวิชาที่ผ่านในรอบที่ 3 (นับแค่รอบ 1–2) — บอกไฟล์ ฟังก์ชัน และวิธีพิสูจน์

### เฉลย
1. **429** · `count` = 10 (ไม่เพิ่มแล้ว เพราะออกจากฟังก์ชันตรงด่าน ⑥ ก่อนบรรทัด `count += 1`)
2. **`null`** — ขั้น 2 ได้รอบ 1 แต่ขั้น 3 ใบเป็น pending ไม่ใช่ rejected → นักศึกษาส่ง/แก้หลังปิดรอบไม่ได้ ต้องรอเจ้าหน้าที่ตรวจ
3. **`"pdf"`** (ดูเนื้อไฟล์ ไม่ดูชื่อ) · `serveFile` อ่าน `file_type = "pdf"` → `application/pdf` (ด่าน multer ต้องผ่านก่อนด้วย — ถ้าเบราว์เซอร์บอกว่าเป็น `image/png` ก็ผ่านด่านแรกได้)
4. **แบบฝึกแก้โค้ด:** `dashboard.service.js` → ในลูป `for (const round of rounds)` ของ `buildYearSummary` **และ** `buildFirstYearList` ครอบการเรียก `addConfirmedRealPasses(passedByStudent, results)` ด้วย `if (round.attempt_number <= 2) { ... }` (ต้องแก้ทั้งสองฟังก์ชันให้การ์ดกับไฟล์ตรงกัน) · พิสูจน์: `ONLY=phase24 npm run test:clean` — S4 (ผ่านรอบ 3) จะหลุดจากผ่านภายในปีแรก ตัวเลขเปลี่ยนจาก 4/5 เป็น 3/5 เทสจะ fail ตรงข้อนั้นซึ่งยืนยันว่าแก้ถูกจุด
