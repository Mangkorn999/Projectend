# 12 — ซ้อมสอบปากเปล่า (คำถามต่อเนื่องแบบกรรมการจริง)

กรรมการจริงไม่ถามข้อเดียวจบ — ถามข้อเปิด แล้ว **"ขุดต่อ"** จากคำตอบของเรา 3–4 ชั้น จนเจอจุดที่เราไม่รู้
ไฟล์นี้มี 5 ชุด ชุดละ 1 คำถามเปิด + 3–4 คำถามขุดต่อ แต่ละข้อมี:
- **คำตอบระดับ A** — พูดได้ใน 45–90 วินาที มีครบ: ปัญหา → วิธี → เหตุผลที่เลือก → ข้อจำกัด → ชี้โค้ด
- **คำตอบ B+ ขาดอะไร** — สิ่งที่คนส่วนใหญ่ตอบแล้วยังไม่ถึง A
- **ชี้โค้ด** — ไฟล์/ฟังก์ชันที่ควรเปิดให้กรรมการดูขณะตอบ

## วิธีซ้อม
1. ให้เพื่อน (หรือแก้ม) อ่านคำถามทีละข้อ **ห้ามดูคำตอบ** ตอบออกเสียง จับเวลา
2. เทียบกับคำตอบ A — ขาดชิ้นไหนจาก 5 ชิ้น (ปัญหา/วิธี/เหตุผล/ข้อจำกัด/โค้ด) จดไว้
3. ซ้อมเปิดไฟล์ใน VS Code ระหว่างพูด (`Ctrl+P` พิมพ์ชื่อไฟล์ → `Ctrl+F` ชื่อฟังก์ชัน) — ต้องเปิดเจอภายใน 10 วินาที
4. ทำซ้ำชุดที่ได้ต่ำกว่า A ในวันถัดไป

## เกณฑ์ให้คะแนนตัวเอง
| ระดับ | ลักษณะคำตอบ |
|---|---|
| **A** | ตอบตรงคำถาม + บอกเหตุผลที่เลือกวิธีนี้เทียบกับทางเลือกอื่น + ยอมรับข้อจำกัดเอง + เปิดโค้ดชี้จุดได้ทันที + ยกตัวอย่างตัวเลข/สถานการณ์จริง (เช่น เทส/บั๊กที่เจอ) |
| **B+** | ตอบถูก อธิบายวิธีได้ แต่ขาด "ทำไม" หรือขาดข้อจำกัด หรือหาโค้ดช้า |
| **B** | ตอบถูกแบบท่องจำ ขุดต่อ 1 ชั้นแล้วติด |
| **C+ ลงไป** | ตอบผิด หรือเดา หรืออธิบายสิ่งที่โค้ดไม่ได้ทำ |

> **ถ้าไม่รู้จริง:** "ส่วนนี้ผมยังไม่ได้ทำ/ไม่แน่ใจ แต่ถ้าจะทำ ผมจะเริ่มที่ไฟล์ … เพราะ …" — ได้คะแนนกว่าเดา (ดู `06` ท้ายไฟล์)

# ชุดที่ 1 — โครงสร้างระบบและเส้นทางของข้อมูล

### 1.1 (เปิด) "นักศึกษากดส่งผลสอบ อธิบายตั้งแต่กดปุ่มจนข้อมูลอยู่ในฐานข้อมูล"
**คำตอบ A:**
"เริ่มที่หน้า `examFormReal.jsx` ฟังก์ชัน `submit` — ถ้าเป็นใบใหม่ ส่ง `POST /api/exam-results` ก่อนเพื่อได้เลขใบ แล้วอัปโหลดไฟล์ทีละไฟล์ · ถ้าเป็นใบที่ถูกตีกลับ จัดการไฟล์ก่อนแล้วค่อยส่งผล เพราะส่งผลแล้วใบกลับเป็นรอตรวจ ถ้ารอบปิดแล้วจะแนบไฟล์ไม่ได้
คำขอผ่าน `apiFetch` ใน `api.js` ซึ่งใส่ `credentials: 'include'` ให้เบราว์เซอร์แนบ cookie
ฝั่ง backend `app.js` ผ่าน helmet, cors, อ่าน JSON, อ่าน cookie แล้วเข้า router → `authenticate` ตรวจ token และ **ตรวจกับฐานข้อมูลว่าผู้ใช้ยังมีอยู่** → `requireRole("student")` → `create`
ใน `create` ตรวจ: มีสิทธิ์กรอก, หารอบของรุ่นตัวเองด้วย `findSubmittableRound`, ใบยืนยันแล้วห้ามแก้, ตรวจทุกรายการว่าอยู่ในรอบ เป็น true/false จริง ไม่ซ้ำ ครบ, แล้วบังคับวิชาที่เคยผ่านเป็นผ่าน (carry-forward)
สุดท้าย repository บันทึกใบ + ผลรายวิชาในคำสั่งเดียว (ใบใหม่) หรือใน `$transaction` (ใบเดิม) ตอบ `{ success: true, data }`
ทุกขั้นที่ไม่ผ่านจะ `throw` ไปที่ `errorHandler` ตัวเดียว ตอบข้อความไทยพร้อม status code"
**B+ ขาดอะไร:** เล่าครบแต่ไม่บอกว่า "ทำไม" ต้องตรวจซ้ำที่ backend (client เชื่อไม่ได้) · ไม่รู้ว่าลำดับใบใหม่กับใบเดิมต่างกัน
**ชี้โค้ด:** `examFormReal.jsx → submit` · `examResults.routes.js` · `examResults.controller.js → create`

### 1.2 (ขุด) "ทำไมต้องแบ่ง routes / controller / repository ไม่เขียนรวมไฟล์เดียว?"
**คำตอบ A:** "แต่ละชั้นมีเหตุผลให้เปลี่ยนต่างกัน — route เปลี่ยนเมื่อสิทธิ์/URL เปลี่ยน, controller เปลี่ยนเมื่อกฎธุรกิจเปลี่ยน, repository เปลี่ยนเมื่อวิธีเก็บข้อมูลเปลี่ยน · ตัวอย่างจริง: บั๊ก B1 แก้ที่ repository (`findPassedSubjectIds`) บรรทัดเดียว controller ไม่ต้องแตะ · และกฎที่ใช้หลายที่แยกเป็น service เช่น `findSubmittableRound` ใช้ทั้งตอนส่งผล ตอนเปิดหน้ากรอก และตอนแนบไฟล์ — ถ้าเขียนซ้ำ 3 ที่จะเพี้ยนกัน (ซึ่ง security review เจอมาแล้วกับการแนบไฟล์)"
**B+ ขาดอะไร:** ตอบแค่ "อ่านง่าย แก้ง่าย" ไม่มีตัวอย่างจริง
**ชี้โค้ด:** `examResults.service.js` (คอมเมนต์บอกว่าใช้ 2 ที่ + certificates ใช้อีกที่)

### 1.3 (ขุด) "ถ้าหน้าเว็บขึ้นข้อความ 'ระบบขัดข้องชั่วคราว' จะหาสาเหตุยังไง?"
**คำตอบ A:** "ข้อความนั้นคือ 500 (มาจาก `fallbackMessage` หรือ `errorHandler` ที่ซ่อนข้อความดิบ) — ไล่ 4 ชั้น: (1) F12 → Network ดู request สีแดงและ status (2) terminal ของ backend — `errorHandler` พิมพ์ `[ERROR] method path: ข้อความ` (3) ยิง curl ตรงเพื่อแยกว่าเป็นที่หน้าเว็บหรือ backend (4) `npx prisma studio` ดูข้อมูลจริง · และระบบออกแบบให้ข้อผิดพลาดจากผู้ใช้เป็น 4xx เสมอ เช่น ส่ง id ใหญ่เกินคอลัมน์เคยเป็น 500 ตอนนี้แปลงเป็น 400 แล้ว"
**B+ ขาดอะไร:** บอกแค่ "ดู console" ไม่เป็นลำดับ · ไม่รู้ว่า 500 ถูกซ่อนข้อความดิบเพราะอะไร (ไม่ให้เผยชื่อตาราง)
**ชี้โค้ด:** `middlewares/errorHandler.js` (ตัวแปร `isNumberTooBig`, บรรทัด `statusCode === 500 && NODE_ENV !== "development"`)

### 1.4 (ขุด) "ถ้ามีผู้ใช้ 200 คนส่งพร้อมกันตอนใกล้ปิดรอบ ระบบรับไหวไหม จุดไหนจะช้าก่อน?"
**คำตอบ A:** "ยังไม่ได้ทำ load test จริง — ประเมินจากโค้ด: ใช้ PrismaClient ตัวเดียวทั้งระบบ (`config/db.js`) จึงมี connection pool ชุดเดียวไม่ท่วม Postgres · ทุก request มี query เพิ่ม 1 ครั้งใน `authenticate` · การส่งผล 1 ครั้งมี query ราว 6–8 ครั้ง ส่วนใหญ่ค้นด้วย primary key/unique/index (`@@unique([student_id, round_id])`, `@@index([round_id])`) · จุดที่จะช้าก่อนคือหน้าข้อมูลนักศึกษาที่ดึงทั้งก้อนแล้วกรองที่หน้าเว็บ และสถิติที่วนทุกใบทุกรอบ — ถ้าข้อมูลโตเป็นหมื่นต้องแบ่งหน้าที่ backend และเก็บสถิติไว้ล่วงหน้า"
**B+ ขาดอะไร:** ตอบ "ไหว" โดยไม่มีเหตุผล หรือไม่ยอมรับว่ายังไม่ได้วัด
**ชี้โค้ด:** `config/db.js` (คอมเมนต์เรื่อง pool), `schema.prisma` (`@@index`)

# ชุดที่ 2 — ความปลอดภัย

### 2.1 (เปิด) "ระบบกันไม่ให้นักศึกษาแอบทำงานของเจ้าหน้าที่ได้ยังไง?"
**คำตอบ A:** "กันที่ backend ทุก endpoint ด้วยสองด่านเรียงกัน: `authenticate` ตอบว่าเป็นใคร และ `requireRole(...)` ตอบว่ามีสิทธิ์ไหม · role อ่านจาก `req.user` ซึ่ง `authenticate` สร้างจากแถวในฐานข้อมูล ไม่ใช่จาก body ที่ client ส่ง และไม่ใช่จากค่าที่ฝังใน token — เปลี่ยน role แล้วมีผลทันที · ฝั่งหน้าเว็บมี `ROLE_PAGES` ซ่อนเมนู แต่นั่นเป็นแค่ UX — ยิง API ตรงก็ได้ 403 · มีเทสยิงทุก endpoint ด้วยทุกบทบาท (`phase26` หัวข้อผู้ช่วยตรวจสอบ/ผู้บริหาร ได้ 403 ทุกข้อ)
ระดับข้อมูลก็กัน เช่น นักศึกษาเปิดไฟล์ได้เฉพาะของตัวเอง (`serveFile` เช็ค `isOwner`) และแจ้งเตือนกรองด้วย `student_id` เสมอ"
**B+ ขาดอะไร:** ไม่แยก "สิทธิ์ระดับ endpoint" กับ "สิทธิ์ระดับข้อมูล (เป็นเจ้าของไหม)"
**ชี้โค้ด:** `middlewares/auth.js` (สร้าง `req.user`), `middlewares/requireRole.js`, `certificates.controller.js → serveFile`

### 2.2 (ขุด) "ถ้ามีคนขโมย cookie ไปได้ล่ะ?"
**คำตอบ A:** "cookie เป็น httpOnly สคริปต์ในหน้าเว็บอ่านไม่ได้ ลดโอกาสโดน XSS ขโมย · `sameSite: lax` กันเว็บอื่นยิงคำขอที่แนบ cookie · ถ้าขโมยได้จริง (เช่น ได้เครื่องไป) token ใช้ได้จนหมดอายุ 1 วัน — JWT ไม่มีสถานะที่ server · ที่ทำได้ตอนนี้: เจ้าหน้าที่ถอนสิทธิ์บัญชีนั้น `authenticate` เช็ค DB ทุกครั้ง จะตัดทันที · ข้อจำกัด: ยกเลิก token เฉพาะใบโดยไม่ถอนสิทธิ์ทั้งบัญชีทำไม่ได้ ต้องเพิ่มตาราง session หรือรายการ token ที่ยกเลิก · และตอนขึ้น HTTPS ต้องตั้ง `COOKIE_SECURE=true`"
**B+ ขาดอะไร:** ไม่รู้ข้อจำกัดของ JWT หรือบอกว่า "logout แล้วปลอดภัย" (ผิด — logout ลบแค่ cookie ในเบราว์เซอร์)
**ชี้โค้ด:** `authController.js → TOKEN_COOKIE_OPTIONS`, `logout`

### 2.3 (ขุด) "ไฟล์ที่นักศึกษาอัปโหลด อันตรายไหม ตรวจยังไง?"
**คำตอบ A:** "ตรวจ 4 ชั้น: (1) multer รับเฉพาะชนิดที่เบราว์เซอร์บอกว่าเป็น PDF/JPG/PNG และ ≤ 10 MB (2) อ่าน 8 ไบต์แรกของไฟล์เทียบ magic bytes — เปลี่ยนนามสกุลหลอกไม่ได้ (3) ตั้งชื่อไฟล์บนดิสก์เอง (เวลา+เลขสุ่ม) ไม่ใช้ชื่อจากผู้ใช้ กัน path traversal (4) เปิดไฟล์ผ่าน endpoint ที่ตรวจสิทธิ์ ไม่ได้เปิดโฟลเดอร์ให้เข้าตรง และส่ง Content-Type ตามชนิดจริง + helmet ใส่ nosniff · ไฟล์ที่ถูกปฏิเสธถูกลบจากดิสก์ทุกทาง (ตัวแปร `saved`) · ข้อจำกัด: ไม่ได้สแกนไวรัส/ไม่ได้ตรวจเนื้อใน PDF ว่ามีสคริปต์"
**B+ ขาดอะไร:** บอกแค่ "เช็คนามสกุล" (ซึ่งไม่ปลอดภัย) หรือไม่รู้เรื่องลบไฟล์ที่ถูกปฏิเสธ
**ชี้โค้ด:** `middlewares/upload.js` (`fileFilter`, `filename`), `certificates.controller.js → detectFileType`, `upload`

### 2.4 (ขุด) "นักศึกษาแนบไฟล์ 10 ไฟล์พร้อมกันเพื่อทะลุขีดจำกัด 5 ไฟล์ได้ไหม?"
**คำตอบ A:** "เคยได้ — security review เขียนเทสยิงพร้อมกัน 10 คำขอ ได้ 6 ไฟล์ เพราะทุกคำขอนับได้ 4 พร้อมกันจึงผ่านด่านนับ (check-then-act) · แก้ด้วยการนับซ้ำ **หลัง** บันทึก ถ้าเกินคำขอนั้นถอนแถวของตัวเองออก ผลสุดท้ายไม่เกิน 5 เสมอ — เป็นหลักการเดียวกับ optimistic guard ตอนตรวจใบ คือตรวจตอนเขียน ไม่ใช่เชื่อผลตรวจก่อนเขียน"
**B+ ขาดอะไร:** ตอบว่า "มี if เช็คจำนวนอยู่แล้ว" โดยไม่เห็นปัญหาการแข่งกัน
**ชี้โค้ด:** `certificates.controller.js → upload` (ตัวแปร `countAfterSave`, `problemAfterSave`), `tests/smoke-phase27-security.mjs`

# ชุดที่ 3 — กฎธุรกิจและอัลกอริทึม

### 3.1 (เปิด) "รอบ 2 นักศึกษากรอกเฉพาะวิชาที่ยังไม่ผ่าน ระบบรู้ได้ยังไง และกันแก้วิชาที่ผ่านแล้วยังไง?"
**คำตอบ A:** "ก่อนบันทึก `create` เรียก `findPassedSubjectIds` หาวิชาที่คนนี้ผ่าน **จริง** ในใบของรอบอื่นที่ไม่ถูกตีกลับ (ตัดใบของรอบนี้ออก) → วิชาที่ต้องตอบ = วิชาของรอบ ลบวิชาที่เคยผ่าน → ตอนสร้างผลที่จะบันทึก วนทุกวิชาของรอบ ถ้าเคยผ่าน บังคับเป็นผ่าน + ติดธง `carried_forward` **ไม่สนค่าที่ client ส่งมา** · ตัวอย่างจากเทส `phase24`: ส่ง [ตก, ผ่าน, ผ่าน] โดยวิชาแรกเคยผ่าน → บันทึก [ผ่าน(ยกมา), ผ่าน, ผ่าน] · ธงยกมาทำให้สถิติรายวิชานับเฉพาะคนสอบจริง"
**B+ ขาดอะไร:** ไม่รู้ว่าใบรอตรวจนับเป็นผ่าน (และเพราะอะไร) หรือไม่รู้เรื่องตัดใบของรอบนี้ออก
**ชี้โค้ด:** `examResults.controller.js → create` (`passedIds`, `mustAnswer`, `finalResults`), `examResults.repository.js → findPassedSubjectIds`

### 3.2 (ขุด) "ทำไมใบรอตรวจนับเป็นผ่าน ไม่กลัวผิดเหรอ?"
**คำตอบ A:** "เป็นการแลกเปลี่ยน: ถ้าไม่นับ เจ้าหน้าที่เปิดรอบ 2 ก่อนตรวจรอบ 1 ครบ นักศึกษาต้องกรอกวิชาที่เพิ่งผ่านซ้ำ · แต่การนับนี้ทำให้เกิด **บั๊ก B1** ที่เราเจอจากแผนทดสอบ: ใบรอบ 1 รอตรวจ → รอบ 2 ยกวิชา A มา → แล้วใบรอบ 1 ถูกตีกลับ → แถว A ที่ยกมาในใบรอบ 2 ยังเป็นผ่าน ไปล็อกรอบ 3 และทำให้ 'ผ่านภายในปีแรก' สูงเกินจริง · แก้โดยกฎเดียว **'ไม่นับแถวที่ยกมา' (`carried_forward: false`)** ใน 3 ที่ — ถ้าใบต้นทางดี แถวจริงในใบต้นทางถูกนับอยู่แล้ว ไม่เสียอะไร · มีเทส `phase25`, `phase26` คุม"
**B+ ขาดอะไร:** เล่า B1 ไม่ได้ หรือบอกแก้แค่ที่เดียว
**ชี้โค้ด:** `findPassedSubjectIds` (คอมเมนต์ B1), `dashboard.repository.js → findEligibleWithPassedSubjects`, `dashboard.service.js → addConfirmedRealPasses`

### 3.3 (ขุด) "ถ้าเจ้าหน้าที่ตีกลับใบหลังปิดรอบไปแล้ว นักศึกษาทำยังไง?"
**คำตอบ A:** "แก้ส่งใหม่ได้ (ตัดสินใจกับเจ้าของงาน 1 ต.ค.) ผ่าน `findSubmittableRound`: ขั้น 1 ถ้ามีรอบเปิดของรุ่นใช้รอบนั้นก่อน · ขั้น 2 ไม่มี → ดูรอบล่าสุดที่เริ่มแล้ว · ขั้น 3 ใบในรอบนั้นต้อง **ถูกตีกลับ** ถึงแก้ได้ — คนไม่เคยส่ง/ใบรอตรวจ ยังส่งหลังปิดไม่ได้ · ใช้ฟังก์ชันเดียวกัน 3 ที่ (ส่งผล, หน้ากรอกผ่าน `can_fix_rejected`, แนบไฟล์) ให้ตัดสินตรงกัน · ไม่ย้อนรอบเก่ากว่ารอบล่าสุด เพราะผลที่ยกไปรอบหลังจะเพี้ยน · ข้อจำกัด: ยังไม่มีเส้นตายหลังปิดรอบ ถ้าต้องการเพิ่มเงื่อนไขจำนวนวันในขั้น 2"
**B+ ขาดอะไร:** ไม่รู้ว่าใบรอตรวจหลังปิดรอบแก้ไม่ได้ หรือไม่รู้ว่าต้องตรงกัน 3 ที่
**ชี้โค้ด:** `examResults.service.js → findSubmittableRound`, `rounds.controller.js → getActive` (`can_fix_rejected`)

### 3.4 (ขุด) "เจ้าหน้าที่สองคนกดยืนยันกับตีกลับใบเดียวกันพร้อมกัน ผลคืออะไร?"
**คำตอบ A:** "คนแรกได้ คนที่สองได้ 409 'ใบนี้ถูกตรวจไปแล้ว' — เพราะเงื่อนไข `staff_status = pending` อยู่ใน `UPDATE … WHERE` (`updateMany`) ฐานข้อมูลทำตรวจ+เขียนเป็นขั้นเดียว คนแรก `count = 1` คนที่สอง `count = 0` · ด่านเช็คก่อนหน้า (`existing.staff_status !== PENDING`) มีไว้ให้ข้อความชัดในกรณีทั่วไป แต่กันกรณีพร้อมกันเป๊ะไม่ได้ (check-then-act) · เรียกว่า optimistic concurrency control · มีเทสยิงพร้อมกันจริง (`phase15`, `phase25`)"
**B+ ขาดอะไร:** ตอบว่า "มี if เช็คสถานะ" โดยไม่เห็นว่า if อย่างเดียวไม่พอ
**ชี้โค้ด:** `examResults.controller.js → reviewExamResult`, `examResults.repository.js → updateStaffStatusIfPending`

# ชุดที่ 4 — สถิติและการวิเคราะห์ข้อมูล

### 4.1 (เปิด) "ร้อยละผ่านครั้งแรกกับผ่านภายในปีแรกคิดยังไง ต่างกันยังไง?"
**คำตอบ A:** "ตัวหารเหมือนกันคือ **นักศึกษาทั้งรุ่น** (รวมบัญชีที่นำเข้าแล้วแต่ยังไม่เข้าระบบ นับเป็นยังไม่กรอก) และนับเฉพาะใบที่เจ้าหน้าที่ยืนยันแล้ว · ผ่านครั้งแรก = ใบรอบที่ 1 ที่ผ่านครบทุกวิชาของรอบ (`countFullyPassed`) · ผ่านภายในปีแรก = รวมผลจริงทุกรอบของปีนั้นรายคน (`Map` ของ `Set`) แล้วดูว่าครอบคลุมวิชาที่ต้องผ่านครบไหม (`hasPassedAll`) · ตัวอย่างเทส: รุ่น 5 คน ผ่านครั้งแรก 2 (40.00%) ภายในปีแรก 4 (80.00%) · ไฟล์ส่งออกรายชื่อใช้ฟังก์ชันเดียวกันกับการ์ด จึง ผ่าน + ไม่ผ่าน = ทั้งรุ่น เสมอ (เทสเทียบตรง ๆ)"

### 4.2 (ขุด) "ทำไมไม่นับใบรอตรวจ ตัวเลขจะต่ำกว่าความจริงไหม?"

### 4.3 (ขุด) "อัตราผ่านรายวิชา ถ้าไม่มีใครสอบวิชานั้นเลยในรอบ ขึ้นเท่าไร?"
**คำตอบ A:** "ขึ้นขีด '—' (`rate: null`) ไม่ใช่ 0% และไม่ใช่ 100% · 0% แปลว่าสอบแล้วตกหมด ซึ่งคนละความหมายกับไม่มีข้อมูล · เกิดได้จริงในรอบ 2–3 ที่ทุกคนยกวิชานั้นมา (แถว `carried_forward` ไม่นับเป็นคนสอบ) · และค่าเฉลี่ยข้ามวิชาที่เป็น null ไม่งั้นค่าเฉลี่ยถูกลากลง · ตาราง 'ผลรายวิชารอบแรก' ใช้ `sat: 0` ให้หน้าจอขึ้นขีดเหมือนกัน"

### 4.4 (ขุด) "ตารางผลรายวิชารอบแรก 3 ช่อง ผ่าน/ไม่ผ่าน/ยังไม่ส่ง รวมได้ 100.00% พอดีทุกแถวได้ยังไง ทั้งที่ปัดทศนิยม?"

## คำถามสั้นที่มักโดนแทรก (ตอบใน 1–2 ประโยค)
| คำถาม | คำตอบสั้น |
|---|---|
| 401 กับ 403 ต่างกัน? | 401 = ยังไม่รู้ว่าเป็นใคร (ไม่มี/หมดอายุ token) · 403 = รู้แล้วแต่ไม่มีสิทธิ์ |

| "ผู้ช่วยตรวจสอบ" ทำอะไรได้? | ตรวจ/ยืนยัน/ตีกลับในคิวเดียวกับเจ้าหน้าที่ เปิดไฟล์ได้ · ถอนการยืนยัน จัดการรอบ/ผู้ใช้ ส่งออก ไม่ได้ (เทส PH26-17) — บทบาท `reviewer` ในฐานข้อมูล ชื่อบนจอเปลี่ยนเป็น "ผู้ช่วยตรวจสอบ" แล้ว |

| ทดสอบไปกี่ข้อ? | API 21 ไฟล์ (รายงาน 1 ต.ค.: 20 ไฟล์ 820 ข้อตรวจผ่านหมด + ไฟล์ความปลอดภัย `phase27` ที่เพิ่มทีหลัง) + เทสผ่านหน้าเว็บจริง 19 หัวข้อ 166 ข้อตรวจ — **ก่อนสอบรันใหม่แล้วใช้ตัวเลขล่าสุด** |
| ทำไมไม่ใช้ react-router? | หน้าไม่กี่หน้า คุมสิทธิ์หน้าต่อบทบาทที่เดียว (`ROLE_PAGES`) ด้วย History API เอง ลด dependency |
| ข้อจำกัดใหญ่สุด? | rate limit อยู่ในหน่วยความจำเครื่องเดียว · ยังไม่ขึ้น HTTPS จริง · ยังไม่มีสำรองข้อมูลอัตโนมัติ · ยกเลิก token รายใบไม่ได้ · ไม่มีเทสอัตโนมัติฝั่ง component ของหน้าเว็บ (มีเทสผ่านเบราว์เซอร์แทน) |
