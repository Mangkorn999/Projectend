## A. ภาพรวมและการออกแบบ (1–10)

**1. ทำไมไม่ใช้ PSU One Passport ตามที่ตั้งใจไว้ตอนแรก?**
*ตั้งใจใช้ แต่ขอ credential สำหรับเชื่อมจากศูนย์คอมพิวเตอร์ไม่ได้ จึงออกแบบให้ระบบยืนยันตัวตนเอง: เก็บรหัสเป็น bcrypt hash, ออก JWT เก็บใน httpOnly cookie. ออกแบบให้ถอดเปลี่ยนได้ — เหลือแก้ที่ `login` ที่เดียว ส่วนที่เหลือของระบบอ่านแค่ `req.user` ไม่สนว่าตัวตนมาจากไหน. (ต้องแก้รายงานบท 4 ตาม `docs/report-fixes.md` A1)*
`authController.js → login`

**2. ทำไมแยก frontend/backend ไม่ทำรวมกัน?**
*แยกหน้าที่: backend คุมกฎและข้อมูล frontend คุมการแสดงผล. ข้อดี: ปรับหน้าตาโดยไม่แตะกฎ, ทีม 2 คนทำงานขนานกัน (มังกร backend / แก้ม frontend), ทดสอบ API ได้โดยไม่ต้องมีหน้าจอ. จุดต่อ (contract) = REST + `{success, data}`.*

**3. ทำไมเลือก React / Express / PostgreSQL?**
*React: แบ่ง component ใช้ซ้ำ state เปลี่ยนแล้วจออัปเดตเอง. Express: เรียบง่าย JS ภาษาเดียวกับ frontend. PostgreSQL: ข้อมูลมีความสัมพันธ์ชัดเจนและต้องการความถูกต้อง (transaction, FK, unique) จึงเหมาะกว่าเอกสารแบบ NoSQL.*

**4. อธิบายสถาปัตยกรรมของ backend**
*4 ชั้น routes → controller → (service) → repository. routes จับคู่ URL + ต่อ middleware, controller ตรวจ input/ตัดสินใจ, service คำนวณที่ซับซ้อน, repository คุย Prisma ที่เดียว. ข้อดี: เปลี่ยนวิธีเก็บข้อมูลแก้แค่ repository เปลี่ยนกฎแก้แค่ controller.*
ดู `03` ข้อ 1

**5. ระบบรองรับผู้ใช้กี่คน / scale ได้แค่ไหน?**
*ออกแบบสำหรับใช้ภายในคณะ (รุ่นละ ~150–200 คน, ทดสอบด้วยข้อมูลจำลอง 5 รุ่น 928 คน). จุดที่จะเป็นคอขวดก่อน: (1) รายชื่อนักศึกษากรองฝั่ง client (ดึงทั้งก้อน) — พอสำหรับหลักพัน (2) rate limit เก็บใน memory — หลายเครื่องต้องใช้ Redis (3) `authenticate` เช็ค DB ทุก request (แลกความถูกต้องของสิทธิ์). มี index บน FK ที่ค้นบ่อยและใช้ PrismaClient ตัวเดียว connection ไม่บวม.*

**6. ระบบทำงานยังไงตั้งแต่นักศึกษากดส่งผลสอบ?**
*ไล่ 8 ขั้นตามที่ซ้อมไว้ใน `01` ข้อ 8.*

**7. ทำไมรอบการกรอกผูกกับ "รุ่น" (academic_year)?**
*เพื่อให้นักศึกษาเห็น/กรอกได้เฉพาะรอบของรุ่นตัวเอง ข้ามรุ่นไม่ได้ตั้งแต่ต้น (หารอบจากปีของนักศึกษาเลย ไม่ได้หารอบเปิดแล้วค่อยเช็คทีหลัง). ข้อดีคือไม่ต้องมีเงื่อนไขกันเพิ่ม.*
`examResults.controller.js → create` (`findActive(student.academic_year)`)

**8. ทำไมแยกสถานะ student_status กับ staff_status?**
*เป็นคนละเรื่อง: student_status = นักศึกษากรอกเสร็จ/ส่งแล้วหรือยัง (draft/submitted), staff_status = เจ้าหน้าที่ตัดสินแล้วหรือยัง (pending/approved/rejected). รวมเป็นสถานะเดียวจะมีผลผสมเยอะและอ่านยาก.*
ดู `02` ข้อ 5.1

**9. ระบบนี้ต่างจากการใช้ Google Form + Excel ตรงไหน?**
*(1) ตรวจสอบสิทธิ์และบังคับกฎอัตโนมัติ (รอบ/วิชา/ยกผลรอบก่อน) (2) มีขั้นตอนตรวจ-ตีกลับพร้อมเหตุผลและประวัติตรวจย้อนหลัง (3) สถิติรุ่นคำนวณตามกฎเดียวกับที่ส่งสภา อัตโนมัติ (4) ควบคุมว่าใครเห็นอะไร.*

**10. ถ้าจะต่อยอด จะทำอะไรต่อ?**
*(1) ย้ายไป PSU One Passport เมื่อขอ credential ได้ (2) deploy จริง + HTTPS (`COOKIE_SECURE=true`) (3) rate limit ด้วย Redis (4) audit log ละเอียดขึ้น (5) แบ่งหน้ารายชื่อที่ backend เมื่อข้อมูลโต (6) จัดการบัญชีเจ้าหน้าที่ที่ลาออกโดยเก็บประวัติครบ (ดูข้อ 38).*

## B. ฐานข้อมูล (11–20)

**11. อธิบาย ER diagram / ความสัมพันธ์หลัก**
*users 1:0..1 students (เจ้าหน้าที่ไม่มีข้อมูลนักศึกษา) · students 1:M exam_results · exam_results 1:M subject_results และ 1:M certificates และ 1:M review_logs · submission_rounds 1:M exam_results/news. วาดได้ตาม `02` ข้อ 4.*

**12. ทำไมแยก exam_results กับ subject_results?**
*ใบผลสอบ 1 ใบมีหลายวิชา (1:M). ถ้ายัดเป็นคอลัมน์ `subject1..subject8` จะผูกกับจำนวน 8 วิชาตายตัว (แต่รอบหนึ่งเลือกวิชาได้) และสถิติรายวิชาคำนวณลำบาก. แยกตารางทำให้ group by วิชาได้ตรง ๆ.*

**13. ทำไมเก็บไฟล์ PDF บนดิสก์ ไม่เก็บใน DB?**
*ไฟล์ใหญ่ทำให้ DB บวม ช้า สำรองยาก. DB เก็บแค่ `file_path`; ไฟล์เปิดผ่าน endpoint ที่ตรวจสิทธิ์ (เจ้าของ/officer/reviewer) ไม่เปิดเป็น static เสรี.*
`certificates.controller.js → serveFile`

**14. ใช้ index/unique ตรงไหน เพราะอะไร?**
*unique(student_id, round_id) กัน 2 ใบในรอบเดียว (กันที่ DB เพราะเช็คใน controller อย่างเดียวพลาดได้ถ้ากดส่ง 2 ครั้งพร้อมกัน), unique(academic_year, attempt_number) กันรอบซ้ำ, unique(psu_passport_id). index บน FK ที่ค้นบ่อย เช่น `exam_results.round_id`, `subject_results.subject_id` (ตารางใหญ่สุด = คน × 8 วิชา × ทุกรอบ).*

**15. Transaction ใช้ตรงไหน ทำไม?**
*ตอนบันทึกใบผลสอบ + ผลรายวิชา ทั้งหมด (`$transaction`) — ให้เขียนครบหรือไม่เขียนเลย ไม่ให้ใบกับผลวิชาไม่ตรงกันถ้าพังกลางทาง.*
`examResults.repository.js`

**16. ทำไมใช้ Prisma? ป้องกัน SQL injection ยังไง?**
*Prisma ส่งค่าเป็น parameter (ไม่ต่อสตริง SQL) จึงกัน SQL injection; ได้ schema กลางเป็นต้นทางความจริงและ migration. ข้อเสีย: ต้องเรียนรู้ API และบางคำสั่ง (เช่น เงื่อนไขในอัปเดต) ต้องใช้ `updateMany`.*

**17. Migration คืออะไร ทำไมต้องมี?**
*ไฟล์ SQL เรียงตามเวลาที่บันทึกการแก้โครงตาราง — ให้ DB ทุกเครื่องมีโครงเหมือนกันและย้อนดูประวัติได้. ในโปรเจกต์ `prisma migrate dev` ใช้ไม่ได้ (ไม่มีสิทธิ์สร้าง shadow DB) ทีมจึงเขียน migration เองแล้ว `migrate deploy`.*

**18. ถ้าฐานข้อมูลเสียหาย/ข้อมูลหาย?**
*ยังไม่ได้ตั้งระบบสำรองอัตโนมัติ (ข้อจำกัดของงานที่สาธิตในเครื่อง). แผน: `pg_dump` ตั้งเวลาสำรองรายวัน + เก็บโฟลเดอร์ `uploads/` คู่กัน เพราะข้อมูลแยกอยู่สองที่ (DB + ไฟล์).*

**19. ทำไมชื่อคอลัมน์เป็น snake_case?**
*ตรงกับ data dictionary ในรายงาน (บท 3.4) และ convention ของ Postgres; ไม่เปลี่ยนชื่อโดยไม่จำเป็นเพื่อให้รายงานกับระบบตรงกัน.*

**20. `ON DELETE RESTRICT` คืออะไร มีผลอะไร?**
*ห้ามลบแถวแม่ถ้ายังมีแถวลูกชี้อยู่ — กันประวัติกำพร้า. ผลที่ตามมา: ลบบัญชีเจ้าหน้าที่ที่เคยทำงานไม่ได้ (ดูข้อ 38).*

## C. สิทธิ์และความปลอดภัย (21–32)

**21. ระบบกันไม่ให้นักศึกษาทำสิ่งที่เจ้าหน้าที่ทำได้ยังไง?**
*ที่ backend: ทุก endpoint ที่ไม่ public ผ่าน `authenticate` แล้ว `requireRole(...)`; role อ่านจาก `req.user` (สร้างจาก DB) ไม่เชื่อ role ที่ client ส่งมา. frontend ซ่อนเมนูแค่เพื่อ UX.*
`middlewares/auth.js`, `requireRole.js`

**22. ทำไมผู้บริหารดูข้อมูลนักศึกษารายบุคคลไม่ได้? (ต่างจาก Scope เดิมหรือเปล่า)**
*ตัดสินใจตามหลัก data minimization: ผู้บริหารใช้ตัวเลขภาพรวมตัดสินใจ ไม่จำเป็นต้องเห็นข้อมูลส่วนบุคคล จึงให้ `GET /students`, `GET /exam-results` และไฟล์หลักฐานเป็น 403 สำหรับ executive — เหลือ Dashboard + รายงานสรุป. ซึ่งต่างจากร่างแรกในรายงานบท 4.3 ที่ให้ดูรายบุคคลได้ → แก้รายงานตามแล้ว (`docs/report-fixes.md` A3). ถ้าคณะต้องการให้ดูอ่านอย่างเดียวได้ ทำได้ตามขั้นตอนใน `05` ข้อ 9 (เปิดที่ backend + ตารางสิทธิ์หน้า + ปิดการเขียนทุกเส้น).*
⚠️ ก่อนสอบให้ยืนยันกับอาจารย์ว่าเห็นชอบกับการตัดข้อนี้

**23. รหัสผ่านเก็บยังไง? ถ้า DB รั่วเป็นยังไง?**
*เก็บ bcrypt hash (รอบ 10) ไม่มีรหัสจริงใน DB; hash ย้อนกลับไม่ได้ และช้าโดยตั้งใจเพื่อให้เดาเป็นล้านครั้งไม่ไหว. รหัสเริ่มต้นของนักศึกษา = เลขบัตรประชาชน (ตัดสินใจร่วมกับเจ้าของงานเพราะนักศึกษาเข้าถึงได้ง่าย) แต่ก็เก็บเป็น hash และ **ไม่อยู่ในไฟล์ส่งออกใดเลย**.*
ข้อจำกัดที่บอกเอง: รหัสเริ่มต้นที่เดาจากข้อมูลบุคคลได้มีความเสี่ยง — ลดด้วย rate limit และการบังคับเปลี่ยนรหัสสำหรับเจ้าหน้าที่

**24. JWT คืออะไร เก็บที่ไหน ทำไม?**
*ข้อความที่ลงลายเซ็นด้วย `JWT_SECRET` ข้างในมี userId/role/studentId อายุ 1 วัน. เก็บใน httpOnly cookie (JS อ่านไม่ได้ กัน XSS) + `sameSite: lax` (กัน CSRF) + `secure` ตอน HTTPS.*

**25. ถ้ามีคนขโมย token ได้?**
*ใช้ได้จนหมดอายุ (JWT เป็น stateless) แต่ `authenticate` เช็ค DB ทุก request จึงตัดได้ทันทีเมื่อบัญชีถูกถอนสิทธิ์/ลบ. ถ้าต้อง revoke เป็นรายโทเค็นต้องมีตาราง session ซึ่งยังไม่ได้ทำ.*

**26. XSS / CSRF / SQL injection กันยังไง?**
*XSS: token อยู่ใน httpOnly cookie + React escape ข้อความอัตโนมัติ. CSRF: `sameSite=lax` + CORS ระบุ origin เดียว (ไม่ใช้ `*`). SQL injection: Prisma ใช้ parameter. อัปโหลดไฟล์: จำกัดชนิด (PDF/JPG/PNG) และขนาด, **ตรวจชนิดจากไบต์ต้นไฟล์ (magic bytes) ไม่เชื่อนามสกุล**, ตั้งชื่อไฟล์สุ่มเอง ไม่ใช้ชื่อจากผู้ใช้. header มาตรฐานด้วย `helmet` (เช่น nosniff).*

**27. กัน brute-force login ยังไง?**
*rate limit 2 ชั้น: ต่อรหัสผู้ใช้ 10 ครั้ง/15 นาที และต่อ IP 60 ครั้ง/15 นาที, เกิน → 429. เปลี่ยนรหัสผ่านก็มี rate limit (ต้องกรอกรหัสเดิม = เดาได้เหมือนกัน). ข้อความ error ของ login เหมือนกันทุกกรณี กันไล่เดาว่ามีบัญชีไหม.*

**28. ข้อมูลส่วนบุคคลถูกปกป้องยังไง?**
*ให้เห็นเท่าที่จำเป็น: ผู้บริหารเห็นแต่สถิติ; ไฟล์หลักฐานเปิดได้เฉพาะเจ้าของ/เจ้าหน้าที่/ผู้ตรวจ; ไฟล์ส่งออกไม่มีเลขบัตรประชาชน; ส่งออกได้เฉพาะ officer. คู่มือมีคำเตือนให้เก็บไฟล์ส่งออกอย่างระมัดระวัง.*

**29. ทำไมต้องบังคับเปลี่ยนรหัสครั้งแรก (must_change_password)?**
*รหัสที่เจ้าหน้าที่ตั้งให้เป็นรหัสชั่วคราวที่อีกคนรู้ → ต้องเปลี่ยนเองก่อนใช้งานอื่นใด. บังคับที่ backend (`authenticate` ด่าน 3 ให้ใช้ได้แค่ `/auth/me` กับ `/auth/password`) ไม่ใช่แค่ frontend.*

**30. ถ้าไม่มี `requireRole` ที่ backend แต่ซ่อนปุ่มไว้ จะเกิดอะไร?**
*ใครเปิด Developer Tools หรือใช้ curl ยิง API ตรงก็ทำได้ทุกอย่าง เพราะ frontend คุมผู้ใช้ไม่ได้ — จึงต้องกันที่ backend เสมอ.*

**31. CORS คืออะไร ตั้งยังไง?**
*เบราว์เซอร์บล็อก request ข้าม origin (5174 → 3000) ถ้า server ไม่อนุญาต. ตั้ง `cors({ origin: <จาก .env>, credentials: true })` — ต้องระบุ origin จริงเมื่อใช้ cookie (ห้าม `*`).*

**32. ค่าลับเก็บที่ไหน?**
*`.env` เท่านั้น (`DATABASE_URL`, `JWT_SECRET`, `CORS_ORIGIN`, `COOKIE_SECURE`) ไม่ commit; `env.js` ตรวจว่าครบก่อน server เริ่ม ขาดแล้วหยุดทันทีดีกว่าไปพังกลางทาง; มี `.env.example` ให้ copy.*

## D. Logic / อัลกอริทึม (33–44)

**33. อธิบายกฎ carry-forward (ยกผลรอบก่อน)**
*วิชาที่นักศึกษาเคยผ่านในใบของรอบอื่น (ที่ไม่ถูกตีกลับ) ถูกล็อกเป็น "ผ่าน" และติดธง `carried_forward` ไม่ว่า client จะส่งค่าอะไรมา; ต้องตอบเฉพาะวิชาที่เหลือ. เหตุผล: ไม่ต้องกรอกซ้ำ + กันแก้ผลที่ผ่านแล้วให้เป็นตก. ธง carried ทำให้สถิติรายวิชานับเฉพาะคนที่สอบจริง.*
ดู `03` ข้อ 6.2

**34. กัน 2 คนตรวจใบเดียวกันพร้อมกันยังไง?**
*Optimistic concurrency: เงื่อนไข `staff_status = 'pending'` อยู่ใน `UPDATE ... WHERE` ทำให้อะตอมิก คนแรกได้ count=1 คนที่สองได้ 0 → 409. การเช็คก่อนอัปเดตอย่างเดียวไม่พอ (check-then-act มีช่องว่าง).*
`examResults.repository.js → updateStaffStatusIfPending`

**35. phase ของรอบคืออะไร ทำไมไม่เก็บใน DB?**
*สถานะจริงของรอบ (closed/scheduled/active/expired) คำนวณจาก status + วันที่ ณ ตอนนั้น. ไม่เก็บเพราะค่าเปลี่ยนเองตามเวลา ถ้าเก็บต้องมีตัวตั้งเวลาอัปเดตและเสี่ยงไม่ตรง. คำนวณตอนอ่านง่ายและถูกเสมอ; ต้องตรงกับเงื่อนไขของ `findActive` ที่ใช้ตอนรับผล.*
`utils/roundPhase.js`

**36. "ผ่านครั้งแรก" กับ "ผ่านภายในปีแรก" ต่างกันยังไง? คิดยังไง?**
*ผ่านครั้งแรก = ใบของรอบที่ 1 ยืนยันแล้วและผ่านครบ ÷ นักศึกษาทั้งรุ่น. ผ่านภายในปีแรก = ผ่านครบเมื่อนับผลสะสมทุกรอบของปีนั้น (รายคน) ÷ ทั้งรุ่น. นับเฉพาะใบยืนยันแล้ว เพราะผลที่กรอกเองยังไม่มีใครเทียบกับใบจริง. ตัวอย่างจากเทส: รุ่น 5 คน ผ่านครั้งแรก 2 ผ่านภายในปีแรก 4.*
`dashboard.service.js → buildYearSummary`

**37. นำเข้านักศึกษาจากไฟล์ที่หน้าตาไม่เหมือนกันได้ยังไง?**
*เดาคอลัมน์จากหัว (ตรง 1 อัน = ใช้, กำกวม = ให้คนเลือก), ล้างตัวเลขไทย/ขีด/จุด/E+ ของ Excel, ตรวจรายแถว (ข้ามแถวเสีย ไม่ล้มทั้งไฟล์), มี dry-run ให้ดูสรุปก่อนบันทึก, hash เลขบัตรก่อนเก็บ.*
ดู `03` ข้อ 11

**38. ทำไมลบบัญชีเจ้าหน้าที่ที่เคยทำงานไม่ได้? แล้วถ้าเจ้าหน้าที่ลาออก?**
*FK ทุกตัวไป users เป็น RESTRICT เพื่อไม่ให้ประวัติ (รอบที่สร้าง ประกาศ บันทึกการตรวจ) กำพร้า — ระบบเช็คก่อนแล้วตอบ 409 ให้ใช้ "ถอนสิทธิ์" (ล็อกอินไม่ได้ ประวัติอยู่ครบ). ตัวเลือกถ้าต้องลบจริง: (ก) ลบแบบซ่อน (soft delete) (ข) โอนรอบ/ประกาศให้คนอื่น + เก็บชื่อผู้ตรวจไว้ในบันทึกการตรวจ — ขึ้นกับข้อกำหนดด้านข้อมูลส่วนบุคคลที่คณะต้องการ. ตอนนี้เลือกเก็บความครบถ้วนของประวัติไว้ก่อน.*
ข้อจำกัดที่บอกเอง: ถอนสิทธิ์แล้วยังไม่มีปุ่มคืนสิทธิ์ใน UI

**39. ทำไมเช็คก่อนลบบัญชี แทนที่จะจับ error จาก DB?**
*Postgres ตอบ SQLSTATE 23001 (restrict_violation) ซึ่ง Prisma ไม่แปลงเป็น P2003 → เคยหลุดเป็น 500 พร้อม SQL ดิบ. แก้ด้วย pre-check (`countLinkedHistory`) + catch สำรองกันกรณีชนกันพอดี; มีเทสคุ้มครอง (`phase23`).*

**40. ตัวเลขสถิติในระบบไม่ขัดกันเองได้ยังไง?**
*ใช้กฎกลางข้อเดียว: "ผ่าน" ทุกตัวนับเฉพาะใบยืนยันแล้ว ตัวหารเป็นทั้งรุ่น และมีแถบเตือนว่ายังมีใบรอตรวจกี่ใบที่ยังไม่นับ. เคยพบตัวเลขขัดกันในหน้าเดียว (ผ่านวิชาหนึ่ง 40 แต่ผ่านครบ 45) จึงรวมกฎแล้วเขียนเทสเทียบไฟล์ส่งออกกับตัวเลขบนการ์ดตรง ๆ.*

**41. จัดการเวลา/timezone ยังไง?**
*ทุกอย่างตีความเป็นเวลาไทย (UTC+7 ตายตัว ไม่มี DST) ด้วย offset คงที่ ไม่ใช้ `setHours()` ที่ขึ้นกับ timezone ของเครื่อง. วันปิดรับไม่มีเวลา = 23:59:59.999 ของวันนั้น.*

**42. `null` กับ `0` ในอัตราผ่านรายวิชาต่างกันยังไง?**
*`null` (ขึ้นขีด) = ไม่มีใครสอบวิชานี้ในรอบ (เช่นทุกคนยกผลมา) ส่วน 0% = สอบแล้วตกหมด — ถ้าใช้ 0 แทน null จะตีความผิดความหมาย.*

**43. ทำไมแจ้งเตือนของเจ้าหน้าที่ไม่เก็บลง DB?**
*เป็นสถานะ ณ ขณะนั้น (รอบใกล้ปิด, ค้างตรวจ N ใบ) ไม่ใช่เหตุการณ์ที่เกิดแล้ว — คำนวณทุกครั้งที่เรียกจึงไม่มีวันเก่า/ไม่ตรง. ส่วนเหตุการณ์ของนักศึกษา (ถูกตีกลับ/ยืนยัน) เก็บในตารางเพราะไม่มีข้อมูลอื่นให้ประกอบย้อนหลังได้.*

**44. review_logs มีไว้ทำไม ในเมื่อ exam_results เก็บผู้ตรวจแล้ว?**
*`confirmed_by` เก็บแค่ผู้ตัดสินล่าสุดและถูกล้างเมื่อนักศึกษาส่งใหม่/ถอนการยืนยัน. `review_logs` เป็น insert-only บันทึกทุกการตัดสิน (ใคร/อะไร/เมื่อไหร่/เหตุผล) ตรวจย้อนหลังได้.*

## E. Frontend (45–52)

**45. ทำไมไม่ใช้ react-router?**
*แอปมีไม่กี่หน้าและต้องคุมสิทธิ์ต่อ role ในที่เดียว จึงเก็บหน้าเป็น state + map URL เองด้วย History API (`pushState`, `popstate`) — ลด dependency. ข้อแลกเปลี่ยน: ต้องดูแลตาราง `PAGE_PATH`/`ROLE_PAGES` เอง.*

**46. State จัดการยังไง? ใช้ Redux ไหม?**
*ไม่ใช้ — state อยู่ที่ component ที่ใช้ (useState) และแชร์ผ่าน props จาก `app.jsx` เท่าที่จำเป็น (ผู้ใช้, หน้า, แจ้งเตือน). แอปขนาดนี้ไม่ต้องการ store กลาง.*

**47. หน้าเว็บรู้ได้ยังไงว่าผู้ใช้ login อยู่/หมดอายุ?**
*เก็บ object ผู้ใช้ใน localStorage (ไม่ใช่ความลับ) ไว้วาด UI; ตอนรีเฟรชยิง `/auth/me` ตรวจ cookie; ถ้า backend ตอบ 401 พร้อม `code:'auth_required'` ทุก request จะล้าง session แล้วกลับหน้า login.*

**48. ปุ่ม/เมนูที่ผู้ใช้ไม่มีสิทธิ์ ซ่อนยังไง แล้วกันจริงที่ไหน?**
*ซ่อนด้วยเงื่อนไข `readonly`/ตาราง `ROLE_PAGES` เพื่อ UX; กันจริงที่ backend.*

**49. ทำไมส่งออก Excel/PDF ต้องผ่าน `downloadFile` ไม่ใช้ลิงก์ตรง?**
*ไฟล์ต้องแนบ cookie login (fetch + `credentials:'include'`) แล้วแปลงเป็น blob ให้เบราว์เซอร์เซฟ; ชื่อไฟล์ตั้งฝั่งหน้าจอเพราะข้าม origin อ่าน header ชื่อไฟล์ไม่ได้.*

**50. ปุ่ม "ดาวน์โหลด PDF" ของรายงานทำงานยังไง?**
*ถ่ายภาพกล่องรายงานที่เห็นบนจอด้วย html2canvas → หั่นเป็นหน้า A4 ที่รอยต่อระหว่างส่วน → ใส่ jsPDF. ข้อดี: หน้าตาตรงกับจอ; ข้อควรระวังที่เคยเจอ: letter-spacing ทำสระไทยซ้อน, แอนิเมชันแถวตารางยังเล่นตอนถ่ายทำให้แถวหาย — แก้ด้วยการปิดในสำเนาที่ถ่าย. ไลบรารีโหลดตอนกดปุ่มเท่านั้น.*

**51. ตัวกรอง/แบ่งหน้าของหน้านักศึกษาทำฝั่งไหน ทำไม?**
*ฝั่งหน้าจอ (ข้อมูลหลักร้อย-พัน เครื่องรับไหว โต้ตอบไว) ส่วนตัวเลขสถิติที่ต้องถูกต้องคำนวณที่ backend. ถ้าข้อมูลโตเป็นหมื่นต้องย้ายไปแบ่งหน้าที่ backend.*

**52. จัดการหลายภาษาและหน้าจอมือถือยังไง?**
*พจนานุกรม TH/EN ใน `i18n.js` เรียกด้วย `t(lang,key)`; CSS มี breakpoint (860/1100/680px) เปลี่ยน sidebar เป็นเมนูเลื่อนและ grid เป็นคอลัมน์เดียว.*

## F. ทดสอบ / เสถียรภาพ / ข้อจำกัด (53–62)

**53. ทดสอบระบบยังไง? มั่นใจได้แค่ไหน?**
*3 ชั้น: (1) smoke test ยิง API จริง 21 ไฟล์ — รายงาน 1 ต.ค. 20 ไฟล์ 820 ข้อตรวจผ่านทั้งหมด + ไฟล์ความปลอดภัย phase27 ที่เพิ่มทีหลัง ครอบคลุม login, สิทธิ์ทุก role, กฎธุรกิจ, ขอบเขตข้อมูล, ส่งออก, วงจรเต็มรอบ 1→2→3, flow จริงของคณะ, กรณีขอบ 43 กรณี (2) เทสผ่านหน้าเว็บจริงอัตโนมัติด้วย Chrome (`npm run test:e2e`) 19 หัวข้อ 166 ข้อตรวจ รวมจอมือถือและสลับภาษา (3) ทดสอบมือ. รันบน schema สะอาดที่สร้างใหม่ทุกครั้ง ไม่แตะข้อมูลจริง. ที่มาของกรณีทดสอบ: ไล่ flow จริงของคณะแล้วเรียงตาม "โอกาสเกิด × ผลกระทบ" (`docs/test-plan.md`) — วิธีนี้ทำให้เจอบั๊ก B1 ก่อนเขียนเทส. ข้อจำกัด: ไม่มี unit test ราย component ฝั่ง frontend, ยังไม่ได้ทำ load test.* (ก่อนสอบรันใหม่แล้วใช้ตัวเลขล่าสุด)

**54. เคยเจอบั๊กอะไรบ้าง แก้ยังไง?** *(ตอบเป็นเรื่องเล่า — แสดงว่าทดสอบจริง)*
*(1) ลบบัญชีที่มีประวัติได้ 500 พร้อม SQL ดิบ → เช็คก่อนลบ ตอบ 409 (2) รอบที่ปิดแล้วหน้าจอยังเขียนเปิดรับ → phase ให้ตรงกับ findActive (3) ตัวเลขสถิติขัดกัน → กฎ "นับเฉพาะยืนยันแล้ว" (4) สอบหลายรอบนับเกินจำนวนคน → นับรายคน (5) PDF ตัวอักษรทับ/แถวหาย → ปิด letter-spacing และแอนิเมชันตอนถ่าย (6) แจ้งเตือนประกาศพาเจ้าหน้าที่ไปหน้านักศึกษา → เลือกหน้าปลายทางตาม role และกันหน้าที่ role นั้นเข้าไม่ได้ (7) **B1** วิชาที่ยกมาจากใบที่ถูกตีกลับภายหลังถูกนับว่าผ่าน → ไม่นับแถวยกมา (8) **แนบพร้อมกัน 10 ไฟล์ได้ 6 ไฟล์** → นับซ้ำหลังบันทึก (9) **ใบรอตรวจ/ใบรอบเก่าเปลี่ยนหลักฐานได้หลังปิดรอบ** → ใช้กฎเดียวกับตอนส่งผล.*

**55. ทำไมต้องรัน `test:clean` ไม่รัน `npm test` ตรง ๆ?**
*DB ที่ใช้อยู่มีข้อมูลจำลอง 928 คน เทสหลายตัวคาดว่าฐานสะอาด เลย fail ทั้งที่โค้ดไม่พัง แยกบั๊กจริงไม่ได้. `test:clean` สร้าง schema ชั่วคราว migrate+seed รันแล้วลบทิ้ง.*

**56. ถ้าผู้ใช้ 100 คนส่งพร้อมกัน?**
*PrismaClient ตัวเดียว (connection pool) ไม่ท่วม Postgres; unique index กันใบซ้ำ; การตรวจใช้ UPDATE แบบมีเงื่อนไขกันชนกัน. ยังไม่ได้ทำ load test จริง (ข้อจำกัด) — ขนาดใช้งานจริงคือรุ่นละ ~200 คนในช่วงเวลาที่เปิดรอบ.*

**57. จุดอ่อนของระบบคืออะไร?**
*พูดตรง ๆ: (1) rate limit อยู่ใน memory (2) ยังไม่ deploy HTTPS จริง (3) ยังไม่มีระบบสำรองอัตโนมัติ (4) ถอนสิทธิ์แล้วไม่มีปุ่มคืนใน UI (5) บางข้อความยังไม่ผ่าน i18n (6) ไม่มี unit test ราย component ฝั่ง frontend (มีเทสผ่านเบราว์เซอร์แทน) (7) แก้ใบที่ถูกตีกลับหลังปิดรอบยังไม่มีเส้นตาย (8) JWT ยกเลิกรายใบไม่ได้ (9) ไม่ได้สแกนไวรัสไฟล์แนบ. ทุกข้อมีทางแก้ที่รู้แล้ว.*

**58. ถ้า server ล่มระหว่างบันทึก ข้อมูลจะเสียไหม?**
*การบันทึกใบผลสอบอยู่ใน transaction: สำเร็จทั้งหมดหรือไม่เขียนเลย. ไฟล์ที่อัปโหลดแล้วแต่บันทึกแถวไม่สำเร็จ โค้ดลบไฟล์บนดิสก์ทิ้งทุกทาง (ตัวแปร `saved` ใน `certificates.controller.js → upload`) · ตอนลบไฟล์ ลบแถวใน DB ก่อนแล้วค่อยลบไฟล์ (ถ้ากลับกันแล้ว DB พัง จะมีแถวชี้ไปไฟล์ที่ไม่มีอยู่) · ถ้าเครื่องดับกลางคันจริง ๆ อาจเหลือไฟล์กำพร้าบนดิสก์ได้ (ไม่กระทบความถูกต้องของข้อมูล).*

**59. ระบบนี้ผ่านเกณฑ์ความเป็นส่วนตัว (PDPA) ไหม?**
*ดำเนินการตามหลักพื้นฐาน: เก็บเท่าที่จำเป็น (ผู้บริหารไม่เก็บอีเมล/เบอร์), จำกัดสิทธิ์ตามหน้าที่, ไม่เปิดเผยเลขบัตรในไฟล์ส่งออก, รหัสผ่านเป็น hash. ยังไม่มีนโยบาย retention/ลบข้อมูลตามคำขอ — เป็นงานต่อยอด.*

**60. ถ้าอาจารย์อยากเพิ่มวิชาที่ 9 ต้องแก้อะไร?**
*ไม่ต้องแก้โค้ด — เจ้าหน้าที่เพิ่มรายวิชาในหน้า "รอบการกรอกและรายวิชา" แล้วเลือกวิชาในรอบใหม่ (รอบหนึ่งเลือกวิชาได้ ไม่ต้องครบทุกวิชา; รอบเก่าที่ไม่มี `subject_ids` ถือว่าใช้ทุกวิชา). เพราะไม่ได้ hardcode 8 วิชาไว้.* (จุดที่ยังมี "8" ฝังคือข้อความบางจุด เช่น หัวข้อ "ผลสอบรายวิชา (8 วิชา)" ใน i18n)

## G. ทีมและกระบวนการ (61–64)

**61. แบ่งงานยังไง ใครทำอะไร?**
*มังกร = Backend + Database (เป็นเจ้าของ `backend/**` และ schema/migration), แก้ม = Frontend (`frontend/**`). จุดต่อคือ REST contract; เปลี่ยน schema ที่กระทบ response ต้องแจ้งอีกฝ่าย; requirement นอกรายงานต้องถามก่อนเพิ่ม.*

**62. ใช้ Git ยังไง?**
*commit แยกตามเรื่อง, add ทีละไฟล์ (ไม่ `git add .` เพราะมีงานค้างของอีกคนในเครื่องเดียวกัน), ข้อความ commit บอกเหตุผลว่าทำไมแก้. เอกสาร `BACKEND_GUIDE.md` อัปเดตในคอมมิตเดียวกับโค้ดเสมอ (มี Changelog).*

**63. สิ่งที่ภูมิใจ/เรียนรู้มากที่สุด?**

## H. เรื่องที่เปลี่ยน 1 ต.ค. 2569 (65–74)

**65. ทำไมเปลี่ยนจากแนบ PDF ไฟล์เดียว เป็นหลายไฟล์และรับรูปภาพ? เกินรายงานไหม?**
*ไล่ flow จริงของคณะแล้วพบว่านักศึกษาส่วนใหญ่มีใบคะแนนเป็นกระดาษ ถ่ายรูปจากมือถือสะดวกกว่า และใบเดียวอาจมีหลายหน้า (ช่องว่าง G1 ใน `docs/test-plan.md`). รายงานกำหนด "อัปโหลดเอกสารหลักฐาน" — นี่คือการทำข้อเดิมให้ใช้งานได้จริง ไม่ใช่ฟีเจอร์ใหม่ และไม่ต้องแก้ schema เพราะตาราง `certificates` เป็น 1:M อยู่แล้ว. จำกัด 5 ไฟล์ไฟล์ละ 10 MB ไม่ให้เจ้าหน้าที่ต้องเปิดไฟล์จำนวนมาก.*
`certificates.controller.js → upload`, `MAX_FILES_PER_RESULT`

**66. magic bytes คืออะไร ทำไมไม่เชื่อนามสกุลไฟล์?**
*ไบต์ชุดแรกของไฟล์ที่มาตรฐานกำหนด (PDF = `%PDF-`, JPG = `FF D8 FF`, PNG = `89 50 4E 47 0D 0A 1A 0A`). นามสกุลและชนิดที่เบราว์เซอร์บอกปลอมได้ (เปลี่ยนชื่อไฟล์ HTML เป็น .pdf) แต่เนื้อไฟล์ปลอมไม่ได้โดยไม่ทำให้ไฟล์เสีย. ระบบอ่านแค่ 8 ไบต์แรก ไม่อ่านทั้งไฟล์ และเก็บชนิดจริงไว้ใช้ตอนเปิดไฟล์. ข้อจำกัด: ไม่ได้สแกนไวรัส/สคริปต์ใน PDF.*
`certificates.controller.js → detectFileType` (ตาราง trace ใน `09` หัวข้อ 8)

**67. ถ้านักศึกษาถูกตีกลับหลังรอบปิดแล้ว ทำยังไง? ทำไมไม่ให้เลื่อนวันปิดรอบ?**
*แก้ส่งใหม่ได้เลยเฉพาะใบที่ถูกตีกลับของรอบล่าสุด (`findSubmittableRound`). ไม่เลื่อนวันปิดเพราะจะเปิดให้ทุกคนในรุ่นส่ง/แก้ได้หมด และทำไม่ได้ถ้ารอบถัดไปเปิดอยู่ (เปิดได้ทีละรอบ). ใบรอตรวจหรือคนไม่เคยส่ง ยังส่งหลังปิดไม่ได้เหมือนเดิม. กฎนี้อยู่ฟังก์ชันเดียวที่ใช้ทั้งตอนส่งผล หน้ากรอก และแนบไฟล์ ให้ตัดสินตรงกัน. ข้อจำกัด: ยังไม่มีเส้นตาย.*
`examResults.service.js → findSubmittableRound`

**68. เล่าบั๊ก B1 — เจอได้ยังไง แก้ยังไง?**
*เจอจากการไล่ flow จริงของคณะในแผนทดสอบ ก่อนมีผู้ใช้เจอ: ใบรอบ 1 ยังรอตรวจตอนเปิดรอบ 2 → วิชา A ถูกยกไปรอบ 2 → ภายหลังใบรอบ 1 ถูกตีกลับ → สำเนา A ในใบรอบ 2 ยังเป็นผ่าน ทำให้รอบ 3 ล็อก A และ "ผ่านภายในปีแรก" สูงเกินจริง (ตัวเลขที่ส่งสภา). เขียนเทสให้ fail ก่อน (`phase25`) แล้วแก้ด้วยกฎเดียว "ไม่นับแถวที่ยกมา" ใน 3 จุด. ไม่เสียอะไรเพราะถ้าใบต้นทางดี แถวจริงในใบต้นทางถูกนับอยู่แล้ว.*
`findPassedSubjectIds`, `findEligibleWithPassedSubjects`, `addConfirmedRealPasses`

**69. ผู้ช่วยตรวจสอบต่างจากเจ้าหน้าที่ยังไง? ทำไมเปลี่ยนชื่อ?**
*บทบาท `reviewer` ในฐานข้อมูล — ตรวจ/ยืนยัน/ตีกลับในคิวเดียวกับเจ้าหน้าที่และเปิดไฟล์หลักฐานได้ แต่ถอนการยืนยัน จัดการรอบ/ผู้ใช้/ประกาศ ส่งออก ลบไฟล์ ไม่ได้ (เทส PH26-17 ได้ 403 ทุกข้อ). เปลี่ยนชื่อบนจอจาก "เจ้าหน้าที่ตรวจสอบ" เป็น "ผู้ช่วยตรวจสอบ" และเมนู "จัดการผู้ใช้งาน" เพราะคณะหาไม่เจอว่าเพิ่มผู้ช่วยได้ที่ไหน (ช่องว่าง G5) — เปลี่ยนแค่คำ ไม่ได้เปลี่ยนสิทธิ์.*
`examResults.routes.js` (`requireRole("officer", "reviewer")`), `i18n.js → role.reviewer`

**70. ถ้าเจ้าหน้าที่กับผู้ช่วยตรวจใบเดียวกันพร้อมกัน หรือนักศึกษากดส่ง 2 ครั้งพร้อมกัน?**
*ตรวจพร้อมกัน: เงื่อนไขอยู่ใน UPDATE … WHERE pending คนหลังได้ 409. ส่งพร้อมกัน: unique(student_id, round_id) ที่ฐานข้อมูลกัน ได้ใบเดียว คำขอที่สองได้ 409 ไม่มี 500. ทั้งสองกรณีมีเทสยิงพร้อมกันจริง (PH15-02, PH25-04).*

**71. รายชื่อ "ไม่ผ่านภายในปีแรก" คิดยังไง ตรงกับตัวเลขบนแดชบอร์ดแน่ใจได้ยังไง?**
*ใช้ helper ชุดเดียวกับการ์ด (`addConfirmedRealPasses`, `getRequiredSubjectIds`, `hasPassedAll`) — ไม่มีโค้ดคำนวณซ้ำ. ผ่าน + ไม่ผ่าน = ทั้งรุ่นเสมอ (คนไม่ส่งอยู่กลุ่มไม่ผ่านพร้อมคอลัมน์สถานะบอกเหตุผล). เทส PH26-39 ตรวจรายชื่อทีละคนเทียบกับตัวเลขแดชบอร์ด.*
`dashboard.service.js → buildFirstYearList`, `GET /api/dashboard/export-first-year`

**72. ข้อความ error ของระบบ ทำไมไม่มีคำภาษาอังกฤษเลย?**
*ผู้ใช้เป็นพยาบาลและเจ้าหน้าที่ ไม่ใช่คนไอที — ทุกข้อความต้องบอก "เกิดอะไรขึ้น + ทำอะไรต่อ" เป็นภาษาไทยทางการ. errorHandler แปลง error ของ Prisma/multer เป็นไทยและซ่อนข้อความดิบของ 500. เทส phase26 ตรวจทุกข้อความ error ว่ามีภาษาไทยและไม่มีชื่อ field, เทสหน้าเว็บหาคำต้องห้าม (`undefined`, `Request failed`, `student_id`) ทุกหน้า.*

**73. helmet คืออะไร ทำไมปิดบางตัว?**
*middleware ใส่ HTTP header ความปลอดภัยมาตรฐานทุกคำตอบ เช่น `X-Content-Type-Options: nosniff` (เบราว์เซอร์ห้ามเดาชนิดไฟล์เอง — สำคัญกับไฟล์ที่นักศึกษาอัปโหลด), ห้ามเว็บอื่นเอาไป iframe. ปิด Content-Security-Policy และตั้ง Cross-Origin-Resource-Policy เป็น cross-origin เพราะหน้าเว็บ (5174) กับ backend (3000) คนละ origin — ค่าเริ่มต้นจะบล็อกรูป/PDF ที่หน้าเว็บดึงมา.*
`app.js`

**74. ระบบทดสอบผ่านหน้าเว็บอัตโนมัติยังไง?**
*`npm run test:e2e` สร้าง schema ชั่วคราว `verify_e2e` → เปิด backend 3200 + หน้าเว็บ 5175 → ใช้ Chrome จริงของเครื่อง (playwright-core) กดตาม flow จริงทุกบทบาท รวมจอมือถือ 390px → ตรวจไม่มีหน้า error/คำต้องห้าม/คีย์แปลภาษาค้าง → ปิดทุกอย่างและลบ schema. ปุ่มที่กดไม่ได้ใน 5 วินาที = FAIL แล้วเดินต่อ หัวข้อหนึ่งพังไม่ลามหัวข้ออื่น.*
`backend/tests/e2e/run-e2e.mjs`, `real-flow.e2e.mjs`
