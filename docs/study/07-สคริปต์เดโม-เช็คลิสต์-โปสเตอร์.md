## 1. ⚠️ สิ่งที่ต้องทำก่อนวันสอบ (ถ้าไม่ทำ เดโมพังแน่)

### 1.1 วันที่ของรอบ — ประเด็นใหญ่สุด
ตอนนี้ (30 ก.ย. 2569) มีรอบ **2/2569 ปิดรับ 30 ก.ย. 23:59**. ถึงวันสอบ (14 ต.ค.) รอบนี้จะเป็นสถานะ **"เลยกำหนดปิด" (`expired`)**
→ นักศึกษาส่งผลไม่ได้ (ระบบปฏิเสธถูกต้อง) → **เดโม flow นักศึกษากรอกผลจะไม่ทำงาน**

**ต้องเตรียมอย่างใดอย่างหนึ่งก่อนสอบ (ทำในหน้า "รอบการกรอกและรายวิชา"):**
- ปิดรอบ 2/2569 → **เปิดรอบใหม่** (เช่น รอบ 3/2569) ตั้งวันปิดให้ห่างจากวันสอบ ≥ 1 เดือน หรือ
- แก้วันปิดของรอบเดิมให้เลื่อนออกไป
(ระบบเปิดรับได้ทีละรอบ ต้องปิดรอบเก่าก่อนเปิดรอบใหม่)

> นี่คือตัวอย่างที่ดีของ "บั๊กที่ไม่ใช่บั๊ก" — ถ้ากรรมการถามว่าทำไมกรอกไม่ได้ ตอบได้ว่า "รอบเลยกำหนดแล้ว ระบบบังคับตามกฎ" แล้วเปิดรอบใหม่ให้ดูสดก็ได้ (เป็นส่วนหนึ่งของเดโมจัดการรอบ)

## 3. โปสเตอร์ (10 คะแนน) — โครงเนื้อหา

เกณฑ์ A = ครบถ้วน สวยงาม เป็นอาชีพ สื่อสาร **ปัญหา วิธีดำเนินงาน ผลลัพธ์ ประโยชน์** ได้โดดเด่น

**โครง A1 (แนวตั้ง) 6 ส่วน:**
1. **หัว:** ชื่อโครงงาน (ไทย/อังกฤษ) · ชื่อ-สังกัด · อาจารย์ที่ปรึกษา (ผศ.ดร.กิตย์ศิริ ช่อเจี้ยง) · โลโก้คณะ/มหาวิทยาลัย
2. **ที่มาและปัญหา:** 2–3 บรรทัดสั้น ๆ + ไอคอน (เดิมจดกระจาย ติดตามลำบาก สถิติส่งสภาช้า)
3. **วัตถุประสงค์:** 3 ข้อ สั้น
4. **วิธีดำเนินงาน/สถาปัตยกรรม:** แผนผัง 3 ชั้น (React → Express → PostgreSQL) + ผู้ใช้ 3 กลุ่ม + วงจรสถานะใบผลสอบ (ภาพเดียวเล่าได้เยอะสุด)
5. **ผลลัพธ์:** ภาพหน้าจอ 3–4 ภาพ (Dashboard, กรอกผล, ตรวจ, รายงาน) + ตัวเลขยืนยัน: "ทดสอบอัตโนมัติ ~580 ข้อ ผ่านทั้งหมด · วงจรรอบ 1→2→3 ครบ · ข้อมูลจำลอง 5 รุ่น 928 คน"
6. **ประโยชน์ + ต่อยอด + ติดต่อ:** ลดงานเอกสาร ตัวเลขตรงกัน ตรวจย้อนหลังได้ · QR ไปวิดีโอเดโม

**ข้อควรทำ:** ตัวอักษรอ่านได้จาก 1.5–2 เมตร (หัวข้อ ≥ 60pt, เนื้อ ≥ 28pt) · ใช้สีธีมเดียวกับระบบ (ส้ม/น้ำตาลของเว็บ) · รูปภาพมากกว่าข้อความ · เว้นขอบ · ไม่เกิน 6 ส่วน
**ข้อห้าม:** ย่อหน้ายาว · ภาพหน้าจอเบลอ/มีข้อมูลส่วนบุคคลจริง (ใช้ข้อมูลจำลอง) · ตัวอักษรเล็ก
**ตรวจก่อนพิมพ์:** ตัวสะกดไทย, ตัวเลขตรงกับที่พูดในเดโม (ไม่เช่นนั้นโดนถาม), ความละเอียดภาพ ≥ 150 dpi ที่ขนาดจริง

## 4. โครงการนำเสนอ (ถ้ามีสไลด์ 5–7 แผ่น)
1. ชื่อ+ทีม · 2. ปัญหาและวัตถุประสงค์ · 3. ภาพรวมระบบ + ผู้ใช้ 3 กลุ่ม · 4. สถาปัตยกรรม + จุดเด่นทางเทคนิค (3 ข้อ: กฎธุรกิจฝั่ง backend, ความปลอดภัย JWT/httpOnly/bcrypt, ตัวเลขสถิติตรงกัน) · 5. **เดโม** (หัวข้อ 2) · 6. ผลทดสอบ + ข้อจำกัด + ต่อยอด · 7. ขอบคุณ/คำถาม

**3 จุดเด่นทางเทคนิคที่ควรเน้น (พูดได้ลึก = คะแนนหัวข้อ 2 และ 5):**
1. **กฎธุรกิจไม่พึ่ง client:** carry-forward, ล็อกหลังยืนยัน, กันตรวจชนกัน (optimistic guard), รอบผูกรุ่น
2. **ความปลอดภัยเป็นชั้น:** bcrypt → JWT ใน httpOnly cookie → authenticate เช็ค DB ทุกครั้ง → requireRole → rate limit → ไฟล์ตรวจสิทธิ์
3. **ตัวเลขน่าเชื่อถือ:** กฎเดียว "นับเฉพาะใบยืนยัน" + เทสเทียบไฟล์/การ์ด/รายงานให้ตรงกัน
