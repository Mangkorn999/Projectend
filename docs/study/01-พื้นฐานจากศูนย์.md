# 01 — พื้นฐานจากศูนย์ (อ่านแล้วเข้าใจ "เว็บนี้ทำงานยังไง")

เป้าหมาย: จบไฟล์นี้แล้วต้องอธิบายได้ว่า **"นักศึกษากดปุ่มส่งผลสอบ แล้วเกิดอะไรขึ้นบ้างตั้งแต่หน้าจอจนถึงฐานข้อมูล"**
ทุกหัวข้อมีช่อง "ในโปรเจกต์เรา" ชี้ไฟล์จริงที่ให้เปิดดู

## 1. เว็บแอปคืออะไร — 3 ชิ้นที่คุยกัน

```
[ ผู้ใช้ + เบราว์เซอร์ ]  ←──HTTP──→  [ Backend (Node + Express) ]  ←──Prisma──→  [ PostgreSQL ]
   หน้าเว็บ React                      ตรรกะ + สิทธิ์ + คำนวณ                        ที่เก็บข้อมูลถาวร
   (frontend/)                         (backend/)
```

| ชิ้น | หน้าที่ | เปรียบเทียบ |
|---|---|---|
| **Frontend** (React) | แสดงหน้าจอ รับการกดของผู้ใช้ แล้วขอข้อมูลจาก backend | พนักงานหน้าเคาน์เตอร์ — พูดกับลูกค้า แต่ไม่มีกุญแจห้องเก็บเงิน |
| **Backend** (Express) | ตัดสินใจทุกอย่าง: ใครทำอะไรได้ ข้อมูลถูกไหม คำนวณสถิติ | ผู้จัดการหลังร้าน — ตรวจบัตร ตรวจเอกสาร แล้วค่อยไปเปิดตู้เซฟ |
| **Database** (PostgreSQL) | เก็บข้อมูลให้อยู่ถาวรแม้ปิดเครื่อง | ตู้เซฟ/ตู้เอกสาร |

**กฎทอง:** frontend "เชื่อไม่ได้" เพราะผู้ใช้แก้โค้ดในเบราว์เซอร์ได้ ดังนั้นการตรวจสิทธิ์และกฎสำคัญต้องอยู่ที่ backend เสมอ
(ในโปรเจกต์เรา `CLAUDE.md` เขียนไว้: ห้าม hardcode การคำนวณผ่าน/ไม่ผ่านไว้ฝั่ง frontend)

**ในโปรเจกต์เรา:** `frontend/` = React+Vite รันที่ `localhost:5174` · `backend/` = Express รันที่ `localhost:3000` · DB ชื่อ `ProjectEnd`

## 2. HTTP — ภาษาที่ frontend กับ backend ใช้คุยกัน

ทุกครั้งที่หน้าเว็บอยากได้/ส่งข้อมูล มันส่ง **request** แล้วได้ **response** กลับ

**Request มี 4 ส่วนที่ต้องรู้**
| ส่วน | ตัวอย่างในโปรเจกต์ |
|---|---|
| Method (ทำอะไร) | `GET` ขอดู · `POST` สร้างใหม่ · `PUT`/`PATCH` แก้ · `DELETE` ลบ |
| URL (กับอะไร) | `/api/exam-results/12/approve` |
| Headers | `Cookie: token=...` (ตัวตนของผู้ใช้) |
| Body | `{ "subject_results": [ { "subject_id": 1, "is_passed": true } ] }` |

**Response มี status code** (ตัวเลขบอกผลลัพธ์) — ต้องจำชุดนี้ กรรมการถามบ่อย:
| รหัส | ความหมาย | ในโปรเจกต์เราเกิดเมื่อ |
|---|---|---|
| 200 / 201 | สำเร็จ / สร้างสำเร็จ | กรอกผลสอบสำเร็จ / สร้างประกาศสำเร็จ |
| 400 | ข้อมูลที่ส่งมาผิด | ส่งวิชาไม่ครบ, `is_passed` เป็นข้อความ |
| 401 | ยังไม่ได้ login / token ใช้ไม่ได้ | ไม่มี cookie, token หมดอายุ |
| 403 | login แล้วแต่ **ไม่มีสิทธิ์** | นักศึกษาเรียก endpoint ของเจ้าหน้าที่ |
| 404 | ไม่พบสิ่งที่ขอ | ไม่มีผลสอบ id นั้น |
| 409 | ชนกับสถานะปัจจุบัน | ยืนยันใบที่ตรวจไปแล้ว, ลบบัญชีที่มีประวัติ |
| 429 | ยิงบ่อยเกินไป | login ผิดรัว ๆ เกิน 10 ครั้ง/15 นาที |
| 500 | backend พัง (บัก) | ไม่ควรเจอเลยตอนเดโม |

> จำง่าย: **4xx = ผู้ใช้/ผู้เรียกทำผิดเงื่อนไข · 5xx = ฝั่ง server พังเอง**. สมัยก่อนเราเคยมี bug ที่ลบบัญชีแล้วได้ 500 แทน 409 (แก้แล้ว) — กรรมการชอบถามว่าแยก 4xx/5xx ทำไม

**JSON** = รูปแบบข้อความที่ frontend/backend ใช้ส่งข้อมูลกัน หน้าตาเหมือน object ของ JavaScript: `{ "success": true, "data": { ... } }`
ข้อตกลงของทีม (contract): backend ตอบ `{ success: true, data }` เมื่อสำเร็จ และ error ผ่าน `next(err)` → `{ success: false, message }`

**REST** = วิธีตั้ง URL ให้อ่านรู้เรื่อง: URL เป็น "ของ" (คำนาม) method เป็น "การกระทำ"
เช่น `POST /api/news` = สร้างประกาศ, `DELETE /api/news/5` = ลบประกาศ 5

## 3. ฐานข้อมูล (PostgreSQL) — ตารางและความสัมพันธ์

**ตาราง (table)** = ตาราง Excel: แถว (row) = 1 รายการ คอลัมน์ (column) = 1 คุณสมบัติ

คำศัพท์ 4 คำที่ต้องอธิบายได้:
| คำ | ความหมาย | ตัวอย่างในโปรเจกต์ |
|---|---|---|
| **Primary Key (PK)** | ค่าที่ไม่ซ้ำ ใช้ระบุแถวเดียว | `users.user_id`, `students.student_id` |
| **Foreign Key (FK)** | คอลัมน์ที่ชี้ไปหา PK ของอีกตาราง | `exam_results.student_id → students.student_id` |
| **Unique** | ห้ามค่าซ้ำ | `users.psu_passport_id`, `@@unique([student_id, round_id])` (1 คน 1 ใบต่อรอบ) |
| **Index** | สารบัญให้ค้นเร็วขึ้น | `@@index([round_id])` ใน `exam_results` |

**ความสัมพันธ์ (relation)**
- 1 : 1 (หรือ 0..1) — `users` ↔ `students` (ผู้ใช้บางคนเป็นเจ้าหน้าที่ จึงไม่มีแถว students)
- 1 : M (หนึ่งต่อหลาย) — `students` → `exam_results` (นักศึกษา 1 คนมีผลสอบได้หลายรอบ)

**ON DELETE RESTRICT** (ตั้งไว้ในโปรเจกต์เรา) = ถ้ามีแถวลูกชี้มาอยู่ ห้ามลบแถวแม่ — กันประวัติกำพร้า
นี่คือเหตุที่ลบเจ้าหน้าที่ที่เคยโพสต์ข่าว/ตรวจผลสอบไม่ได้ (ต้องใช้ "ถอนสิทธิ์")

**ห้ามเก็บไฟล์ใน DB** — โปรเจกต์เก็บแค่ `file_path` (ที่อยู่ไฟล์บนดิสก์ใน `backend/uploads/`) + `file_type` (ชนิดจริงที่ตรวจจากเนื้อไฟล์) เพราะ DB เก็บไฟล์ใหญ่แล้วช้าและสำรองยาก · ใบผลสอบ 1 ใบมีไฟล์ได้หลายแถว (`certificates` 1:M) จึงรองรับหลายไฟล์ได้โดยไม่ต้องแก้ตาราง

**SQL vs Prisma:** SQL คือภาษาคุย DB โดยตรง (`SELECT * FROM students WHERE ...`). **Prisma** คือ "ตัวแปลง" — เราเขียน JavaScript
`prisma.student.findMany({ where: { academic_year: 2569 } })` แล้ว Prisma แปลงเป็น SQL ให้ ข้อดี: ไม่ต้องเขียน SQL เอง, มี type, schema เป็นที่เดียว (`prisma/schema.prisma`)

**Migration** = ประวัติการแก้โครงตาราง (เก็บเป็นไฟล์ SQL ใน `prisma/migrations/` เรียงตามเวลา) เพื่อให้ DB ทุกเครื่องมีโครงเหมือนกัน
> ข้อควรรู้ของโปรเจกต์เรา: `prisma migrate dev` ใช้ไม่ได้ (user DB ไม่มีสิทธิ์สร้าง shadow database) ต้องเขียนไฟล์ migration เอง แล้วรัน `npx prisma migrate deploy`

**ในโปรเจกต์เรา:** เปิด `backend/prisma/schema.prisma` ดูทั้ง 11 โมเดล (ดู `02` ว่าแต่ละตารางทำอะไร)

## 4. ความปลอดภัยพื้นฐาน 4 เรื่องที่กรรมการชอบถาม

### 4.1 Password hashing (bcrypt)
ไม่เก็บรหัสผ่านจริง เก็บ **hash** (ผลลัพธ์ทางเดียวที่ย้อนกลับไม่ได้). ตอน login ระบบ hash รหัสที่พิมพ์มาแล้วเทียบ: `bcrypt.compare(password, user.password_hash)`
ใช้ bcrypt เพราะ "ช้าโดยตั้งใจ" (`SALT_ROUNDS = 10`) คนเดาเป็นล้านครั้งจะใช้เวลานานมาก
**ในโปรเจกต์เรา:** `authController.js → login`

### 4.2 JWT (บัตรผ่าน)
หลัง login สำเร็จ backend ออก **token** ให้ = ข้อความที่ข้างในมี `{ userId, role, studentId, mustChangePassword }` และ **ลงลายเซ็น** ด้วย `JWT_SECRET`
ทุก request ถัดไปผู้ใช้แนบ token มา backend ตรวจลายเซ็น (ปลอมไม่ได้เพราะไม่รู้ secret) แล้วรู้ว่าเป็นใคร ไม่ต้องถามรหัสผ่านซ้ำ
อายุ 1 วัน (`expiresIn: "1d"`)

### 4.3 httpOnly cookie (เก็บ token ที่ไหน)
เก็บ token ใน **cookie แบบ httpOnly** = JavaScript ในหน้าเว็บอ่านไม่ได้ → ถ้ามีคนแทรก script อันตราย (XSS) ก็ขโมย token ไม่ได้
(ทางเลือกคือเก็บใน localStorage ซึ่ง JS อ่านได้ → ไม่ปลอดภัยเท่า)
ตัวเลือกเพิ่ม: `sameSite: "lax"` กัน CSRF, `secure` ต้องเป็น `true` เมื่อขึ้น HTTPS จริง
**ในโปรเจกต์เรา:** `TOKEN_COOKIE_OPTIONS` ใน `authController.js`

### 4.4 Authentication vs Authorization
- **Authentication (ยืนยันตัวตน)** = "คุณคือใคร" → middleware `authenticate`
- **Authorization (ตรวจสิทธิ์)** = "คุณทำสิ่งนี้ได้ไหม" → middleware `requireRole("officer")`
ลำดับต้องเป็น authenticate ก่อน requireRole เสมอ (ไม่รู้ว่าเป็นใครจะตรวจสิทธิ์ไม่ได้) — อยู่ใน Security Checklist ของ `CLAUDE.md`

## 5. JavaScript ที่โปรเจกต์ใช้ — 10 ท่าที่พบทุกไฟล์

ถ้าติดสัญลักษณ์ ดูเพิ่มที่ `backend/SYNTAX_NOTES.md`. ตัวอย่างล้วนมาจากโค้ดจริง
**ฉบับละเอียด (แปลงทุกท่าเป็น if/for พร้อมแบบฝึก) อยู่ที่ `10`**

```js
// 1. const / let — ตัวแปร (const ห้ามกำหนดใหม่)
const roundSubjectIds = subjectsOfRound(round, allSubjects).map((s) => s.subject_id);

// 2. arrow function  (พารามิเตอร์) => ผลลัพธ์
const percent = (part, whole) => (whole ? Math.round((part / whole) * 100) : 0);
//                                  ↑ ternary: เงื่อนไข ? ค่าถ้าจริง : ค่าถ้าเท็จ

// 3. array methods — 4 ตัวที่ใช้บ่อยที่สุด
[1,2,3].map(x => x * 2)        // → [2,4,6]   แปลงทุกตัว ได้ array ใหม่ขนาดเท่าเดิม
[1,2,3].filter(x => x > 1)     // → [2,3]     คัดเฉพาะที่เงื่อนไขจริง
[1,2,3].every(x => x > 0)      // → true      จริงหมดทุกตัวไหม
[1,2,3].some(x => x > 2)       // → true      มีสักตัวที่จริงไหม

// 4. destructuring — แกะค่าจาก object ออกมาเป็นตัวแปร
const { subject_results } = req.body;

// 5. spread ...  — กางของเดิมออกมาแปะใหม่
const round2 = { ...round, phase: "active" };   // คัดลอก round แล้วเพิ่ม phase

// 6. optional chaining ?.  และ nullish ??
req.body?.remark?.trim()         // ถ้า body หรือ remark ไม่มี → undefined (ไม่พัง)
const name = user.student?.student_id ?? null;   // ถ้าซ้ายเป็น null/undefined ใช้ขวา

// 7. template string
`รอบที่ ${round.attempt_number}/${round.academic_year}`

// 8. import / export (ES module)
import * as examRepo from "./examResults.repository.js";
export const create = async (req, res, next) => { ... };

// 9. async / await — รอผลที่ช้า (เรียก DB, เรียก API) โดยไม่ค้างโปรแกรม
const student = await studentRepo.findById(req.user.studentId);   // รอจนได้ผลแล้วค่อยไปต่อ

// 10. try / catch — จับ error
try { ... } catch (err) { next(err); }   // โยนให้ errorHandler ตัวกลาง
```

**Promise.all** (เจอบ่อยใน `app.jsx`, `dashboard.service.js`) = ยิงหลายงานพร้อมกันแล้วรอทุกอันเสร็จ เร็วกว่ารอทีละอัน
```js
const [news, rows] = await Promise.all([apiFetch('/news'), apiFetch('/notifications/me')]);
```

## 6. Node.js + Express — backend ทำงานยังไง

**Node.js** = รัน JavaScript นอกเบราว์เซอร์ · **Express** = ไลบรารีรับ request แล้วส่งให้ฟังก์ชันที่ถูกต้อง

แนวคิดหลักของ Express คือ **middleware chain (สายพาน)**: request ผ่านฟังก์ชันเรียงกัน แต่ละตัวเลือก "ปล่อยผ่าน" (`next()`) หรือ "ตอบกลับเลย" (`res.status(401)...`)

```js
router.patch("/:id/approve", authenticate, requireRole("officer", "reviewer"), approve);
//                            ด่าน 1: ใครน่ะ   ด่าน 2: มีสิทธิ์ไหม               ตัวทำงานจริง
```

โครงทุกโมดูล: `routes.js → controller.js → repository.js` (ดู `03` หัวข้อ 1)
**เหตุผลที่แบ่ง:** เปลี่ยนวิธีเก็บข้อมูล → แก้ repository ที่เดียว · เปลี่ยนกฎธุรกิจ → แก้ controller ที่เดียว

## 7. React — frontend ทำงานยังไง

**React** = ไลบรารีสร้างหน้าจอจาก "ชิ้นส่วน" (component). หน้าจอ = ฟังก์ชันที่คืน JSX (HTML ที่เขียนในโค้ด JS)

### 7.1 Component และ props
```jsx
function Avatar({ name, size = 38 }) {             // ← component = ฟังก์ชัน, {name,size} = props (ค่าที่ส่งเข้ามา)
  return <span className="avatar">{name.charAt(0)}</span>;   // ← JSX
}
<Avatar name="สมชาย" size={32} />                  // ← เรียกใช้
```
props = "พารามิเตอร์ของ component" (อ่านอย่างเดียว)

### 7.2 State (ความจำของหน้าจอ)
```jsx
const [page, setPage] = useState('news');     // page = ค่าปัจจุบัน, setPage = ตัวเปลี่ยนค่า
setPage('dashboard');                          // เปลี่ยนค่า → React วาดหน้าจอใหม่ให้อัตโนมัติ
```
หลักสำคัญ: **เปลี่ยน state → หน้าจอวาดใหม่เอง** (ไม่ต้องสั่งแก้ HTML ด้วยมือ)

### 7.3 useEffect (ทำงานหลังวาดจอ — ใช้ดึงข้อมูล)
```jsx
useEffect(() => {
  apiFetch('/rounds').then(setRounds);    // ดึงข้อมูลแล้วเก็บลง state → จอวาดใหม่
}, []);                                    // [] = ทำครั้งเดียวตอนหน้าเปิด
```
รูปแบบที่เจอซ้ำทุกหน้าใน `frontend/src/design/*Real.jsx`: **เปิดหน้า → useEffect เรียก API → setState → วาดตาราง**
(ถ้าใส่ตัวแปรใน `[...]` เช่น `[roundId]` = ทำใหม่ทุกครั้งที่ตัวแปรนั้นเปลี่ยน)

### 7.4 useRef, useMemo
- `useRef` = กล่องเก็บค่า/ชี้ element ที่เปลี่ยนแล้ว **ไม่** ทำให้จอวาดใหม่ (ใช้ใน `reportRef` ชี้กล่องรายงานตอนบันทึก PDF, และ `startX` ตอนลากแจ้งเตือน)
- `key={...}` ใน list = ป้ายให้ React รู้ว่าแถวไหนเป็นแถวไหน (ใช้ `key={n.news_id}`)

### 7.5 Conditional rendering และ list
```jsx
{notifications.length ? <List/> : <Empty/>}     // เงื่อนไข
{rows.map(r => <tr key={r.id}>...</tr>)}         // วนสร้างหลายอัน
{!readonly && <button>ลบ</button>}               // แสดงเมื่อเงื่อนไขจริงเท่านั้น
```
ตัวอย่างจริง: ปุ่มที่ผู้บริหารไม่ควรเห็น (`readonly`) ซ่อนด้วยท่านี้ — แต่ **การกันจริงอยู่ที่ backend** ไม่ใช่การซ่อนปุ่ม

## 8. "กดส่งผลสอบ" เกิดอะไรขึ้น — ไล่ตั้งแต่ต้นจนจบ (ตัวอย่างสำหรับตอบกรรมการ)

1. นักศึกษากดปุ่ม "ยืนยันและส่งผลสอบ" ใน `examFormReal.jsx` → ฟังก์ชัน `submit`
2. frontend เรียก `apiFetch('/exam-results', { method:'POST', body:{ subject_results } })` ใน `api.js` (แนบ cookie อัตโนมัติ `credentials:'include'`)
3. request ไปถึง backend `app.js` → จับคู่ `/api/exam-results` → `examResults.routes.js`
4. ผ่าน `authenticate` (ตรวจ JWT + เช็คกับ DB ว่าผู้ใช้ยังอยู่) → `requireRole("student")`
5. `examResults.controller.js → create`:
   - ตรวจว่ามีสิทธิ์กรอก (`exam_eligible`) · หารอบที่ส่งได้ของรุ่นตัวเองด้วย `findSubmittableRound` (รอบที่เปิดอยู่ หรือรอบล่าสุดที่ใบของคนนี้ถูกตีกลับ) · ตรวจวิชาครบ/ซ้ำ/เป็น true-false
   - ใช้กฎ carry-forward (วิชาที่เคยผ่าน "จริง" แล้วถูกล็อกเป็นผ่าน)
6. `examResults.repository.js` สั่ง Prisma บันทึกใบผลสอบ + ผลรายวิชา (ในทรานแซกชันเดียว)
7. ตอบ `{ success: true, data: ... }` กลับ → frontend อัปโหลดไฟล์หลักฐาน **ทีละไฟล์** (PDF/JPG/PNG สูงสุด 5 ไฟล์, `POST /exam-results/:id/certificates`) → backend ตรวจชนิดไฟล์จากไบต์ต้นไฟล์จริง → พาไปหน้าสถานะ
   (ถ้าเป็นการแก้ใบเดิม ลำดับกลับกัน: ลบไฟล์ที่กดนำออก → อัปโหลดไฟล์ใหม่ → ส่งผลสอบ — ดู `04` หัวข้อ 4.1)
8. เจ้าหน้าที่เปิดคิวตรวจ → เห็นใบนี้ "รอตรวจสอบ" → กดยืนยัน/ตีกลับ → backend บันทึกสถานะ + `review_logs` + สร้างแจ้งเตือนให้นักศึกษา

ฝึกพูด: อธิบาย 8 ข้อนี้ภายใน 1 นาทีโดยไม่ดูเอกสาร — ถ้าทำได้ คุณตอบคำถามหัวข้อภาพรวมระบบได้แล้ว

## 9. คำศัพท์ที่ต้องอธิบายได้ (เช็คตัวเอง)

| คำ | ตอบสั้น ๆ ว่า |
|---|---|
| endpoint | URL + method หนึ่งคู่ = งานหนึ่งอย่างที่ backend ทำได้ |
| middleware | ฟังก์ชันที่ทำงานก่อน controller เช่น ตรวจ token |
| controller / repository | ตัดสินใจ / คุยกับ DB เท่านั้น |
| ORM (Prisma) | เขียน JS แทน SQL และเป็น schema กลาง |
| JWT | บัตรผ่านที่ลงลายเซ็น เก็บตัวตน+role |
| httpOnly cookie | cookie ที่ JS อ่านไม่ได้ กัน XSS |
| hash (bcrypt) | เก็บรหัสแบบย้อนกลับไม่ได้ |
| FK / RESTRICT | ตัวชี้ไปอีกตาราง / ห้ามลบถ้ามีลูกอยู่ |
| migration | ไฟล์ประวัติการแก้โครงตาราง |
| state / props | ความจำของ component / ค่าที่ส่งเข้ามา |
| useEffect | ทำงานหลังวาดจอ ใช้ดึงข้อมูล |
| optimistic guard | กันสองคนแก้ทับกันด้วยเงื่อนไขตอน UPDATE (ดู `03` หัวข้อ 7) |
| carry-forward | ยกวิชาที่ผ่านแล้วจากรอบก่อนมาล็อกเป็นผ่าน (ดู `03` หัวข้อ 6) |
| magic bytes | ไบต์ชุดแรกของไฟล์ที่บอกชนิดไฟล์จริง (PDF ขึ้นต้น `%PDF-`) ใช้ตรวจไฟล์แทนการเชื่อนามสกุล (ดู `09` หัวข้อ 8) |
| race condition | สองคำขอแข่งกันแตะข้อมูลเดียวกัน ผลขึ้นกับว่าใครช้ากว่า (ดู `09` หัวข้อ 7, 8) |
