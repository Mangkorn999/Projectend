## 1. ระบบนี้แก้ปัญหาอะไร (ประโยคเปิดของโปสเตอร์/การนำเสนอ)

คณะพยาบาลต้องติดตามผลสอบใบอนุญาตประกอบวิชาชีพของนักศึกษาชั้นปีสุดท้าย (สอบ 8 วิชา หลายครั้ง/หลายรอบ) ซึ่งเดิมจดกระจัดกระจาย
ระบบนี้รวมเป็นที่เดียว: นักศึกษากรอกผล + แนบหลักฐาน → เจ้าหน้าที่ตรวจยืนยัน → ผู้บริหารดูสถิติอัตราผ่าน/ไม่ผ่าน
ใช้ภายในคณะพยาบาลเท่านั้น ไม่เชื่อมหน่วยงานอื่น

**ผู้ใช้ 3 กลุ่มหลัก (+ 1 กลุ่มเสริม):**
| กลุ่ม | ทำอะไรได้ | ทำอะไรไม่ได้ |
|---|---|---|
| นักศึกษา (`student`) | กรอกผล แนบหลักฐาน (PDF/JPG/PNG สูงสุด 5 ไฟล์) ลบไฟล์ของตัวเอง ดูสถานะ/ประวัติ/ประกาศ แจ้งเตือน · แก้ใบที่ถูกตีกลับได้แม้รอบปิด | เห็นข้อมูลคนอื่นไม่ได้ |
| เจ้าหน้าที่คณะ (`officer`) | ทุกอย่างด้านจัดการ: ตรวจ/ยืนยัน/ถอนการยืนยัน, รอบ, รายวิชา, ผู้ใช้, ประกาศ, นำเข้านักศึกษา, รายงาน/ส่งออก | — (สิทธิ์สูงสุด) |
| ผู้บริหารคณะ (`executive`) | ดู Dashboard สถิติ + รายงานสรุป (อ่านอย่างเดียว) | ดูรายบุคคล/ไฟล์ไม่ได้ (data minimization), แก้ข้อมูลไม่ได้, ส่งออกรายชื่อไม่ได้ |
| **ผู้ช่วยตรวจสอบ** (`reviewer` — ชื่อบนจอเปลี่ยนจาก "เจ้าหน้าที่ตรวจสอบ" เมื่อ 1 ต.ค.) | ตรวจ/ยืนยัน/ตีกลับ ในคิวเดียวกับ officer เปิดไฟล์หลักฐานได้ | ถอนการยืนยัน, จัดการรอบ/ผู้ใช้/ประกาศ, ส่งออก, ลบไฟล์ (403 ทุกข้อ — เทส PH26-17) |

**Tech stack + เหตุผล (ตอบกรรมการได้):**
| ชั้น | เทคโนโลยี | ทำไมเลือก |
|---|---|---|
| Frontend | React + Vite | แบ่งเป็น component ใช้ซ้ำ, state เปลี่ยนแล้วจอ update เอง, Vite เริ่มเร็ว |
| Backend | Node.js + Express | ภาษาเดียวกับ frontend (JS), เรียบง่าย, มี middleware ชัดเจน |
| Database | PostgreSQL + Prisma | ข้อมูลมีความสัมพันธ์ชัด (นักศึกษา→ผลสอบ→รายวิชา) เหมาะฐานข้อมูลเชิงสัมพันธ์; Prisma ทำ schema กลาง + ปลอดภัยจาก SQL injection |
| Auth | bcrypt + JWT ใน httpOnly cookie | ตั้งใจใช้ PSU One Passport แต่ขอ credential ไม่ได้ จึงออกบัญชีเอง |

## 4. ฐานข้อมูล 13 ตาราง

> `CLAUDE.md` เขียนไว้ 11 ตาราง (ตาม data dictionary รายงาน). โค้ดตอนนี้มี 13: เพิ่ม `rooms`, `notifications` (อยู่ใน `docs/report-fixes.md` B6–B7) และ `review_logs` — **ตรวจให้แน่ว่ารายงานฉบับสุดท้ายมีครบ 13**

| ตาราง | เก็บอะไร | คอลัมน์ที่ต้องรู้ |
|---|---|---|
| `roles` | ชื่อบทบาท | `role_name` (student/officer/executive/reviewer) |
| `users` | ทุกคนที่ login ได้ | `psu_passport_id` (unique, ใช้เป็นรหัสผู้ใช้), `password_hash`, `must_change_password`, ชื่อ/อีเมล/เบอร์ (nullable), `import_academic_year` |
| `faculties` | คณะ | ปัจจุบันมีคณะเดียว |
| `rooms` | ห้องเรียน (ปกติ/อังกฤษ) | `room_name` |
| `students` | ข้อมูลเฉพาะนักศึกษา | `student_id` (PK), `academic_year` (ปีที่จบ), `first_name_en/last_name_en`, `exam_eligible` |
| `subjects` | 8 วิชา | `subject_code`, `subject_name` |
| `submission_rounds` | รอบการกรอก | `academic_year`, `attempt_number`, `open_date/close_date`, `status` (open/closed), `subject_ids[]`; unique(ปี, ครั้งที่) |
| `exam_results` | ใบผลสอบ 1 ใบ/คน/รอบ | `student_status`, `staff_status`, `remark`, `confirmed_by/at`; unique(student_id, round_id) |
| `subject_results` | ผลรายวิชาในใบ | `is_passed`, `carried_forward` (true = ยกมาจากรอบก่อน ไม่ได้สอบในใบนี้ — หลังแก้ B1 ไม่ถูกนับเป็น "ผ่านจริง" ที่ใดเลย) |
| `certificates` | ไฟล์หลักฐาน (ใบละได้หลายไฟล์ สูงสุด 5 — คุมที่โค้ด ไม่ใช่ที่ตาราง) | `file_path` (ไม่เก็บ binary), `file_type` (pdf/jpg/png จากไบต์ต้นไฟล์), `file_name`, `certificate_type` |
| `news` | ประกาศ | `round_id` (บังคับ), `image_path`, `posted_by` |
| `notifications` | แจ้งเตือนของนักศึกษา | `type` (approved/rejected/revoked/eligible), `is_read` |
| `review_logs` | ประวัติการตรวจ (เพิ่มอย่างเดียว ไม่ทับ) | `action` (approved/rejected/revoked), `reviewer_id`, `remark` |

**ER diagram ย่อ (วาดบนกระดาษให้ได้):**
```
roles 1──M users 1──0..1 students M──1 rooms
                │                │
                │                └─ 1──M exam_results M──1 submission_rounds
                │                         │   │                │
                │                         │   └─1──M certificates
                │                         └─1──M subject_results M──1 subjects
                │                         └─1──M review_logs M──1 users (ผู้ตรวจ)
                ├─ 1──M submission_rounds (created_by)
                ├─ 1──M news (posted_by) M──1 submission_rounds
                └─ students 1──M notifications
```

**ทำไมแยก `users` กับ `students`:** เจ้าหน้าที่/ผู้บริหารก็ login ได้ แต่ไม่มีข้อมูลนักศึกษา → `users` เก็บตัวตนร่วม `students` เก็บเฉพาะของนักศึกษา (ความสัมพันธ์ 1 : 0..1)
**ทำไมแยก `exam_results` กับ `subject_results`:** ใบผลสอบ 1 ใบมีหลายวิชา (1 : M) — แยกตารางเพื่อไม่ให้คอลัมน์บวมและสถิติรายวิชาคำนวณได้ตรง ๆ
**ทำไมมี `review_logs`:** `exam_results.confirmed_by` เก็บแค่ผู้ตรวจล่าสุด (และถูกล้างเมื่อนักศึกษาส่งใหม่) ส่วน log เป็นประวัติ "ใครตัดสินอะไรเมื่อไหร่" ที่ตรวจย้อนหลังได้

## 5. วงจรสถานะ (state machine) — ต้องวาดได้

### 5.1 ใบผลสอบ (`exam_results`) — สองสถานะแยกกัน
- `student_status`: `draft` (ยังกรอกไม่เสร็จ) → `submitted` (ส่งแล้ว)
- `staff_status`: `pending` (รอตรวจ) → `approved` (ยืนยัน) **หรือ** `rejected` (ตีกลับ)

```
นักศึกษาส่ง ──▶ [รอตรวจ] ──ยืนยัน──▶ [ยืนยันแล้ว] ──ถอนการยืนยัน(officer)──▶ [รอตรวจ]
                   │                      ล็อก: นักศึกษาแก้ไม่ได้ (409)
                   └──ตีกลับ(ต้องมี remark)──▶ [ถูกตีกลับ] ──นักศึกษาแก้แล้วส่งใหม่──▶ [รอตรวจ]
                                                              (ใบเดิม result_id เดิม ไม่สร้างใบที่สอง)
```
กติกา (ปรับ 1 ต.ค.):
- รอบยังเปิดรับ → นักศึกษาแก้ได้ทั้งใบ **รอตรวจ** และ **ถูกตีกลับ** (แก้ผล + แนบ/ลบไฟล์)
- รอบปิดแล้ว → แก้ได้ **เฉพาะใบที่ถูกตีกลับ** ของ **รอบล่าสุด** ของรุ่น (`findSubmittableRound`) · ใบรอตรวจหลังปิดรอบแก้ไม่ได้ ต้องรอเจ้าหน้าที่ตรวจ · ถ้ามีรอบใหม่เปิดอยู่ ให้แก้ในฟอร์มของรอบใหม่
- เจ้าหน้าที่/ผู้ช่วยตรวจได้ทั้งระหว่างรอบและหลังปิดรอบ
- ใบที่ตรวจแล้วตรวจซ้ำตรง ๆ ไม่ได้ (409) ต้องกลับเป็น pending ก่อน (นักศึกษาส่งใหม่ หรือเจ้าหน้าที่ถอนการยืนยัน)

### 5.2 รอบการกรอก (`submission_rounds`) — สถานะใน DB กับ "สถานะจริง"
DB เก็บแค่ `open`/`closed` (เจ้าหน้าที่กดเอง) แต่ **สถานะจริง (phase)** คำนวณตอนตอบทุกครั้งจากวันที่ด้วย `utils/roundPhase.js`:

| phase | เงื่อนไข | นักศึกษากรอกได้? |
|---|---|---|
| `closed` | status ≠ open | ไม่ได้ |
| `scheduled` | open แต่ยังไม่ถึง `open_date` | ไม่ได้ (บอกวันเปิดให้) |
| `active` | open และอยู่ในช่วง open_date–close_date | **ได้** |
| `expired` | open แต่เลย `close_date` (ยังไม่ได้กดปิด) | ไม่ได้ (เตือนเจ้าหน้าที่ให้ปิด) |

> ข้อยกเว้นของ `closed`/`expired`: ใบที่ถูกตีกลับของรอบล่าสุดยังแก้ได้ — `GET /api/rounds/active` ส่ง `can_fix_rejected: true` มาให้หน้าเว็บเปิดฟอร์มแม้ phase ไม่ใช่ `active`

**ทำไมไม่เก็บ phase ลง DB:** ค่าเปลี่ยนเองตามเวลาโดยไม่มีใครกดอะไร ถ้าเก็บต้องมีตัวตั้งเวลามาอัปเดต — คำนวณตอนอ่านง่ายและไม่เพี้ยน
กติกาเพิ่ม: เปิดรับได้ **ทีละรอบเดียวทั้งระบบ** · ปี+ครั้งที่ซ้ำไม่ได้ (unique) · เปิดแล้วห้ามแก้วิชา

## 6. ข้อตกลงข้าม frontend/backend (contract)

- Response สำเร็จ: `{ success: true, data: ... }` · Error: `{ success: false, message: "ข้อความไทย" }` + status code
- Auth: cookie `token` (httpOnly) — frontend ไม่เคยแตะ token; เก็บแค่ object ผู้ใช้ใน localStorage ไว้วาด UI ตอนรีเฟรช
- ทุก endpoint ที่ไม่ public ต้อง `authenticate` ก่อน `requireRole`
- ชื่อ field ใน DB เป็น `snake_case` ตาม data dictionary ในรายงาน

## 7. เช็คตัวเองก่อนไปไฟล์ถัดไป
1. วาดแผนผังระบบ 3 ชั้นได้ไหม และบอกได้ไหมว่าใครคุยกับใคร
2. บอกได้ไหมว่าทำไมต้องมี `subject_results` แยกจาก `exam_results`
3. อธิบายความต่างของ status `open` ใน DB กับ phase `active` ได้ไหม
4. บอกได้ไหมว่าผู้บริหารทำอะไรไม่ได้ และกันที่ชั้นไหน (ตอบ: ที่ backend ด้วย `requireRole` ไม่ใช่แค่ซ่อนปุ่ม)
